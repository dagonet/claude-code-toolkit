# v4.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship toolkit/server v4.1.0 — option B: the template `CLAUDE.md` becomes byte-identical per variant (region removed, `@.claude/project-instructions.md` last), per-agent project tool grants live in `.claude/agent-grants.json` and are spliced by the server, a project-scope PreToolUse hook denies editing-tool writes to a v4 consumer's `CLAUDE.md`, manifest v4 with a refuse-not-guess v3→v4 migration, skill floor `>=v4.1.0`.

**Architecture:** Five stacked task PRs onto `v4/1` (cut from main at `150627d`, the v4.1 spec merge on top of the v4.0.3 release commit `7f9634e`): the server task and the hook task in parallel from the plan tip (disjoint trees), then the templates/consistency/bootstrap task from the merged tip (it registers the hook and declares the floor the server enforces), then the skill/docs task, then the release task. Every sha reviewed by the outside session; the controller runs the full gate at merge time.

**Tech Stack:** Python 3.12+ server (`server/src/template_sync`, pytest), Bash hooks (`hooks/`, fixtures in `scripts/test-hooks.sh`), the consistency script, six template variants, `setup-project.sh`/`.ps1`, markdown skill body, docs.

**Spec:** `docs/plans/2026-09-18-v4.1-design.md` — the authority; each task names its sections. Line numbers were measured on main `7f9634e` (v4.0.3) on 2026-09-19.

## Global Constraints

1. Every PR and every fix reviewed by `mcp-dev-servers-update-cc-template` at the exact sha in a detached worktree. Task PRs stack onto `v4/1`, true merges, no rebases; release PR `v4/1 → main`; tag `v4.1.0` on the merge commit.
2. All commits in worktrees. Implementers run only the suites their task touches, in the FOREGROUND (`bash scripts/test-hooks.sh > <log> 2>&1`, timeout 600000, bounded `until` polls if the harness backgrounds it at 600 s; `bash scripts/test-server.sh` after `bash server/install.sh` in the worktree; `bash scripts/verify-template-consistency.sh`). Never background a suite; never run `test-hooks.sh` concurrently with another suite or gate (shared gate dir).
3. Every file LF (`git diff --check`). A root hook change is mirrored to `user-level-reference/hooks/` in the same commit (check 21a) — EXCEPT hooks listed in `HOOKS_NO_MIRROR`, which have no mirror by design; `deny-claude-md-writes.sh` joins that list (spec §6).
4. Every behaviour change ships with the test that fails without it; RED observed first (state the failing line in the report), then GREEN; two-sided fixtures (the deny AND the allow case; the refusal AND the acceptance).
5. Derived, never hard-coded, except where the expectation IS the decision: `UNGRANTABLE_TOOLS` is a hand-written literal asserted with `⊆` (spec §4); the closed status tuple gains `MIGRATION_REQUIRED` by hand (spec §7); the exact skip/info sets and `len(LINES)` are stated by hand and move in the SAME commit that adds the ids (reviewer criterion 4).
6. A check's passing output is distinguishable from its null case; a verify line's expected end state is stated per mode AND per manifest version (v4; the v3 window).
7. Second-instance rule: after fixing a pattern, grep for its other copies and pin them together; list them in the PR body. Specifically: ten sites call `_apply_placeholders` on template content today (whole-file grep; the base provider `resolve_base` and the two stored-hash writers `finalize_v3`/`migrate_v2_to_v3` included) — all ten go through the one helper Task 1 introduces, and the test asserts the INVARIANT (zero call sites outside the helper), never the count (spec §5, reviewer D3/H1/H2). When a fix enumerates call sites, the enumeration is a measurement and gets the same whole-file grep the claim got.
8. Stage NAMED paths only — never `git add -A`, `git add .`, `git commit -a`. Never push. Never create `.claude/git-guard-off`. No `git stash`. Commit with `git commit -F <msgfile outside the repo>`; the message ends with the two attribution lines the controller supplies. Never amend after reporting — a fix is a new commit.
9. The acceptance rule for any new assertion (reviewer): a one-line change to the production code must be able to make it fail. If not, it is not a check — reduce or drop it and say so.
10. Bytes are measured with `wc -c` (or `LC_ALL=C awk`) in the task that changes them, and the measured numbers go in the report; nothing is cited from the spec's §2.
11. Every new status, field, or verify line is checked against "what else measures this?" before it lands (spec §7): the closed partition, the exact info/skip sets, `len(LINES)`, `_SHAPE_INDEPENDENT`, the CLI/fleet printers, the skill's per-mode expected lines.
12. Nothing in this plan synthesises a `tools:` line for an agent that ships none (spec §5, reviewer D1). Per ruling R-E no shipped agent lacks one today; the rule is witnessed with a fixture agent and stands for any future agent. No task adds, removes, or reshapes any shipped agent's `tools:` line.
