# v6.1 Implementation Plan: mcp-dev-servers as dagonet plugins, plus the security fixes

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** release v6.1.0. It brings six independent, uvx-started MCP server plugins to the public `dagonet` marketplace, with no guard weaker than before, and the four v6.1 hook security fixes.

**Architecture:**

- **The plugins.** Each server is a two-file plugin under `plugins/<name>/` in this repo, listed in `.claude-plugin/marketplace.json`. Its `.mcp.json` starts the server with `uvx`, pinned to the tagged mcp-dev-servers commit.
- **The rename.** The plugin form renames every tool to `mcp__plugin_<name>_<name>__<tool>`. Each rule that names an old-form tool gets its twin, and a new consistency check keeps the pairs together.
- **The security fixes** are small edits to `hooks/lib/json.sh`, `hooks/lib/git-cmd.sh`, `hooks/hooks.json` and `hooks/dispatch.sh`. Each one is red-tested first.

**Tech Stack:** bash, python3/node/jq JSON readers, Claude Code plugin manifests, uv/uvx, PowerShell (setup-project.ps1).

**Spec:** `docs/plans/2026-11-09-v6.1-mcp-plugins-and-security-design.md`. Executors read both files. Section references (§) point at the spec.

## Global Constraints

- **Branches and merges.** Work happens on `feat/v6.1` in `~/git/.worktrees/claude-code-toolkit/v61`. Never push to `main`; the user merges the pull request.
- KISS: the simplest correct change, and a strict refusal rather than modelling more behaviour.
- **File format.** Every file is LF.
- **Templates.** `templates/*/.claude/settings.json` and `AGENT_TEAM.md` stay byte-identical across the six variants: edit `templates/general/` first, then `cp` to the other five.
- **Versions.**
  - `.claude-plugin/plugin.json` and all six `plugins/*/.claude-plugin/plugin.json` carry `version` == `VERSION` line 1.
  - The release sets `VERSION` to `6.1.0`, and line 2 to `v6.1.0: the mcp-dev-servers as six opt-in plugins; four hook security fixes`.
- **No machine-wide files at the root.** Never add a root `.mcp.json`, `settings.json`, `commands/` or `.lsp.json`; the cct plugin root is the repo root.
- **Plugin names and server keys:** `git-tools`, `github-tools`, `dotnet-tools`, `ollama-tools`, `rust-tools`, `python-tools`.
- **Plugin-form tool prefix:** `mcp__plugin_<name>_<name>__`. Task 0 may correct it; a correction is recorded as a ruling.
- **The mcp-dev-servers pin.**
  - The SHA is `0a20b97dd42733c629e369e16f4e79af81f93d47`, the commit of tag `v0.4.0`. The tag is annotated (object `21ac945…`), so peel it with `^{commit}`.
  - The exact `.mcp.json` command: `"command": "uvx"`, `"args": ["--from", "mcp-dev-servers @ git+https://github.com/dagonet/mcp-dev-servers@0a20b97dd42733c629e369e16f4e79af81f93d47", "mcp-<name>"]`.
- **Public plugins.** No plugin file holds a machine path, a hostname, a user name or a default enablement.
- **Environment safety.**
  - Never print environment variable values; check names or presence only.
  - Run hooks and test suites with `env -u TYPESAFE_API_KEY`.
- **`claude plugin` and installer experiments** run only with `HOME=$(mktemp -d)` and `env -u CLAUDE_CONFIG_DIR`. Never copy `~/.claude/.credentials.json`. Never touch the live `~/.claude`.
- **The gate:**
  - `bash scripts/verify-template-consistency.sh`, `bash scripts/test-hooks.sh` and `bash scripts/test-server.sh`, run through `hooks/run-gate.sh` in the FOREGROUND with timeout 600000.
  - `scripts/test-hooks-parser-matrix.sh` runs after anything touching `hooks/lib/json.sh`, or a hook that embeds a node program.
  - Both are machine-wide jobs: the controller announces them, and they never overlap.
- **PC jobs** go through the PC helper (cc-toolkit-windows). Heavy runs wait for mm-agent's all-clear.
- **Logs.** Bulky logs go to `~/.cache/cct-v61/`, never to `/tmp/claude-1000`.
- **Shell rules for this host:**
  - no leading `cd X &&` chains (write a script file and run `bash <path>`);
  - `git -C` takes a literal absolute path;
  - no heredocs in Bash commands;
  - push, pull and tag each run as their own call.
- **Tests first.** Every behaviour change starts with a failing test. Every new check is two-sided: a fixture that must fail, and the real tree that must pass.

## Review Focus

1. **A stranger installs a plugin without `uv`.** The server cannot start; Claude Code shows it as failed in `/mcp` only. The user should learn the prerequisite before installing. Pinned by check 77: every sub-plugin description names `uv` (Task 5).
2. **An old `claude mcp` registration and the plugin both run.** That gives duplicate tools and two processes. The drift probe must report it (Task 7, row "shadowing user-scope entry → drift").
3. **A command exactly at the size cap.** It must route normally, and one byte over it must refuse (Task 4, boundary rows N and N+1).
4. **A twin present in the template allow list but missing from the deny list,** or the reverse. A missing deny means an MCP push. Check 78 must go red (Task 6, fixture rows for an allow-only and a deny-only twin).
5. **A stranger's first session with several plugins and an empty uv cache.** Six uvx processes build the same package at once. uv may also download a Python, and a stdio server that misses the connect timeout is not retried for 15 minutes. Expected: the servers come up, or the README tells the user to warm the cache once. Pinned by Task 0 Step 1 (the cold-cache measurement) and Task 9 Step 1 (the warm-up line if needed).

(A sub-plugin `version` not bumped with `VERSION` is pinned by the widened check 72 in Task 5.)
