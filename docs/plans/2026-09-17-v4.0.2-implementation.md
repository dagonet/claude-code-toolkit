# v4.0.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship toolkit/server v4.0.2 — the eighteen v4.0.1 rollout follow-ups, one of them a real `template_verify` defect — each fixed at its source with a test that was red first.

**Architecture:** Six stacked task PRs onto integration branch `v4/0.2`: two server tasks first (the verify defect and the identity/registry pin), then three parallelisable tasks on disjoint files (verify lines + seeds, hooks + rows, skill/doc text), then the release task. Every task is reviewed by the outside session at its exact sha; the controller runs the full gate at merge time.

**Tech Stack:** Python 3.12+ (`server/src/template_sync`, pytest in `server/tests`), Bash hooks (`hooks/`, fixtures in `scripts/test-hooks.sh`), markdown skill body, six template variants.

**Spec:** `docs/plans/2026-09-17-v4.0.2-design.md` — the authority; each task names the spec items it implements. Executors read the spec item(s) for their task; the spec's measured line numbers were taken against main `a97235b` on 2026-09-17.

## Global Constraints

1. Every PR and every fix is reviewed by `mcp-dev-servers-update-cc-template` at the exact sha in a detached worktree. Task PRs stack onto `v4/0.2`, true merges, no rebases. The release PR merges `v4/0.2 → main`; the tag goes on that merge commit.
2. All commits happen in worktrees. Implementers never run the full gate (the controller does); they run the suites their task touches: `bash scripts/test-server.sh` (needs `bash server/install.sh` once in the worktree — a worktree's server tests need that worktree's own venv, or `PYTHONPATH=<wt>/server/src`; verify `template_sync.__file__` points into the worktree), `bash scripts/test-hooks.sh`, `bash scripts/verify-template-consistency.sh`.
3. Every file LF (`git diff --check`; `file <path>` shows no CRLF). Byte-identical variant files are edited in `templates/general/` then `cp`'d to the other five.
4. Every fix ships with the test that fails without it: write the test, run it RED, fix, run it GREEN. A fixture or verify line is two-sided (failing case demonstrated).
5. Expectations are derived, never hard-coded (keys from the variant, commit from HEAD, tool names from the live registry).
6. A check's passing output must be distinguishable from its null case (in-band SKIP with a reason; INFO lines have a null-case text).
7. Capabilities, not versions: `EXPECTED` in `test_template_sync_capabilities.py` pins the set exactly; new names this release: `deleted_acknowledged` (Task 1), `registered_tools` (Task 2). Each with a behavioural witness in `WITNESSES`.
8. Second-instance rule: after fixing a pattern, grep the tree for other copies and pin them together; list them in the PR body.
9. An implementer who finds a stated defect already green STOPS and reports (status `DONE_WITH_CONCERNS`), never writes a test that was never red.
10. Never `git add -A` / `git add .` / `git commit -a`; stage named paths. Never push to `main`. Never create `.claude/git-guard-off`. Commit messages end with the attribution lines the controller supplies in the brief.
11. A release note never names a directory to delete; a rollout notice never pins a sha.
12. Skill body (`SKILL.md`) carries no `$0..$9` / `$ARGUMENTS` (check 47); `region.sh` is invoked by absolute path `~/.claude/skills/sync-template/region.sh`.
