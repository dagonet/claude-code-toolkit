**Status:** spec, 2026-09-18. Authority for the v4.0.3 task plan.
**Source of the backlog:** the v4.0.2 consumer rollout (all five consumers synced 2026-09-18; every item below was measured by a consumer session or the reviewer against v4.0.2). Ledger: `.superpowers/sdd/2026-09-17-v4.0.2-implementation/progress.md`, "Consumer rollout on v4.0.2" (candidates #1–#13; #3 was never assigned).
**Version:** toolkit `4.0.3`, server `4.0.3` (verify changes), skill marker `v4.0.3` (skill text changes). `manifest_version` stays **3**; no floor raise. v4.1 (option B) is a separate spec and branch; v4.0.3 lands on main first.

## Goal

Close the four measured gaps with consumer cost (the script-file commit-gate bypass, the review-wait re-gate, the double FAIL for one accepted deviation, the legacy no-op record that reappears) and the eight wording/pin items around them, with a test that was red first for every behaviour change. No migration; every consumer absorbs it with a plain sync.

## Non-goals

- Option B / agent grants / the region seed's MCP guidance line (v4.0.2 item 3) — **moved to v4.1** (ruling R1 below): option B removes the PROJECT-CUSTOM region from the template `CLAUDE.md`, so a seed line inside that region has no future; the guidance goes into the `.claude/project-instructions.md` seed instead, where neither the byte budget nor the single-placeholder classifier applies.
- Any change to `is_empty()`/the region classifier or `BUDGET_CLAUDE_MD` (same reason).

## Global constraints (bind every task)

1. Every PR and every fix reviewed by the outside session at the exact sha in a detached worktree; task PRs stack onto `v4/0.3`, true merges; release PR `v4/0.3 → main`, tag on the merge commit.
2. Commits in worktrees; the gate in the detached gate worktree with its own venv (`bash server/install.sh` once there, again after the VERSION bump); never run `test-hooks.sh` or the gate while another worktree commits or runs git (shared gate dir — the self-gate rows are immune since v4.0.2 but other rows and the pre-commit hook still write there).
3. Gate = the three commands via `bash hooks/run-gate.sh > <log> 2>&1`, never piped.
4. Every file LF; byte-identical variant files edited in `templates/general/` then copied; the user-level hook mirrors updated in the same commit as the root hook (check 21a).
5. Every fix ships with the test that fails without it; two-sided fixtures; an implementer who finds a stated defect already green stops and reports.
6. Expectations derived, never hard-coded (the derive-vs-hard-code rule: hard-code only what IS the decision).
7. A check's passing output is distinguishable from its null case.
8. Capabilities, not versions; no new capability names in this release (no skill branches on any change here).
9. Second-instance rule: after fixing a pattern, grep for its other copies (the three hooks that parse command strings; the two gate-dir writers; the two remedy strings).
10. A release note never names a directory to delete; a rollout notice never pins a sha; the expected verify line is stated PER MODE (pre_commit has 1 SKIP by design).
11. Implementers run every suite in the FOREGROUND (timeout 600000) — two v4.0.2 implementers stalled on their own background suites.

### A. Hooks (`hooks/`, mirrors in `user-level-reference/hooks/`)

**#12 — `bash <script>` bypasses the commit gate.** Defect (MM-Agent, measured): `pre-commit-test.sh` parses the command string only; `gc_segments` (`git-cmd.sh:402-404`) strips quotes and splits on `| ; &&`, and the awk matcher unwraps `bash -c "…"`/`sh -lc`/`(…)`/`$(…)` — but a segment whose first token is `bash`/`sh` and whose argument is a FILE is never opened, so `bash script.sh` containing `git commit` commits ungated (a gated commit costs ~14 min of dotnet test there; the script-file commit returned in seconds). The user-level `CLAUDE.md:15` rule ("Write the logic to a script file and run `bash <path>`") steers people into the shape; no comment documents the gap. Fix: a new `gc_script_body <segment>` in `git-cmd.sh`: when a segment's first token (after wrappers) is `bash`, `sh`, `source` or `.`, and the first non-option argument names an existing REGULAR file (`[ -f ]`, never `[ -r ]` — a directory is readable and `bash somedir` is a plausible typo; resolved against the payload cwd; MSYS and Win32 spellings both), the first 16 KB of the file's text (`head -c 16384`, stated in the header comment — an unbounded read inside a PreToolUse hook is a latency footgun on a vendored or generated script) is appended to the command text the matcher sees — as additional segments, so the existing per-segment logic applies unchanged; depth 1 only (a script invoking another script is the documented residual gap, stated in the header comment, beside the TOCTOU residual: the hook reads the file, allows the command, and nothing stops the file changing before bash runs it — unfixable at this layer, written down so nobody believes the gate is stronger than it is); an absent path or a non-regular file adds nothing (bash fails on it anyway); `-c` payloads keep the existing route. Applied in all three parsers of command strings: `pre-commit-test.sh` (commit), `gate-before-merge.sh` (merge/push), `no-push-main.sh` (push) — constraint 9. The user-level `CLAUDE.md:15` sentence becomes "Write the logic to a script file and run `bash <path>` — the guard hooks read the script's text, so a `git commit`/`merge`/`push` inside it is gated exactly as if typed". Test rows (`test-hooks.sh`): `bash s.sh` where `s.sh` contains `git commit -m x` → the Test runs (RED today: no run); `bash s.sh` without a git verb → no run; `bash missing.sh` → exit 0, no run; `sh -c "git commit"` unchanged; `. s.sh` and `source s.sh` → run; a script whose ONLY git verb is inside a nested `bash inner.sh` → not gated (the documented residual, pinned so it cannot silently widen); the same shape through `gate-before-merge.sh` (`bash m.sh` containing `git merge feature` on main → 2) and `no-push-main.sh` (`bash p.sh` containing `git push origin main` → 2). Files: `hooks/lib/git-cmd.sh`, `hooks/pre-commit-test.sh`, `hooks/gate-before-merge.sh`, `hooks/no-push-main.sh` (+ their `user-level-reference/hooks/` mirrors), `user-level-reference/CLAUDE.md`, `scripts/test-hooks.sh`.

**#13 — a tree-identical expired artifact forces a full re-gate.** Defect (penumbra, second consecutive sync; also v4.0.0): the commit-time gate mints a valid artifact, the PR waits on the user's merge decision, and at merge time the artifact is past the 3600 s TTL with the tree unchanged (4 h 52 m; 35412 s at v4.0.0) — a PO who cannot run the gate spawns an ops agent to re-earn a green that never went red. Mechanism: `gate-before-merge.sh:1438-1444` applies the TTL uniformly AFTER the three lookup tiers, all of which already matched on `tree`. Fix: the TTL check distinguishes two bindings — an artifact selected by SHA only (tier 1, or a tree scan whose `tree` field is absent) keeps the 3600 s TTL; an artifact whose `tree` equals `HEAD^{tree}` is accepted up to the prune window (`GC_GATE_TTL_S * 24`, the same derived constant `run-gate.sh` prunes by — one definition, asserted equal by the existing copy check), with the allow message naming the reason ("accepted on tree identity: age Ns exceeds the TTL, tree unchanged"); beyond the prune window, blocked as today. Rationale: the TTL guards a sha whose tree may have moved on; a tree that has not moved is the stronger binding for the CODE. **The tree is not the environment** (reviewer): the gate's third command runs against `server/.venv`, which was reinstalled at 4.0.2 minutes before this release's own gate — an artifact minted before such a reinstall, tree-identical, would bless a tree whose server suite now runs against a different venv. So the extended window additionally requires an ENVIRONMENT FINGERPRINT match: `run-gate.sh` records `"env": "<sha256>"` over (the bytes of `server/.venv/pyvenv.cfg`, the SORTED LISTING of every `*.dist-info` directory name under the venv's `site-packages` — a directory read that moves on any install, upgrade or removal, so `pip install -U mcp` into an existing venv changes the fingerprint (reviewer: one dist-info name would only catch venv recreation, the case that bit us, not the upgrade most likely next), `python --version` of the venv interpreter, `node --version` if node is on PATH — each contributor labelled, missing ones recorded as `absent` so the hash is defined), and `gate-before-merge.sh` recomputes it at merge time; the extension applies only when `env` is present AND equal; a missing or different `env` keeps the 3600 s rule with the block message naming which contributor differs ("tree unchanged, environment changed: <label>"). The 3600 s sha-binding stays fingerprint-free. Skill step 9 (`SKILL.md:1160`) says: a review-gated sync re-gates only if the tree changed, the environment fingerprint changed, or more than 24 h passed. Test rows: expired + identical tree + identical env → 0 with the reason in the message; expired + identical tree + different env (fixture edits a pyvenv.cfg byte) → 2 naming the contributor; expired + different tree → 2; identical tree + env but older than the prune window → 2; a sha-only artifact (no `tree` key) expired → 2; an artifact with `tree` but no `env` (older writer) expired → 2 (no silent extension). Files: `hooks/gate-before-merge.sh` (+ mirror), `scripts/test-hooks.sh`, `SKILL.md` step 9, `docs/template-sync.md`.

**#8 — `gc_gate_dir` on an unresolved target: a stray path and a false diagnosis (R2).** Defect (reviewer, measured on git 2.55): `gc_gate_dir <non-repo path>` (`hooks/lib/git-cmd.sh:788-794`; the standalone copy in `run-gate.sh`) fails both `rev-parse` calls, prints the literal `/.gate` (the MSYS root — `C:\Program Files\Git\.gate` — outside every repo), emits `WARN: git < 2.31 …` (false on git 2.55) and lets the fallback's `fatal: not a git repository` leak beside it; `gc_gate_dir ""` resolves against the PROCESS cwd and returns the correct directory of the wrong repo. A hook segment such as `git -C <non-repo> status` reaches this path. Fix: FIRST LINE of the function, before any git call: `[ -n "$1" ] || return 1` — an empty target never fails a git command (`git -C ""` means "the cwd") and so returns a plausible answer for the wrong repo with rc 0; the guard must precede the thing that succeeds for the wrong reason (reviewer). Then the fallback is taken only when the failure IS the git version (probe `git rev-parse --path-format=absolute --git-common-dir` on a directory that `git rev-parse --show-toplevel` accepts; if `--show-toplevel` fails, the target is unresolved) — unresolved → return non-zero, print nothing, no WARN; git < 2.31 → the documented WARN + `<toplevel>/.gate`, stderr of the probe swallowed. Every caller (`pre-commit-test.sh`'s note and artifact writers, `run-gate.sh`) skips the write when the function fails: a diagnostic must never land outside the repo the command was about. The record gains `"gate_dir":"<absolute path>"`. Test rows: `gc_gate_dir <non-repo path>` → rc 1, empty stdout, empty stderr, and `[ ! -e "/.gate" ]` afterwards (RED today: prints `/.gate` and the false WARN); `gc_gate_dir ""` → rc 1 (an empty target is unresolved, never "the cwd"); a `git -C <non-repo> status` segment through `pre-commit-test.sh` → exit 0 and no file written anywhere (pin with a listing of the shared gate dir before/after by NAME, per v4.0.2 R6); git-version fallback still reachable (a mock `git` on PATH that rejects `--path-format` but answers `--show-toplevel`) → WARN + legacy path (existing behaviour, pinned). Files: `hooks/lib/git-cmd.sh`, `hooks/pre-commit-test.sh`, `hooks/run-gate.sh` (its standalone copy of the function — the copy check must still pass), mirrors, `scripts/test-hooks.sh`, `scripts/verify-template-consistency.sh` (the two-copies-agree assertion, if the function grows).

**#4 — pre-commit records are never pruned.** Defect (open-brain, Yutraffic): `run-gate.sh:338-339` prunes `last-pass.*.json` older than `GC_GATE_TTL_S * 24 / 60` minutes at the next gate run; `pre-commit-test.sh` has no prune for `last-precommit.<tree>.json` / `last-precommit-noop.*.json` (grep: none), so they grow one per tree forever. Fix: the same `find … -mmin "+$prune_min" -delete` line, same derived constant, for the two precommit families, run at the artifact write path in `pre-commit-test.sh` (never on the read path — a read must not have side effects). Test rows: an artificially aged (`touch -d '-2 days'`) precommit record is gone after the next commit-path write, a fresh one stays; the noop family likewise. Files: `hooks/pre-commit-test.sh` (+ mirror), `scripts/test-hooks.sh`.

### B. Server — `template_verify` (`server/src/template_sync/verify.py`)

The second line's "IDENTICAL == template-class count" is a drift assertion duplicated from the first. Fix: `classes_and_hashes` asserts entry SHAPE (template-with-hash / once-without-hash, as today) and that the status PARTITION is complete — every template-class entry has exactly one status among `IDENTICAL`, `TEMPLATE_UPDATED`, `LOCAL_EDITED`, `TEMPLATE_DELETED`, `ACKNOWLEDGED_KEPT`, `CONFLICT`, and their counts sum to the template-class count; drift belongs to `status_clean` alone. `measured` lists the partition (`identical=N template_updated=N local_edited=N …`) on both branches. **The enumeration is EXPLICIT and closed** (reviewer): the buckets are a literal tuple `TEMPLATE_CLASS_STATUSES = ("IDENTICAL", "TEMPLATE_UPDATED", "LOCAL_EDITED", "TEMPLATE_DELETED", "ACKNOWLEDGED_KEPT", "CONFLICT")`; an entry whose status is not in the tuple falls OUTSIDE the sum and is named in `measured` as `unenumerated=<status>`; never a catch-all `else`, never a total derived from `len(entries)` — either would make the sum equal the count by construction. The general test the reviewer named applies: a one-line production change (a new status added to `compute_status_v3` without extending the tuple) must make the line FAIL. ## Risks

- #12 widens what the commit gate reads: a script that is slow to read or huge adds nothing dangerous (read-only), but a script whose text contains `git commit` in a COMMENT or a string will now trigger the Test — a false positive in the fail-closed direction, acceptable and pinned by a row (a commented `# git commit` line triggers; the label says so).
- #13 relaxes a freshness rule: bounded by the same 24 h the prune uses, and only for an identical tree; an artifact whose tree matches HEAD is by construction the artifact of the code being merged.
- #8's fix changes when a diagnostic record is written; the record is never read by enforcement, so the only risk is losing a diagnostic in the unresolved case — which is the case where the diagnostic was landing in the wrong repo.
