# v4.3.2 — native pre-push hook + faster gate hooks (design)

**Status:** draft for the user's review, 2026-10-04. **Base:** `feat/v4.3.1` at `5d3d789` (v4.3.1, not yet tagged).
**Scope decision (user, scheduled brief 2026-10-04):** a small patch release with two items: (P) a native git `pre-push` hook that refuses pushes to the protected branches however the push was started, and (F) faster gate hooks for git-shaped commands. **Standing rule:** KISS — the simplest correct design; every section says what it deliberately leaves out.

Sources: the v4.3.1 CHANGELOG *Known limits* (G3 "script scanning is best-effort"; S6 "`git status --short` still takes about 1.2-1.7 s per Bash call on Windows"; Downstream step 8 "a native git pre-push hook is planned for v4.3.2"), and the Windows measurements taken after v4.3.1.

---

## Part P — a native git `pre-push` hook

### P1. Why a native hook (the gap it closes)

**Evidence.** v4.3.1 G3 states the posture: *typed text fails closed, script scanning is best-effort*. `no-push-main.sh` is a Claude Code PreToolUse hook. It sees the command text Claude typed. It does not see a push started by a script it could not follow (`./x.sh`, a script calling a script, `pwsh -Command`, a relative script it cannot find), by a variable (`git $verb`), by an alias, or from outside Claude Code (a terminal, an IDE, a GUI client). It also cannot see `remote.<name>.push` or `push.default`. It says so in its own "Could not determine" paragraph.

**Mechanism.** Git runs `pre-push` for every `git push`, however it was started. Git passes the hook the refs it will actually update, already resolved, on stdin as `<local ref> <local sha> <remote ref> <remote sha>`. The hook needs no command parsing and no cwd tracking, so the best-effort gap closes for pushes. `--no-verify` still skips the hook (see P5).

**What it does not replace.** `no-push-main.sh` stays as it is. It refuses earlier, with Claude-specific advice, and it covers a clone where the native hook is not installed.

### P2. The hook: `hooks/git-pre-push.sh`

One new tracked file in the root `hooks/` directory. It reaches consumers the way every hook does: `setup-project.sh`/`.ps1` copy `hooks/` recursively, and the sync server tracks `hooks/**`.

**Behaviour, per stdin line:**
1. The remote ref is `refs/heads/<b>` and `<b>` is in the protected set → **refuse**. This covers create, update, force-update and **delete**: a delete has local sha `0{40}`. The message names the branch and says whether it is an update or a delete.
2. Any other ref is allowed. That includes `refs/tags/*` (**tags are allowed**, including a tag named `main`), `refs/notes/*`, and branches whose names only contain a protected name (`mainline`, `feature/main`).
3. Any refused line → exit 1. Git then aborts the **whole** push (git's own semantics: the other refs in that push do not land either). The message ends with the deliberate escape and the PR advice.

**The protected set: one source of truth.** The hook sources `hooks/lib/git-cmd.sh` and calls `gc_protected_branches "$top"`. `no-push-main.sh` uses the same function and the same `- **Protected branches**:` grammar (BOM, list marker, backticks, commas, placeholder, `none`). It is not re-implemented, so the two cannot drift. Today's default is kept: no line, an empty value or an unfilled placeholder gives `main master` plus the remote's trunk when git reports one, with the existing WARN. The brief's "default main" is a subset of that, and keeping parity with `no-push-main.sh` is the simpler rule (open question Q2).

**Fail closed.** Each of these refuses every push (exit 1) with a message that names the cause:
- `hooks/lib/git-cmd.sh` is missing, or present but corrupt (`gc_protected_branches` undefined). A missing `lib/json.sh` already makes the lib `exit 2` while it is sourced, which is non-zero.
- No repository top-level can be found.
- `PROJECT_CONTEXT.md` **exists but cannot be read**. If the hook fell through to the defaults here, a `develop` list would silently become `main master`.

A **missing** `PROJECT_CONTEXT.md` takes the default set, as it does in `no-push-main.sh`. That set protects something, so this is not a fail-open.

**Not honoured: `.claude/git-guard-off`.** That kill switch disables Claude-side gates for one fix. A native hook with two escapes is harder to reason about than one with one escape. The hook's single escape is `--no-verify` (P5).

### P3. Installation in consumer projects

**Decision: a marked shim at `<git common dir>/hooks/pre-push` that execs the tracked `hooks/git-pre-push.sh`. Do not set `core.hooksPath`.**

| Option | Against it |
|---|---|
| `core.hooksPath=hooks` (or `hooks/git`) | It **replaces** `.git/hooks` wholesale and silently disables a consumer's existing husky, pre-commit or lefthook hooks. It is local config, so it is not cloned either: no distribution advantage. `hooks/` would mean two different things (Claude hooks and git hooks). |
| Copy the full hook into `.git/hooks/pre-push` | A stale, unversioned copy. Every hook update needs a re-install, and the copy drifts from the lib it would have to inline. |
| **Shim → tracked file (chosen)** | The shim is 7 lines and never changes. The logic updates with every sync. One shim in the **common** git dir serves every linked worktree. |

**Shim** (exact text in the plan): `#!/bin/sh`, a marker line, then `exec bash "<top-level>/hooks/git-pre-push.sh" "$@"`, where the top-level is resolved by git when the hook runs. If the tracked file is missing (a branch that predates v4.3.2), the shim **refuses** and says how to resolve it: merge the trunk, or push deliberately with `--no-verify`.

**Installer:** `bash hooks/git-pre-push.sh --install [<dir>]`. One entry point used by the setup scripts, the migration step and the fixtures:
- `<dir>` is not in a git repository → print `not installed: not a git repository — run 'bash hooks/git-pre-push.sh --install' after 'git init'`, exit 1.
- `core.hooksPath` is set (locally or globally) → **do not write**. Git would ignore `.git/hooks`. Print the chain line for the user's own hook, exit 1.
- The target exists **without** the marker (a foreign hook) → **do not overwrite**. Print the chain line, exit 1.
- Otherwise write the shim (LF, `chmod +x`, temp file + `mv`). Re-running it is idempotent: a shim with the marker is rewritten in place. Exit 0.
- The chain line: `refs=$(cat); printf '%s\n' "$refs" | bash "$(git rev-parse --show-toplevel)/hooks/git-pre-push.sh" "$@" || exit 1`. It saves stdin first, because an existing hook may read stdin too.

**Setup scripts.** `setup-project.sh` runs `bash "$TARGET_DIR/hooks/git-pre-push.sh" --install "$TARGET_DIR"` after copying hooks. `setup-project.ps1` runs it through **git's own shell**: `git -C <target> -c alias.cct-pre-push='!bash hooks/git-pre-push.sh --install .' cct-pre-push`. Git runs `!` aliases with its bundled `sh` from the top-level, so the bash it finds is Git for Windows' bash and never WSL's `System32\bash.exe`, which `Get-Command bash` can return. Neither script ever **fails** the bootstrap on a non-zero install. Each prints a WARN and a *Next step* line in the summary, because the common flow (setup into a fresh directory, then `git init`) cannot install at setup time.

**The sync.** The server writes tracked files only, so it delivers `hooks/git-pre-push.sh` but cannot write `.git/hooks`. Existing consumers run the installer once per clone (CHANGELOG *Downstream migration*). Deliberately **not** done: a sync-template skill step or a `template_verify` line that installs or checks the shim (open question Q1).

**This toolkit repo.** Its root `hooks/` carries the file, so a maintainer runs `bash hooks/git-pre-push.sh --install` once per clone. That is a migration step, not tracked state.

**Mirror.** None. `git-pre-push.sh` joins `HOOKS_NO_MIRROR` with this reason: it is a git hook installed per clone, not a Claude hook registered in `settings.json`, so a bare `~/.claude` install has no use for it.

### P4. Windows (Git Bash and PowerShell)

Git for Windows runs every hook with its bundled `sh`, whether the push was typed in Git Bash, PowerShell, cmd, VS Code or a GUI client. The shim's `#!/bin/sh` and `exec bash` run in that environment. The `.git/hooks` file is untracked, so `core.autocrlf` never touches it. The installer writes it with `printf` (LF), and a fixture asserts there is no CR. The tracked file is LF by `.gitattributes` (`* text=auto eol=lf`). Windows ignores the executable bit, and the shim does not depend on it for the tracked file (`exec bash <file>`). Proof is a live controller check (plan, last task): a push to `main` from PowerShell, from Git Bash and from a script is refused, and a feature push goes through.

### P5. `--no-verify` and the server-side layer

`git push --no-verify` skips `pre-push`. That is git's design and it is **documented as the deliberate escape**, the one way to push a protected branch on purpose (for example a release done by hand). The hook prints it in every refusal. The real backstop is server-side. Docs recommend a **GitHub ruleset on the default branch with "Require a pull request before merging"** (and "Block force pushes"). This toolkit repo has one since v4.3.1. A client-side hook can always be skipped, and a ruleset cannot.

### P6. Tests

- **Fixture block V1** (`scripts/test-hooks.sh`). (a) The hook called directly as git calls it (cwd = top-level, argv `origin <url>`, crafted stdin lines): update, delete, tag, look-alike names, two-line push, `develop` list, `none`, no field, no file, placeholder, unreadable file, missing lib, missing `json.sh`. (b) End-to-end with **real pushes to a bare remote** after `--install`: push `main` refused with the remote unchanged; `HEAD:main` from a feature branch, `:main` and `--delete main` refused; a feature push and a tag push land; a mixed push lands nothing; a push from `bash p.sh` refused (the gap P1 names); a second remote's `main` refused; a push from a linked worktree refused; a branch without the tracked file refused by the shim; `--no-verify` lands (the documented escape, asserted so it stays documented). (c) The installer: shim written with the marker, executable, LF only; idempotent; a foreign hook untouched; `core.hooksPath` set → not written; not a repository → exit 1. Every git call in V1 runs with `GIT_CONFIG_GLOBAL=<empty file>` and `GIT_CONFIG_NOSYSTEM=1`, so a developer's global `core.hooksPath` cannot change the result.
- **Bootstrap fixtures** (`scripts/test-setup-project.sh`): setup into a `git init` target installs the shim; setup into a non-repository exits 0 with the WARN and the *Next step* line; the `.ps1` run does the same when `pwsh` is present (same `pwsh`/`powershell` loop as the existing rows).
- **Consistency check (next free number, see the plan):** `hooks/git-pre-push.sh` calls `gc_protected_branches` and does not grep `Protected branches` itself; both setup scripts call `git-pre-push.sh --install`. A control check proves the check fires.

### Part P — deliberately left out

`core.hooksPath`; a hook for `pre-commit` or `pre-merge-commit` (the Claude-side gates own those, and a native commit gate would run the Test twice); branch **patterns** (`release/*`) — the set stays exact names, as in `no-push-main.sh`; per-remote protection (every remote is protected, a personal fork's `main` included); automatic install by the sync (Q1); a `--uninstall` (delete the shim by hand); honouring `git-guard-off`.

## Part F — faster gate hooks for git-shaped commands

**Evidence.** Measured on the Windows target after v4.3.1: `git status --short` still costs about 1.2-1.7 s per Bash call. `pre-commit-test.sh`'s v4.3.1 fast path costs 776 ms on `ls -la` (10-run median, idle). Reading the code at `5d3d789` shows two causes.

### F1. Narrow the fast-path triggers to words (`hooks/pre-commit-test.sh`)

**Today** (`hooks/pre-commit-test.sh`, S6 block): after quotes and backslashes are removed and case is ignored, the walk runs when the text contains `*commit*|*merge*|*pull*|*push*|*sh*|*source*` or `.` followed by whitespace or end. `*sh*` matches `--short`, `publish`, `stylish`, `bash`, `show`, `push`, and **every `x.sh` filename**. `*.[[:space:]]*` matches every sentence in prose (`echo "done. ok"`, `-m "Fix x. Add y"`).

**Design.** Change only the two triggers that misfire. The long stems stay substrings:
- `sh` → a **word**: the text with every character outside `[[:alnum:]._]` turned into a space contains ` sh `. Treating `.` and `_` as word characters means `x.sh`, `--short` and `sh_x` do not fire. Treating `/` as a separator means `/bin/sh` and `/usr/bin/sh` do fire.
- `.` → a **lone token**: the text with whitespace and ``; & | ( ) { } ! ` < >`` turned into spaces contains ` . ` (shipped separator set `` [[:space:];&|(){}!`<>] ``: backtick, `<` and `>` were added after review). Prose dots, `./x` and `..` do not fire. `. x`, `ls;. x` and `ls && . x` do fire. A token **ending in `/.`** fires too (the `"/. "` arm: `x/. c.sh`, where the walk takes the basename as a dot-source).
- **Glob characters** `[ ? *` always walk: the walk expands globs (`set -- $seg` in `gc_script_body`), so `/bin/[s]h c.sh` runs a script the word match cannot see.
- **`sh.exe`** (v4.3.2 Task 6b) is a second runner word, any case. A second word test on the text with quotes removed but backslashes kept makes `C:\Git\bin\sh.exe` fire (backslash removal would glue it into `Gitbinsh.exe`).
- `bash`, `pwsh` and `powershell` become **explicit substrings**. Before, they were covered implicitly by `*sh*`. A substring keeps `C:\...\pwsh.exe` covered after backslash removal (`...7pwsh.exe`).
- `commit`, `merge`, `pull`, `push` and `source` stay **substrings** on purpose. They rarely appear by accident, and a substring is trivially a superset. Word-matching them would need its own proof for `git.exe`, glued backslash paths and quoting, which is risk with no measured payoff.

**Why it stays fail-closed (the superset argument; the plan pins it with a differential test).** The walk can refuse only through: a gated verb (`commit`, `merge`, `pull`, `push`, `gh pr merge`; substrings unchanged); a script body that `gc_script_body` reads (a token whose basename after `/` or `\` is `bash`, `bash.exe`, `sh` or `sh.exe`, any case (Task 6b; it was exactly `bash` or `sh` after `/` only), or `.`/`source` at segment position 1, where segments split on `&& || ; |` and newline and tokens split on IFS whitespace); or a PowerShell body (`gc_seg_is_ps`: basename after `/` or `\` in `powershell[.exe]`/`pwsh[.exe]`).
- (6b: a token ending in `\sh`, the form `sh.exe` and any-case spellings are covered by the second word test `pct_w2`, which keeps backslashes, plus `nocasematch`.) A token that equals `sh` or ends in `/sh` sits between start, whitespace, a segment separator or `/` on the left, and whitespace or a separator on the right. Every one of those characters is outside `[[:alnum:]._]`, so ` sh ` appears.
- A position-1 `.` sits between start, whitespace or a separator on the left, and IFS whitespace or the separator after it on the right. All of those are mapped to spaces, so ` . ` appears.
- `bash`, `source`, `pwsh` and `powershell` appear as substrings whenever the walk's tokens contain them, because quote and backslash removal only deletes characters.

**Kept unchanged.** Zero forks: parameter expansion and `case`, with the bracket patterns held in variables because a literal `}` inside `${…}` would end the expansion. Every existing refusal row (S6, S6b, G1–G6, all earlier blocks) stays green.

### F2. A cheaper no-op record (`pct_note no-commit-segment`)

**Correction to the brief.** The no-op path does **not** run `add -u` into a temp index or `write-tree`. `pct_capture_tree` runs only after a commit segment is found (`hooks/pre-commit-test.sh` at the Gate fallback and before the Test). The no-op record's forks, read from the code, are:
- `date +%s` at hook start, `date +%s` and `date -u` in the record;
- `git rev-parse --show-toplevel`, then `gc_gate_dir`, which runs `rev-parse --show-toplevel` and `rev-parse --git-common-dir` again;
- `mkdir -p`, the `printf | wc -c | tr -d` pipeline, `mv`, and `pct_prune`'s `find`.

That is 9 to 11 programs (3 of them git) plus their command-substitution subshells. On Cygwin each costs tens of milliseconds.

**Design.** A dedicated `pct_note_noop` that writes the **same record** (same file name, same keys, same meaning):
- **one** `git rev-parse --path-format=absolute --show-toplevel --git-common-dir` (gate dir = second line + `/gate`). It falls back to `gc_gate_dir` when that call fails (git < 2.31, or not a repository, which then writes nothing as today);
- `mkdir` only when the directory is missing;
- time from the bash builtin `printf '%(…)T'` (bash ≥ 4.2; `TZ=UTC0` for `ts`), falling back to `date` on older bash (macOS `/bin/bash` 3.2). The hook-start `PCT_HOOK_T0` uses the same helper;
- `cmd_len` as `${#GC_CMD}` under `LC_ALL=C` (bytes, the v4.1.2 contract) instead of `wc -c`;
- **no `pct_prune`** on this path. The no-op file name is always `last-precommit-noop.unknown.json`, because `PCT_TREE` is set only on commit paths, so it never accumulates. The commit paths still prune, and that prune covers no-op files left by older versions.
- The temp file + `mv` stays (atomic replace for a reader).

Result on the fast path: parser 1 + git 1 + mv 1 (+ mkdir once). Today's ~12 programs become 3.

### F3. Expected savings and how they are measured

| Arm (pre-commit-test.sh) | v4.3.1 Windows (measured) | v4.3.2 Windows (expected) | Linux (relative) |
|---|---|---|---|
| `ls -la` (fast path) | 776 ms | ~350-500 ms (F2) | ~90 → ~50-60 ms |
| `git status --short` | ~1.2-1.7 s per call (walk) | same as the fast path (F1 + F2): ~0.8-1.2 s saved | walk → fast path |
| `echo "done. ok"` (prose) | walk | fast path (F1) | walk → fast path |

The expected figures are **estimates** (Cygwin fork plus exec ≈ 30-60 ms per coreutil, ≈ 60-100 ms per `git.exe`), not acceptance criteria. **Acceptance is structural:** the V2 spawn-count pins (fast path: exactly 1 git, 0 `date`/`wc`/`tr`/`find`) and the differential verdict test. **Measurement:** `scripts/time-hook.sh` gains two arms (`git status --short`, `echo "done. ok"`). It runs with `GATE=` set to the v4.3.1 baseline (`git archive 5d3d789 hooks`) and then to the new hook, with the existing control arm, `RUNS=10`. The **Windows target numbers come from the local controller** (idle Git Bash, 10-run medians, the v4.3.1 protocol). Linux medians go in the CHANGELOG as a relative indicator only. The same run also times `no-push-main.sh` and `gate-before-merge.sh` on `git status --short`, so the per-call total is reported honestly (see Known limits).

### Part F — deliberately left out

Word-matching the verb stems (F1); a pure-bash `.git` discovery to drop the last git fork (it would re-implement `gitdir:` files, worktrees and `commondir`); dropping the no-op record (it is the "did the hook run?" diagnostic the sync-template skill reads); a verb pre-filter for `no-push-main.sh` and `gate-before-merge.sh` (they still walk any command with a `git` word; measured and reported, candidate for later); any change to the parser call (`json_payload`, one call since v4.3.1).

## Known limits (to carry into the CHANGELOG)

- **The pre-push hook is per clone.** A fresh clone, a new machine, a cloud session, or a setup run into a directory that is not yet a repository has no shim until `bash hooks/git-pre-push.sh --install` runs. `no-push-main.sh` still covers Claude-typed pushes there.
- **`--no-verify` skips it** by git's design. That is the documented escape; the server-side ruleset is the backstop.
- **`core.hooksPath` or an existing foreign `pre-push`:** not installed automatically. The installer prints the chain line and exits 1.
- **A checkout without `hooks/git-pre-push.sh`** (a branch older than v4.3.2) refuses every push from that worktree until the trunk is merged in, or until a deliberate `--no-verify`. This is fail-closed by choice.
- **Every remote is protected**, a personal fork's `main` included. Names are exact; patterns are not supported. A refused ref aborts the whole push.
- **The shim runs the hook from the checkout being pushed.** A branch that edits `hooks/git-pre-push.sh` changes its own guard. This is the same trust as every tracked hook, and the server-side ruleset is the answer.
- **F1:** the stems `commit`, `merge`, `pull`, `push`, `source`, `bash`, `pwsh` and `powershell` still trigger the walk as substrings (for example `pushd`, `git log --grep=commit`). That is slower, never less safe.
- **F1:** `no-push-main.sh` and `gate-before-merge.sh` still walk every command with a `git` word, so a `git status --short` call is not as cheap as `ls -la` across all three gates. The numbers are in the CHANGELOG.
- **F2:** git < 2.31 and bash < 4.2 keep the old forks (`gc_gate_dir`, `date`); outside a repository the record is still not written.
- **Quoting and spelling the gates do not model:** ANSI-C quoting (`git $'\x63ommit'`) is not decoded; uppercase and NBSP verbs are not matched (git itself rejects them); `git -\C commit -m x` reads as `-C commit` (as the shell and git do), and git itself refuses it (exit 129, unknown option `-m`).
- **Windows figures** in F3 are estimates until the controller's run replaces them.

## Verification plan

RED-then-GREEN per task through the block harness (V1, V2). The V2 differential test runs the v4.3.1 hook and the new hook on the same 40+ commands and requires identical exit codes.
