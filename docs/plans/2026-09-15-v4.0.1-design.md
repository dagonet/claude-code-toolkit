# v4.0.1 — consumer-rollout fixes (design spec)

**Status:** spec, 2026-09-15. Authority for the v4.0.1 task plan.
**Source of the backlog:** the v4.0.0 consumer rollout (four consumers synced 2026-09-14/15; every item below was measured in a live sync or in the verification round that followed). Ledger: `.superpowers/sdd/2026-09-12-v4.0-server-move-implementation/progress.md`, rulings R32–R33 and "Manifest verification round".
**Version:** toolkit `4.0.1`, server `4.0.1`. `manifest_version` stays **3** (every manifest change here is additive; older servers preserve unknown keys). `MIN_SERVER_FOR_V3` stays `0.3.2`; the sync skill's floor is unchanged — the first legitimate floor raise is v4.1 (option B), not this release.

## Goal

Make the v4.0.0 sync path clean for the installed base: every defect a consumer had to work around by hand during the rollout is fixed at its source, and a consistency check exists that would have caught every END-STATE defect among them (process defects that leave no trace are closed by their own items, not by the check). No behaviour change for a consumer that does not sync.

## Non-goals

- Option B (template CLAUDE.md byte-identical + project-owned instruction file, PreToolUse deny, `@import` gate) — v4.1, separate spec.
- Merging mcp-dev-servers into this repo — rejected 2026-09-15 (name-only coupling, variant/machine-specific deps, separate release train). Items 23–24 are the alternative.
- Migrating MM-Agent — after this release, on the user's trigger.

## Global constraints (bind every task)

1. Every PR and every fix is reviewed by an outside session at the exact sha, in a detached worktree, never a branch checkout in the shared checkout (constraint 13). Task PRs stack onto integration branch `v4/0.1`, true merges (`--merge`), no rebases (R11).
2. **All toolkit commits happen in worktrees until item 11 lands** — the live checkout's per-commit Test is red while a session's MCP server holds `server/.venv`.
3. Gate: `bash scripts/verify-template-consistency.sh && bash scripts/test-hooks.sh && bash scripts/test-server.sh`, run as `bash hooks/run-gate.sh > <log> 2>&1` — never piped (R14). Implementers do not run the full gate (R3); the controller runs it at merge time.
4. Every file LF; no counts in `CLAUDE.md` (R15); byte-identical variant files edited in `templates/general/` then copied.
5. Every fix ships with the test that fails without it. A check or fixture is two-sided: the failing case is demonstrated, not assumed.
6. Expectations are **derived**, never hard-coded: declared keys from the consumer's own variant, expected commit from the template repo HEAD, file classes from the manifest, exported tool names from the installed servers.
7. Namespace rule (R28): any MSYS path handed to a Windows executable is suspect unless the token is bare — `cd` and go relative, or `cygpath -w` first; values crossing MSYS↔Win32 are checked in the consumer's namespace.
8. Server package name for metadata probes is `claude-code-toolkit-template-sync`; the metadata assertion in `test_version.py` names the remedy (`bash server/install.sh`).
9. **A check's passing output must be distinguishable from its null case.** A SKIP is reported in-band with a count and a reason; `ok`/green never means "nothing ran"; a list that is non-empty on every healthy consumer is not a FAIL line anywhere. (The family behind items 2, 18, 22, 23 and check 46 — open-brain, yutraffic.)
10. **Capabilities, not versions.** `test_template_sync_capabilities.py` pins the capability set EXACTLY. Every new server surface the skill branches on gets a capability name and a witness: `superseded_keys` (item 8), `new_template_files_detail` (3), `missing_declared_keys` (2), `optional_absent_detail` (18), `template_verify` (22), `region_bytes_raw` (6); EXPECTED is updated in the same PR. The skill feature-detects by presence (`capabilities` list, `.get(...)` on the field) and never by `server_version`.
11. Every claim in this spec that names a line number or a measured value was re-measured against v4.0.0 on 2026-09-15 by the session that reported it; an implementer who finds a stated defect already green stops and reports it rather than writing a test that was never red.

**10 — commit matcher false positive on a bare `commit` VALUE.** Defect (re-measured 2026-09-15 by yutraffic and open-brain against the v4.0.0 function, not recalled): the `^{commit}` peel syntax is ALREADY rejected at v4.0.0 — `gc_matches_subcommand` (`hooks/lib/git-cmd.sh:1061`) compares tokens by exact equality and `v4.0.0^{commit}` is not `commit`. The LIVE false positive is `commit` appearing as an option's VALUE after the real subcommand: `git -C X log --grep commit` → MATCH → `pre-commit-test.sh` runs the target repo's Test on a read-only command. Implemented as a verb list `GC_FIRST_TOKEN_VERBS="commit"` consulted by the awk walk. **The walk becomes the sole authority: BOTH line 1 (the `GC_GIT_PRE` regex fast path) and line 3 (the loose `-C` pre-filter) are deleted** — for `merge`/`push` the walk already subsumes the fast path (a bare operand at the first position is "anywhere after the globals"), and two code paths that can disagree is how this function got here (reviewer session). Three requirements on the walk, from the reviewer's verbatim run of the first draft (F1–F3): (a) the state machine RESTARTS at every `git` token — a segment `git add -A && git commit -m x` must still match (`pre-commit-test.sh` splits on `&&`/`;` via `gc_segments` before the matcher, `:199-218`, but nothing pins that and other callers may not); (b) the git-token test handles backslash paths correctly — `tok ~ /\\git$/` degrades to `git$` on this awk ("\g is not a known regexp operator"), so `notgit` and `"git` opened the walk; and the string literal `"\\git"` inside the single-quoted program lexes to the 3-character `git`, so a substr comparison against it is dead code (F11) — the backslash is handed in as `-v bs='\'` and the test is `substr(tok, length(tok)-3, 4) == bs "git"`; (c) surrounding quotes/parens are stripped from a token before BOTH the git test and the verb comparison, so `bash -c "git commit -m x"`, `sh -lc '…'` and `(git commit -m x)` — the quoted-payload case only line 1 caught — stay matched (documented as handled at `pre-commit-test.sh:82-85`); consequence, decided not discovered (F12): a QUOTED operand `git log --grep "merge"` now refuses under the merge/push posture as the unquoted form already did — a deliberate fail-closed widening, pinned; (d) the matcher writes nothing to stderr (today every call emits one awk warning line), pinned (F13). Pinned rows in `test-hooks.sh`: the compound shapes (`git add -A && git commit`, `git add . ; git commit`, `cd X && git commit`, `git -C X log --grep commit && git -C X commit`), `notgit commit` (no run), `C:\bin\git commit` (run), the three quoted/paren wrappers (run), the merge posture (`show-branch merge` refuses; quoted `--grep "merge"` refuses, deliberate), and the empty-stderr row, so none of it can move by accident.
