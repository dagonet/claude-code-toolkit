## Part G — gate and hook fixes

### G1. Long Test must not let a commit through (fail-open, seen live)

**Evidence.** MM-Agent commits `5e270dd` and `08b03aa` (2026-09-30) landed with `rc=1` Test records (elapsed 641 s and 1981 s). The PreToolUse hook was killed at the harness's 600 s hook timeout, the tool call proceeded, the agent reported "pre-commit hook passed", and the Test's `dotnet test` children ran on as orphans over the same `bin/`.

**Mechanism today.** `hooks/pre-commit-test.sh` runs the Test synchronously with no time budget; the template registration has no `timeout` field, so the harness default (600 s) applies; a killed hook is a non-blocking error.

**Design.**
1. New optional PROJECT_CONTEXT key `**Test timeout**: <seconds>` (commented example only, like the other v4.3.0 keys; check 63 extends to it). Default **540 s**. Accepted range 30–3300; anything else → WARN and the default.
2. `pre-commit-test.sh` runs the Test as a child it owns, waits up to the budget, and on expiry:
   - kills the whole process tree. On Windows/Git Bash that means the native tree (`taskkill //F //T //PID <winpid>` via `/proc/<pid>/winpid`), elsewhere `kill -- -<pgid>`; verifies nothing of the tree survives;
   - writes the pass record with `"rc":"timeout"` (never a passing record);
   - exits **2** with: "Test exceeded its N s budget -- commit refused. Shorten the per-commit Test (fast subset) and move the full suite to **Gate** / **Gate extra**, or raise **Test timeout** (max 3300)."
3. Every registration of `pre-commit-test.sh` (6 templates, root settings, user-level reference) gets an explicit `"timeout"` field = budget ceiling + 60 s (3360), so the hook's own budget always fires first and the harness never kills it mid-Test. If the project raises **Test timeout** above 540, the harness limit already covers it.
4. Fixtures: a fake Test that sleeps past a tiny budget (via an env override for tests only) → exit 2, record `rc:"timeout"`, no surviving child; a Test that finishes inside the budget → unchanged behaviour; malformed key → WARN + default.

**Known limit to state:** a project that removes the `timeout` field from its registration falls back to the harness default (600 s); with **Test timeout** ≤ 540 the hook still fires first.

### G2. `git.exe` / quoted `git` / `command git` not recognised (fail-open, pre-existing since v4.1.2)

**Evidence.** v4.3.0 scan-fix review (2026-10-01): `git.exe push`, `"git" push` slip every gate. **Mechanism:** `gc_matches_subcommand` (`hooks/lib/git-cmd.sh` ~:1491-1530) `is_git()` accepts only `git`, `*/git`, `*\git`.
**Design.** `is_git()` also accepts, case-insensitively: `git.exe`, `*/git.exe`, `*\git.exe`, and the same after stripping one pair of surrounding `"…"` / `'…'`; a leading `command`, `env [VAR=val…]`, `exec`, `nohup` or `time` word is skipped before the test. Fixtures for each spelling against no-push-main, pre-commit-test and gate-before-merge. Only adds matches (cannot widen what passes).

### G3. A later `cd` hides a scanned script's verbs (fail-open, pre-existing since v4.1.2)

**Evidence.** v4.3.0 scan-fix-3 review: `bash c.sh; cd sub` hides `c.sh`'s verbs in all three gates. **Mechanism (reviewer's reading; the plan's first step confirms it with a failing fixture before any fix):** `gc_augmented_cmd` appends script bodies after walking the whole command (`hooks/lib/git-cmd.sh` ~:642), and the hooks then judge the augmented text against the cwd the last `cd` left, so a relative script path resolves in the wrong directory.
**Design.** Resolve each script path (shell and `.ps1`) against the cwd in effect at the segment that names it (track `cd` while walking segments). If a path cannot be resolved with certainty (e.g. `cd "$VAR"`), scan the candidate under EVERY cwd seen so far (adds text only). Fixtures: `bash c.sh; cd sub`, `cd sub; bash ../c.sh`, `cd "$X"; bash c.sh`.

### G4. Parallel PRs from one parent overwrite each other's gate artifact

**Evidence.** yutraffic (2026-09-30 sync report): two PRs branched from the same main each ran the gate at commit time; the second overwrote `last-pass.<parent>.json`, so PR 1's tree had no artifact (tier-2 tree scan cannot find a file that no longer exists). **Mechanism:** `run-gate.sh:405,422` names the artifact `last-pass.$HEAD_SHA.json` (HEAD at run time). When the gate runs before the commit is created (the consumer's flow), HEAD is the PARENT, so two branches from one parent write the same file name. The plan's first step reproduces this with a two-branch fixture before any fix.
**Design.** When the gated tree differs from `HEAD^{tree}` (the commit-time case), name the artifact `last-pass.tree-<tree>.json`; otherwise keep `last-pass.<sha>.json`. `gate-before-merge.sh` tier 2 already matches by tree, so it finds both shapes; add the `tree-` filename as an explicit tier-1b lookup (exact tree) before the mtime scan. Pruning (`GC_GATE_PRUNE_S`) covers both shapes. Fixtures: two branches from one parent, gate each at commit time, both merges pass; the stale-tree and wrong-tree cases still refuse.

## Part S — sync-tool fixes (server + skill)

### S1. Opt-in notes vanish at finalize (3 of 3 consumers reported)

**Evidence.** panoscribe, penumbra, open-brain: `template_compute_status` reports `template_notes_changed` on PROJECT_CONTEXT.md before finalize; after finalize `template_verify`'s `once_notes_changed` reads "no once-class file has changed template notes" because the base moved. Verify is the skill's authoritative report, so the opt-in keys are never surfaced there.
**Design.** `template_finalize_sync` records, per once-class file whose template notes changed in this sync, an entry in the manifest `pending_once_notes: [{file, from_commit, to_commit}]` and returns it in its response. `template_verify` reports each pending entry as INFO ("new optional template notes in <file> since <from>: review and adopt by hand"). The next finalize replaces the list (entries for files whose notes did not change again are dropped). Skill step 8 reports the list. Server tests for record/report/replace.

### S2. `template_verify` silently ignores unknown parameters

**Evidence.** yutraffic: `phase="pre_commit"` (wrong name) ran `mode=post_commit` silently and FAILed `tree_clean`. **Design.** All MCP tools in the server reject unknown keyword arguments with a clear error naming the accepted parameters (one shared decorator/check), and `template_verify` echoes the effective `mode` in its result. Server tests.

### S3. `files_added: 0` while new hooks were created

**Evidence.** penumbra, open-brain, yutraffic. **Mechanism:** `mcp.py:1697-1730` counts `added` only from `new_files`; files created from template via `applied_files` count as updated. **Design.** Add `files_created` (applied entries with action `created_from_template`) and make `files_updated` exclude them; keep `files_added` for `new_files` registrations, documented as such. Server tests.

### S4. Skill (`user-level-reference/skills/sync-template/SKILL.md`) wording
