**Status:** approved design, 2026-09-03. Challenge round 2026-09-05: five consumer
verdicts (MM-Agent PASS, penumbra GREEN with four REDs, yutraffic APPROVE with conditions,
open-brain SHIP with two blockers, panoscribe ACCEPT with two blockers) and six server
batches folded in; ledger in `2026-09-05-v3.1-scope-fold-in.md` §7. Scope fold-in and
challenge-round questions: `2026-09-05-v3.1-scope-fold-in.md`. Server review and confirmed contract:
`mcp-dev-servers/docs/plans/2026-09-05-v3.1-ownership-server-review.md`; server version
0.3.0. **Two implementation plans follow**, one per
repo, executed in the order §9 fixes: the server's first (backward compatible), then this
repo's. Neither plan is executable until both exist, because the manifest schema and the
status vocabulary in §6–§7 are the interface between them.
**Prerequisite:** `docs/plans/2026-09-03-v3.1-template-diet.md` — `CLAUDE.md` must be
≤ 6 KB before it becomes template-owned.
**Companion, not prerequisite:** `docs/plans/2026-09-03-v3.1-gate-checked-branches-spec.md`.
**Repos:** this one (templates, `setup-project`, consistency checks, and the
`sync-template` skill body at `user-level-reference/skills/sync-template/`) and
`mcp-dev-servers` (the template-sync MCP server and the skill's version contract).

## 1. Problem

Five consumer projects, one release cycle, measured:

- Sync **conflicts** every time a consumer has edited `CLAUDE.md` or `CLAUDE.local.md`
  outside the PROJECT-CUSTOM region. The region protects one block; everything else goes
  through a three-way merge that has dropped lines silently before.
- Apparent **contradictions** between consumers (Test-vs-Gate precedence, session-branch
  gating, which optional plugins apply, protected-branch names) are almost all behaviours
  the template *defaults* where it should *declare*. Once declared per project, they stop
  contradicting.
- Two consumers hold on old versions deliberately because the cost of a sync is a
  hand-merge.

Root cause of the first: **shared ownership of prose files.** The template and the project
both write `CLAUDE.md`. No merge algorithm fixes that; only ownership does.

## 2. Evidence base

- Anthropic: `CLAUDE.md` is "context, not enforced configuration"; conflicting files → "may
  pick one arbitrarily"; `.claude/rules/*.md` without `paths:` loads at launch at CLAUDE.md
  priority; the multi-repo recommendation is a plugin, not copied files.
  (code.claude.com/docs/en/memory, /large-codebases)
- Copier: template-owned / `_skip_if_exists` / `_exclude`, an answers file, per-version
  migrations, and a pre-commit hook forbidding conflict markers. Its issue #33 ("project
  docs replaced by template docs") is this problem verbatim; the fix was "generate in a
  separate path instead of replacing canonical files."
- cruft: `cruft check` in CI = our `verify-user-level-drift.sh`.
- Template-sync actions: a project-declared ignore list.

## 3. Decisions (user-approved)

- **(a)** `CLAUDE.md` becomes fully template-owned. **`CLAUDE.local.md` stops being
  template-shipped** — by Anthropic's definition it is personal and gitignored.
- **(1)** Ownership is expressed in the manifest and enforced by the sync server — a
  coordinated release, not a toolkit-only convention.
- **Automatic migration** of existing consumers on their first v3.1 sync.
- Project prose lives in `.claude/rules/project.md` (no `paths:` → loads at launch). No
  `@import` line needed; no new mechanism.

## 4. The three classes

| class | sync behaviour | files |
|---|---|---|
| `template` | overwritten every sync; a local edit is a **reported loss** (diff shown, diff saved to the backup dir), never a merge | `CLAUDE.md`, `AGENT_TEAM.md`, `.claude/settings.json`, `.claude/agents/*.md`, `.claude/rules/*.md` except `project.md`, `.gitattributes`, `hooks/**` |
| `once` | created if absent, **never touched again** | `.claude/rules/project.md`, `PROJECT_CONTEXT.md`, `PROJECT_STATE.md`, `gitignore` (copied as `.gitignore`), `VERIFICATION_PLAYBOOK.md` (template-shipped, project-appended: nine rules at penumbra, eleven at yutraffic — the third case §5a's dichotomy did not close; template rule updates arrive via CHANGELOG, never overwrite), `.prettierrc`, `rustfmt.toml` (rust-tauri only; formatter knobs a project tunes; paired with a content-drift note in the audit) |
| `project` | not in the manifest; the server never reads or writes it; it LISTS such files only as `orphans` when they sit under a template-class pattern (informational, silenceable per path with an explicit `project` rule placed before the broad one) (MM-Agent F7, server b1) | `CLAUDE.local.md`, anything the consumer adds |

`.gitattributes` (all six variants, byte-identical, single purpose — a consumer edit is a
bug; under `once` a future template fix never reaches anyone) is `template`, not a style
file (penumbra, yutraffic).

The class is a fact about the file, declared once, not a heuristic about its diff. A file
changing class between versions is a migration (§7), never an inference. Classification
applies to TEMPLATE-tree paths and manifest entries; a consumer-tree file with no manifest
entry is `project` regardless of any pattern it matches — never diffed, hashed or swept —
and appears only in `orphans`. First-match-wins picks the rule for a template path; it
never classifies a consumer file. (penumbra F13, server b2-6)

## 5. The five files

**`CLAUDE.md`** — `template`, ≤ 6 KB, facts only. PROJECT-CUSTOM markers **removed**. One
line near the top: *Project-specific instructions: `.claude/rules/project.md` (yours; sync
never overwrites it).* One line containing the literal `context-mode` stays in the
template-owned file: the context-mode MCP server's `writeRoutingInstructions` appends its
routing block to the project `CLAUDE.md` on every startup unless the file already
`includes("context-mode")` (measured from `server.bundle.mjs`, 2026-09-05; two consumers
hit it). Without it every context-mode consumer holds a permanent unauthored
`LOCAL_EDITED`. The line is in the diet plan's literal table and a consistency check
asserts it in all six variants; the check also greps the plugin bundle for the predicate
so a plugin change turns red rather than silent. Quick Start carries NO placeholder-bearing
commands (setup fills `{{BUILD_COMMAND}}` etc. by hand and nothing records the value, so a
template-owned CLAUDE.md would re-inject them — open-brain) and ONE placeholder-free line,
the gate `bash hooks/run-gate.sh` (the one command the merge gate requires and the template
omitted — panoscribe); build/test/format/lint live in PROJECT_CONTEXT.md.

**`.claude/rules/project.md`** — `once`. Seeded by `setup-project` with a header and
nothing else; seeded by migration with the consumer's former region content (§7). The only
file a consumer writes prose in. No `paths:` frontmatter.

**`CLAUDE.local.md`** — **not shipped.** Its content is redistributed: MCP-usage rules →
`template`-owned `.claude/rules/mcp.md`; SQLite rules → path-scoped
`.claude/rules/sqlite.md` (`paths: ["**/*.db", "**/*.sqlite", "**/*.sql"]`); the
open-brain section is dropped (the open-brain MCP server injects its own instructions).
`setup-project` stops creating it. An existing consumer copy is `project`. Four of five
consumers hold a copy byte-identical to the template at their held version; left live it
duplicates the redistributed `rules/mcp.md` and `rules/sqlite.md` and stays unbudgeted. The
migration therefore reports `redundant_project_file` for a copy identical to the
held-version template (compared before the entry is dropped) and the skill OFFERS
deletion — never deletes unasked. A diverged copy stays and the report names which of its
sections now duplicate template-owned rules. (MM-Agent, penumbra, yutraffic, open-brain,
panoscribe)

**`PROJECT_CONTEXT.md`** — `once`, with a **key audit** each sync. The audited rule carries
`required_keys` (hook-read: `**Protected branches**:`, `**Gate**:`, `**Test**:`),
`deprecated_keys` (map: `Gate Command`→`Gate`, `Test Command`→`Test`), `aliases`, and
`placeholder_map` (`Build Command`↔`BUILD_COMMAND`, Test/Format/Lint likewise); every
template key not in `required_keys` is optional. The report lists: `missing_required`,
`optional_absent` ("default applies"), `placeholder_keys` (`{{…}}` values),
`deprecated_keys`; per required key `value`, `template_value`, `template_value_at_sync`,
`template_default_changed`, `consumer_holds_old_default`; a key is present when the
consumer holds it exactly, a qualified form `Key (…)`, or a declared alias (`matched_as`);
project-only keys are ignored; `template_notes_changed` reports non-key hunks of the
template at the held base vs current with the hunk text; `placeholder_key_divergence`
reports a key whose value disagrees with its mapped placeholder (panoscribe:
`BUILD_COMMAND` held the test command). It **never inserts**; base unavailable → flags
omitted + `audit_base_unavailable`. Names are compared without the `**…**:` decoration,
whitespace-normalised. A reported gap every sync beats a silently inserted default nobody
reviewed. (MM-Agent F1/F2, yutraffic C2, panoscribe F27, server b1/b3)

**`AGENT_TEAM.md`** — `template`, unchanged class; diet applies.

**`.claude/settings.json`** — `template`, and it stays `template`. The post-edit `dotnet
build` consumer is InvestmentAdvisor (`G:/git/InvestmentAdvisor/.claude/settings.json`) —
a consumer on a pre-v2.0 config, not one of the five challenge-round sessions — which
holds it as PROJECT_CUSTOM to carry the hook the dotnet variant used to ship and lost when
v2.0 made all six `settings.json` byte-identical. **That is a variant gap, not a
per-project value**, and the restoration is justified on its own; it is fixed in the
template (§5a), after which the consumer's customisation is redundant and `template` class
holds.

MM-Agent's measured delta: the SubagentStop matcher extended with project agent names
(`^mm-runner$|^finisher$`) is a per-project value whose key is the agent list itself;
because `settings.json` is `template` and there is no merge class, the v3.1 hook derives
the SubagentStop matcher from the PROJECT's `.claude/agents/*.md` at runtime
(consumer-only agents included) — a v3.1 REQUIREMENT, MM-Agent verifies. Their six
`Read(.env*)` deny rules are a transitional duplicate the template cannot ship (they broke
auto mode): §5a does NOT gain a third category; the migration note names them as a
pre-sync retirement.

### 5a. The rule this sets, and the fix for the dotnet case

> **Every file a consumer holds as PROJECT_CUSTOM / keep-mine is one of two things: a
> variant gap (fix the template) or a per-project value (make it a declared key). It is
> never a reason to give the file a softer ownership class.** The ownership plan includes
> a pass over all five consumers' keep-mine lists, classifying each.

Fix for the dotnet case, keeping `settings.json` and every hook byte-identical across
variants: a new hook `hooks/post-edit-build.sh` on `PostToolUse` `Edit|Write`, which
reads `**Post-edit build**:` from `PROJECT_CONTEXT.md` and runs it. `none` or an unfilled
placeholder → no-op (placeholder reported by the key audit). `setup-project` fills it per
variant: dotnet/dotnet-maui `dotnet build --no-restore -v q` (the command the old hook
ran), every other variant `none`. Same shape as `**Gate**:` — identical mechanism
everywhere, per-project value, declared in the one file hooks already parse. Fixture in
`test-hooks.sh`; no `hooks/lib/` change.

**PO write surface** (penumbra F12): `hooks/enforce-delegation.sh` reads extra path
prefixes from PROJECT_CONTEXT.md, keyed `**PO write surface**:`; `none` = template
default, `optional_absent` in the key audit; then the hook returns to `template`.

A keep-mine hook script may carry the project's GATE LOGIC itself (open-brain: a six-step
`hooks/run-gate.sh` behind `**Gate**: bash hooks/run-gate.sh`). §5a classifies it right
(per-project value, key `**Gate**:`), but overwriting it leaves a self-referencing gate
that exits 78 — commits survive, merges die silently. The keep-mine pass tests for gate or
test logic living IN a hook script rather than behind the field; the remedy is a
project-owned script outside `hooks/` (panoscribe's root `preflight.sh` is the existence
proof) with the field pointed at it. The two-category rule stands; a transitional
duplicate (a deny rule the hook now covers) is not a third category — it is retired
before the first v3.1 sync, named in §11.

## 6. Manifest v3

```json
{
  "manifest_version": 3,
  "template_version": "3.1.0",
  "template_commit": "<sha of the template repo at sync>",
  "variant": "general",
  "templateRepo": "<path or URL the server resolves>",
  "placeholders": { "PROJECT_NAME": "…" },
  "requires_server": ">=0.3.0",
  "files": {
    "CLAUDE.md":                 { "hash": "sha256:…", "ownership": "template" },
    ".claude/rules/project.md":  { "ownership": "once" }
  }
}
```

- `template_commit` replaces v2's `lastSynced` (the server reads `lastSynced` as an alias).
  `templateRepo` and `placeholders` stay because every template hash is computed AFTER
  placeholder replacement and the server locates the template tree through `templateRepo`.
  `once` entries carry no hash — they are never diffed. Hashes are written with the
  `sha256:` prefix and read in both forms. One hash per `template` entry:
  `TEMPLATE_UPDATED` = current replaced template ≠ hash, `LOCAL_EDITED` = project file ≠
  hash, and when both hold `LOCAL_EDITED` wins (same overwrite, plus the saved diff).
- Every path `setup-project` writes appears here with an `ownership` value. A path absent
  from `files` is `project`.
- The toolkit carries the class table in `templates/ownership.json` at the toolkit repo
  root, variant-independent, shape `{"tracked_paths": ["hooks","scripts","templates",
  "user-level-reference"], "rules":[{"pattern":"hooks/**","ownership":"template"},
  {"pattern":"gitignore","ownership":"once","target":".gitignore"},
  {"pattern":"PROJECT_CONTEXT.md","ownership":"once","audit":"keys","required_keys":[…],
  "deprecated_keys":{…},"aliases":{…},"placeholder_map":{…}}]}`; first match wins;
  PurePosixPath-style globs with `**`; paths relative to the variant directory, root-tracked
  `hooks/**` resolving as today; optional `target` for the rename case (manifest key = project
  path); optional `audit` (§7) with its `required_keys`/`deprecated_keys`/`aliases`/
  `placeholder_map`. The server reads it to classify `new_template_files` and the
  migration; a path with no matching rule is reported as `unclassified_template_files` and
  NOT applied — the server half of the red gate. The toolkit half: a consistency check
  asserts every path `setup-project` writes matches a rule and no variant ships
  `CLAUDE.local.md`; its delete-the-guard row removes a rule and expects red. `X.Y.Z` →
  **0.3.0** (named by the server owner 2026-09-05: manifest shape and status enum both
  change).
- `template_version` derivation (penumbra F16, server b2-3): the nearest reachable tag
  whose tree over `tracked_paths` equals the tree at `template_commit` —
  `git tag --merged <template_commit> --sort=-v:refname`, per tag compare tree ids over
  every tracked path, first all-equal tag wins — never `git describe`; no match or not a
  git checkout → `template_version: null` + warning `untagged_template_tree` at finalize.
  `tracked_paths` missing from `ownership.json` → server falls back to `templates/<variant>`
  plus root-tracked pattern prefixes and warns (server owner counter, accepted: the toolkit
  layout, not server knowledge).
- Guarantee (panoscribe): a consumer file absent from the manifest is `project` even when
  a future template-class pattern (e.g. `*.sh`) would match it; the toolkit consistency
  check asserts every `ownership.json` pattern matches at least one template-tree file and
  none is a bare root `*.ext`; the server test asserts the classification.
- Normalisation (yutraffic F22, server b4): the server strips a leading BOM and folds
  CRLF/lone CR to LF before hashing and classifying (trailing newline is NOT normalised);
  `IDENTICAL` means identical after that; after an overwrite the file IS byte-identical to
  the template, so §8's sentence is true post-apply. A BOM-only or EOL-only difference is
  reported per file as `encoding_drift: []|subset of ["bom","crlf"]`, informational. The
  toolkit cause is fixed in v3.1: `setup-project.ps1` wrote every generated file with
  `Set-Content -Encoding UTF8` (PS 5.1 = BOM) — measured on yutraffic's
  `.prettierrc`/`rustfmt.toml`, UP_TO_DATE at every sync since v2.0.

## 7. Server behaviour

**Statuses** (replace CONFLICT entirely):

| class | status | action |
|---|---|---|
| template | `IDENTICAL` | none |
| template | `TEMPLATE_UPDATED` | overwrite |
| template | `LOCAL_EDITED` | show diff, write diff to the step-2b backup dir, overwrite |
| template | `TEMPLATE_DELETED` | existing semantics (6d sweep) |
| once | `PRESENT` | none — never diffed |
| once | `MISSING` | create from template |
| project | — | never reported |

On `LOCAL_EDITED`, `template_apply_file` takes `backup_dir`; it writes
`<backup_dir>/<rel>.pre-sync` (full pre-image) and `<backup_dir>/<rel>.diff`, then
overwrites; with `backup_dir` empty in that state the call is REFUSED with a named error
(overwriting a local edit without the backup is the loss this spec removes).
`template_compute_status` returns the diff inline as `local_diff`. `source="skip"` on a
`template` entry is refused under v3; `source="provided"` stays.

**Key audit** (from §5 `PROJECT_CONTEXT.md`): opt-in per ownership rule via
`"audit":"keys"`; the full report shape (`required_keys`, `deprecated_keys`, `aliases`,
`placeholder_map`, and every report field) is specified in §5, not repeated here; never
writes.

`new_template_files` lists only `template` and `once` paths absent from the consumer tree.

**Migration is an explicit tool, `template_migrate_manifest(project_path, backup_dir="",
dry_run=false)`, not a side effect of load.** `dry_run` writes nothing and returns the
would-be `project.md`, `hunk_count`, `migration_base`, `redundant_project_file`,
`project_md_bytes`, warnings, and the would-be v3 manifest (penumbra) — the read-only
pre-release check on a live tree. `template_load_manifest` is the gate: it returns
`manifest_version`, `server_version`, `migration_required`, and refuses (`valid:false`,
named reason) when `requires_server` is unsatisfied. The skill calls migrate at step 1 only
when `migration_required` is true, after copying the pre-migration `CLAUDE.md` and manifest
into `backup_dir`.

1. Read the consumer's `CLAUDE.md`; extract the PROJECT-CUSTOM region content.
2. Diff the remainder against the template `CLAUDE.md` **at the consumer's held version**.
   The base is `git show <template_commit or lastSynced>:templates/<variant>/CLAUDE.md`,
   PLACEHOLDER-REPLACED with the manifest's `placeholders` before the region split and the
   diff — the same rule §6 applies to hashes (penumbra F8/F9, server b2). Fallback chain:
   `template_commit` → `template_version^{commit}` → `migration_base_unavailable`
   (existence checked via `git cat-file -e`; the skill's `git fetch --tags` is what makes
   the fallback reachable — see §9). If no base resolves, emit NO hunk section, add warning
   `migration_base_unavailable`, still write the region content, and NEVER diff against the
   current template (those hunks would be the v3.1 rewrite, not the consumer's edits).
   Hunks outside the region are the consumer's local edits.
3. Write `.claude/rules/project.md` with this shape (the inner diff block is a real
   triple-backtick fence in the written file):
   ~~~
   # Project instructions
   <!-- template-sync: project-owned; migrated from CLAUDE.md at v3.1.0; migration-base: <sha> | unavailable; rendered: yes|no -->

   <region content, verbatim>

   ## Migrated from CLAUDE.md — review, then keep or delete
   ```diff
   <hunks>
   ```
   ~~~
   The "Migrated" section is emitted only when hunks remain AFTER rendering (step 2's
   placeholder replacement removes the spurious ones). The region body is compared,
   normalised, against the template's own region body at the base: identical (the seed) →
   the body is OMITTED and `region_was_seed: true` is reported (open-brain's 74-byte region
   is the seed comment — presenting the toolkit's own seed as the consumer's content would
   defeat the one file whose purpose is to be theirs); base unavailable → the body is kept,
   `region_was_seed: null`. Hunks are **fenced**, so they stop acting as instructions until
   the consumer un-fences them — an edit written against a v2.3 `CLAUDE.md` may contradict
   the v3.1 one, and two live files disagreeing silently is the failure this spec exists to
   remove. Nothing is lost; nothing is silently kept live.
4. Rewrite the manifest as v3. `CLAUDE.local.md` is dropped from it. `CLAUDE.md` becomes
   `template` and is overwritten in the same sync.
5. **Idempotent:** an existing `project.md` is never overwritten; the marker line in the
   header stops step 3 from running twice; a v3 manifest skips migration entirely. Unknown
   top-level manifest keys are PRESERVED and reported as `unknown_keys` (a stale stamp such
   as `deletedAcknowledged` stays visible every sync; silent drop and silent keep both hide
   the mistake — "preserve AND report; silence was the problem, not the policy", drop-and-
   report is not offered as co-equal, open-brain); the known superseded v2 per-file fields
   (`templateHash`, `templateRawHash`, `localHash`, `locallyModified`, `localPartHash`,
   `templatePartHashAtSync`, `resolution`) are dropped.

**`gate_self_reference`** (open-brain, server b5 + addendum): DIRECT self-reference only —
any whitespace token in a `required_keys` value of the audited once file that is
template-class by the ownership rules (directly or via `target`), edited or not:
`template_compute_status` reports `gate_self_reference: [{key,path,status}]`;
`template_apply_file` on such a path and `template_migrate_manifest` REFUSE before any
write, naming the key. A wrapper script outside `hooks/` that still calls
`hooks/run-gate.sh` passes the static check and loops at runtime (measured, exit 78 vs a
`**Gate**: true` control) — the runtime guard `RUN_GATE_ACTIVE` catches it; the static
check cannot. So both tools also report `gate_unverified: true` whenever the audited file
declares `**Gate**:` — the sync never executes it — and the skill's post-sync step runs it
once.

**Report fields** (listed once here so the skill and the server name the same things):
`orphans`, `redundant_project_file`, `unknown_keys` (preserve AND report), `encoding_drift`,
`template_notes_changed`, `placeholder_key_divergence`, `gate_self_reference`,
`gate_unverified`, `restart_required` (skill-side: derived from whether agents/skills
changed — MM-Agent row 5).

## 8. Verification

**Server (`mcp-dev-servers`, pytest).** Class × state matrix: `template` × {identical,
template-updated, locally-edited}, `once` × {present, missing}, `project` × {present} —
asserting status and resulting tree. Migration fixtures, four shapes now, each a real
consumer tree: region + out-of-region edits (open-brain: 3 hunks, region = seed → header +
hunks, no region body); REGION-ONLY (penumbra: 51 lines verbatim, NO "Migrated" heading);
NEITHER on a held template WITH placeholders (panoscribe, yutraffic: header-only
`project.md` — the vacuity control is evidence ONLY if the held template contained
placeholders; on a placeholder-free fixture it passes with the bug present); plus MM-Agent
(zero out-of-region, region content = theirs). Run-twice idempotency; existing `project.md`;
a v3 manifest (no migration). Add the server test on open-brain's exact manifest shape (v2
+ `lastSyncedVersion`/`lastSyncedVersionOf` + 26 clean + 3 keep-mine → v3 with
server-written `template_version`, both keys in `unknown_keys`, keep-mine entries template
class with templateHash carried as hash). The wrapper fixture (open-brain ARM A, a
`scripts/gate.sh` that shells out to `hooks/run-gate.sh`) is the negative case for the
static `gate_self_reference` check.

**Toolkit.** `scripts/test-setup-project.sh` (check 27) asserts every written file carries
an `ownership` value and no variant emits `CLAUDE.local.md`. New consistency checks: the
ownership table covers every template file; the sentinel check (six variants carry the
`context-mode` line + a grep of the plugin bundle for its `includes("context-mode")`
predicate); the ownership.json pattern guarantee row (every pattern matches ≥1
template-tree file, none is a bare root `*.ext`); a no-BOM fixture after a ps1 bootstrap
(no written file starts with `EF BB BF`); the `VERSION` line-2-differs check.
`verify-user-level-drift.sh` unchanged.

**Consumers, before anyone syncs** — same protocol as v3.0.2, read-only against the tag,
in a throwaway copy of *their own tree*: run the migration; report `project.md`'s content
and that `CLAUDE.md` is byte-identical to the template afterwards (pre-apply comparison is
normalised: BOM, EOL). Their out-of-region edits are the fixture nobody else can supply.
Delete-the-guard on the new consistency check: remove a class from the table, the check
must go red.

## 9. Version contract and rollout

1. **Server first** — accepts v2 and v3 manifests; v2 with no v3 template available
   behaves exactly as today.
2. **Toolkit v3.1.0 tag** — `requires_server` in the manifest; the refusal lives in the
   SKILL: `server_version` absent from the `template_load_manifest` response ⇒ server
   < 0.3.0 ⇒ stop with the named reason before any write. This is what makes the
   `server_version` field load-bearing rather than a report line. The skill's `git fetch
   --tags` is what makes §7's `template_version^{commit}` fallback reachable — it is the
   fetch that enables the skill-side refusal.
3. **Consumers restart, then sync** — the step-1 body assertion binds at session start.
   The sync report adds `restart_required: yes|no`.

Consumer sync cadence (MM-Agent row 5): a release states in its CHANGELOG whether it is
docs-only or changes enforcement, so a consumer's hold is a deliberate content gate, not
distrust; the skill's verification rounds shrink with the merge they guarded (2b's control,
step 4, 6b's applied-set retire once there is no merge left to guard).

**Rollback:** none by design. Pre-migration `CLAUDE.md` and manifest sit in the step-2b
backup dir with the absolute path printed.

Anthropic-recommended end state, in which the mechanism layer stops being copied at all).
