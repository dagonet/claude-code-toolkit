# Spec — three-class file ownership for template sync (v3.1)

**Status:** approved design, 2026-09-03. Scope fold-in and challenge-round questions:
`2026-09-05-v3.1-scope-fold-in.md`. Server review and confirmed contract:
`mcp-dev-servers/docs/plans/2026-09-05-v3.1-ownership-server-review.md`; server version
0.3.0. **Two implementation plans follow**, one per
repo, executed in the order §9 fixes: the server's first (backward compatible), then this
repo's. Neither plan is executable until both exist, because the manifest schema and the
status vocabulary in §6–§7 are the interface between them.
**Prerequisite:** `docs/plans/2026-09-03-v3.1-template-diet.md` — `CLAUDE.md` must be
≤ 6 KB before it becomes template-owned.
**Companion, not prerequisite:** `docs/plans/2026-09-03-v3.1-gate-checked-branches-spec.md`.
**Repos:** this one (templates, `setup-project`, consistency checks, and the
`sync-template` skill body at `user-level-reference/skills/sync-template/`) and
`mcp-dev-servers` (the template-sync MCP server and the skill's version contract).

## 1. Problem

Five consumer projects, one release cycle, measured:

- Sync **conflicts** every time a consumer has edited `CLAUDE.md` or `CLAUDE.local.md`
  outside the PROJECT-CUSTOM region. The region protects one block; everything else goes
  through a three-way merge that has dropped lines silently before.
- Apparent **contradictions** between consumers (Test-vs-Gate precedence, session-branch
  gating, which optional plugins apply, protected-branch names) are almost all behaviours
  the template *defaults* where it should *declare*. Once declared per project, they stop
  contradicting.
- Two consumers hold on old versions deliberately because the cost of a sync is a
  hand-merge.

Root cause of the first: **shared ownership of prose files.** The template and the project
both write `CLAUDE.md`. No merge algorithm fixes that; only ownership does.

## 2. Evidence base

- Anthropic: `CLAUDE.md` is "context, not enforced configuration"; conflicting files → "may
  pick one arbitrarily"; `.claude/rules/*.md` without `paths:` loads at launch at CLAUDE.md
  priority; the multi-repo recommendation is a plugin, not copied files.
  (code.claude.com/docs/en/memory, /large-codebases)
- Copier: template-owned / `_skip_if_exists` / `_exclude`, an answers file, per-version
  migrations, and a pre-commit hook forbidding conflict markers. Its issue #33 ("project
  docs replaced by template docs") is this problem verbatim; the fix was "generate in a
  separate path instead of replacing canonical files."
- cruft: `cruft check` in CI = our `verify-user-level-drift.sh`.
- Template-sync actions: a project-declared ignore list.

## 3. Decisions (user-approved)

- **(a)** `CLAUDE.md` becomes fully template-owned. **`CLAUDE.local.md` stops being
  template-shipped** — by Anthropic's definition it is personal and gitignored.
- **(1)** Ownership is expressed in the manifest and enforced by the sync server — a
  coordinated release, not a toolkit-only convention.
- **Automatic migration** of existing consumers on their first v3.1 sync.
- Project prose lives in `.claude/rules/project.md` (no `paths:` → loads at launch). No
  `@import` line needed; no new mechanism.

## 4. The three classes

| class | sync behaviour | files |
|---|---|---|
| `template` | overwritten every sync; a local edit is a **reported loss** (diff shown, diff saved to the backup dir), never a merge | `CLAUDE.md`, `AGENT_TEAM.md`, `.claude/settings.json`, `.claude/agents/*.md`, `.claude/rules/{lang,mcp,sqlite}.md`, `hooks/**` |
| `once` | created if absent, **never touched again** | `.claude/rules/project.md`, `PROJECT_CONTEXT.md`, `PROJECT_STATE.md`, `gitignore` (copied as `.gitignore`) |
| `project` | not in the manifest; the server never reads, writes, or lists it | `CLAUDE.local.md`, anything the consumer adds |

The class is a fact about the file, declared once, not a heuristic about its diff. A file
changing class between versions is a migration (§7), never an inference.

## 5. The five files

**`CLAUDE.md`** — `template`, ≤ 6 KB, facts only. PROJECT-CUSTOM markers **removed**. One
line near the top: *Project-specific instructions: `.claude/rules/project.md` (yours; sync
never overwrites it).*

**`.claude/rules/project.md`** — `once`. Seeded by `setup-project` with a header and
nothing else; seeded by migration with the consumer's former region content (§7). The only
file a consumer writes prose in. No `paths:` frontmatter.

**`CLAUDE.local.md`** — **not shipped.** Its content is redistributed: MCP-usage rules →
`template`-owned `.claude/rules/mcp.md`; SQLite rules → path-scoped
`.claude/rules/sqlite.md` (`paths: ["**/*.db", "**/*.sqlite", "**/*.sql"]`); the
open-brain section is dropped (the open-brain MCP server injects its own instructions).
`setup-project` stops creating it. An existing consumer copy is `project` — untouched.

**`PROJECT_CONTEXT.md`** — `once`, with a **key audit** each sync: the server compares the
consumer's `**Key**:` set against the template's and reports (a) keys the template has that
the consumer lacks, (b) values still holding `{{…}}`. It **never inserts**. A reported gap
every sync beats a silently inserted default nobody reviewed.

**`AGENT_TEAM.md`** — `template`, unchanged class; diet applies.

**`.claude/settings.json`** — `template`, and it stays `template`. One consumer (dotnet)
holds it as PROJECT_CUSTOM to carry a post-edit `dotnet build` hook — which the dotnet
variant used to ship and lost when v2.0 made all six `settings.json` byte-identical.
**That is a variant gap, not a per-project value**, and it is fixed in the template
(§5a), after which the consumer's customisation is redundant and `template` class holds.

### 5a. The rule this sets, and the fix for the dotnet case

> **Every file a consumer holds as PROJECT_CUSTOM / keep-mine is one of two things: a
> variant gap (fix the template) or a per-project value (make it a declared key). It is
> never a reason to give the file a softer ownership class.** The ownership plan includes
> a pass over all five consumers' keep-mine lists, classifying each.

Fix for the dotnet case, keeping `settings.json` and every hook byte-identical across
variants: a new hook `hooks/post-edit-build.sh` on `PostToolUse` `Edit|Write`, which
reads `**Post-edit build**:` from `PROJECT_CONTEXT.md` and runs it. `none` or an unfilled
placeholder → no-op (placeholder reported by the key audit). `setup-project` fills it per
variant: dotnet/dotnet-maui `dotnet build --no-restore -v q` (the command the old hook
ran), every other variant `none`. Same shape as `**Gate**:` — identical mechanism
everywhere, per-project value, declared in the one file hooks already parse. Fixture in
`test-hooks.sh`; no `hooks/lib/` change.

## 6. Manifest v3

```json
{
  "manifest_version": 3,
  "template_version": "3.1.0",
  "template_commit": "<sha of the template repo at sync>",
  "variant": "general",
  "templateRepo": "<path or URL the server resolves>",
  "placeholders": { "PROJECT_NAME": "…" },
  "requires_server": ">=0.3.0",
  "files": {
    "CLAUDE.md":                 { "hash": "sha256:…", "ownership": "template" },
    ".claude/rules/project.md":  { "ownership": "once" }
  }
}
```

- `template_commit` replaces v2's `lastSynced` (the server reads `lastSynced` as an alias).
  `templateRepo` and `placeholders` stay because every template hash is computed AFTER
  placeholder replacement and the server locates the template tree through `templateRepo`.
  `once` entries carry no hash — they are never diffed. Hashes are written with the
  `sha256:` prefix and read in both forms. One hash per `template` entry:
  `TEMPLATE_UPDATED` = current replaced template ≠ hash, `LOCAL_EDITED` = project file ≠
  hash, and when both hold `LOCAL_EDITED` wins (same overwrite, plus the saved diff).
- Every path `setup-project` writes appears here with an `ownership` value. A path absent
  from `files` is `project`.
- The toolkit carries the class table in `templates/ownership.json` at the toolkit repo
  root, variant-independent, shape `{"rules":[{"pattern":"hooks/**","ownership":"template"},
  {"pattern":"gitignore","ownership":"once","target":".gitignore"},
  {"pattern":"PROJECT_CONTEXT.md","ownership":"once","audit":"keys"}]}`; first match wins;
  PurePosixPath-style globs with `**`; paths relative to the variant directory, root-tracked
  `hooks/**` resolving as today; optional `target` for the rename case (manifest key = project
  path); optional `audit` (§7). The server reads it to classify `new_template_files` and the
  migration; a path with no matching rule is reported as `unclassified_template_files` and
  NOT applied — the server half of the red gate. The toolkit half: a consistency check
  asserts every path `setup-project` writes matches a rule and no variant ships
  `CLAUDE.local.md`; its delete-the-guard row removes a rule and expects red. `X.Y.Z` →
  **0.3.0** (named by the server owner 2026-09-05: manifest shape and status enum both
  change).

## 7. Server behaviour

**Statuses** (replace CONFLICT entirely):

| class | status | action |
|---|---|---|
| template | `IDENTICAL` | none |
| template | `TEMPLATE_UPDATED` | overwrite |
| template | `LOCAL_EDITED` | show diff, write diff to the step-2b backup dir, overwrite |
| template | `TEMPLATE_DELETED` | existing semantics (6d sweep) |
| once | `PRESENT` | none — never diffed |
| once | `MISSING` | create from template |
| project | — | never reported |

On `LOCAL_EDITED`, `template_apply_file` takes `backup_dir`; it writes
`<backup_dir>/<rel>.pre-sync` (full pre-image) and `<backup_dir>/<rel>.diff`, then
overwrites; with `backup_dir` empty in that state the call is REFUSED with a named error
(overwriting a local edit without the backup is the loss this spec removes).
`template_compute_status` returns the diff inline as `local_diff`. `source="skip"` on a
`template` entry is refused under v3; `source="provided"` stays.

**Key audit** (from §5 `PROJECT_CONTEXT.md`): opt-in per ownership rule via
`"audit":"keys"`; the server parses `**Key**:` lines on both sides and reports
`missing_keys` and `placeholder_keys` (`{{…}}` values) in `compute_status`; never writes.

`new_template_files` lists only `template` and `once` paths absent from the consumer tree.

**Migration is an explicit tool, `template_migrate_manifest(project_path, backup_dir)`, not
a side effect of load.** `template_load_manifest` is the gate: it returns `manifest_version`,
`server_version`, `migration_required`, and refuses (`valid:false`, named reason) when
`requires_server` is unsatisfied. The skill calls migrate at step 1 only when
`migration_required` is true, after copying the pre-migration `CLAUDE.md` and manifest into
`backup_dir`.

1. Read the consumer's `CLAUDE.md`; extract the PROJECT-CUSTOM region content.
2. Diff the remainder against the template `CLAUDE.md` **at the consumer's held version**:
   `git show <template_commit or lastSynced>:CLAUDE.md` — v2 manifests never carried
   `template_version`. If the SHA is missing or unresolvable, emit NO hunk section, add
   warning `migration_base_unavailable`, still write the region content, and NEVER diff
   against the current template (those hunks would be the v3.1 rewrite, not the consumer's
   edits). Hunks outside the region are the consumer's local edits.
3. Write `.claude/rules/project.md` with this shape (the inner diff block is a real
   triple-backtick fence in the written file):
   ~~~
   # Project instructions
   <!-- template-sync: project-owned; migrated from CLAUDE.md at v3.1.0; migration-base: <sha> | unavailable -->

   <region content, verbatim>

   ## Migrated from CLAUDE.md — review, then keep or delete
   ```diff
   <hunks>
   ```
   ~~~
   The hunk section is emitted only if non-empty. Hunks are **fenced**, so they stop acting
   as instructions until the consumer un-fences them — an edit written against a v2.3
   `CLAUDE.md` may contradict the v3.1 one, and two live files disagreeing silently is the
   failure this spec exists to remove. Nothing is lost; nothing is silently kept live.
4. Rewrite the manifest as v3. `CLAUDE.local.md` is dropped from it. `CLAUDE.md` becomes
   `template` and is overwritten in the same sync.
5. **Idempotent:** an existing `project.md` is never overwritten; the marker line in the
   header stops step 3 from running twice; a v3 manifest skips migration entirely. Unknown
   top-level manifest keys are PRESERVED and reported as `unknown_keys` (a stale stamp such
   as `deletedAcknowledged` stays visible every sync; silent drop and silent keep both hide
   the mistake); the known superseded v2 per-file fields (`templateHash`, `templateRawHash`,
   `localHash`, `locallyModified`, `localPartHash`, `templatePartHashAtSync`, `resolution`)
   are dropped.

## 8. Verification

**Server (`mcp-dev-servers`, pytest).** Class × state matrix: `template` × {identical,
template-updated, locally-edited}, `once` × {present, missing}, `project` × {present} —
asserting status and resulting tree. Migration: a v2 tree with region + out-of-region
edits; **a v2 tree with neither** (the vacuity control — must yield a header-only
`project.md`, so a non-empty one is evidence rather than default output); run-twice
idempotency; `project.md` already present; a v3 manifest (no migration).

**Toolkit.** `scripts/test-setup-project.sh` (check 27) asserts every written file carries
an `ownership` value and no variant emits `CLAUDE.local.md`. New consistency check: the
ownership table covers every template file. `verify-user-level-drift.sh` unchanged.

**Consumers, before anyone syncs** — same protocol as v3.0.2, read-only against the tag,
in a throwaway copy of *their own tree*: run the migration; report `project.md`'s content
and that `CLAUDE.md` is byte-identical to the template afterwards. Their out-of-region edits
are the fixture nobody else can supply. Delete-the-guard on the new consistency check:
remove a class from the table, the check must go red.

## 9. Version contract and rollout

1. **Server first** — accepts v2 and v3 manifests; v2 with no v3 template available
   behaves exactly as today.
2. **Toolkit v3.1.0 tag** — `requires_server` in the manifest; the refusal lives in the
   SKILL: `server_version` absent from the `template_load_manifest` response ⇒ server
   < 0.3.0 ⇒ stop with the named reason before any write. This is what makes the
   `server_version` field load-bearing rather than a report line.
3. **Consumers restart, then sync** — the step-1 body assertion binds at session start.

**Rollback:** none by design. Pre-migration `CLAUDE.md` and manifest sit in the step-2b
backup dir with the absolute path printed.

## 10. Out of scope, stated

v3.1 carries the `git-cmd.sh:937` lib fix (fold-in §3.1 item 1), so the parser matrix is
mandatory before the v3.1.0 tag; the gate-checked parser may therefore live in the lib
beside `gc_protected_branches`. No plugin packaging (v4 — the
Anthropic-recommended end state, in which the mechanism layer stops being copied at all).
`**Gate-checked branches**:` is its own spec and may ride the same release if its plan is
ready. `user-level-reference/CLAUDE.md` and the agent files are a later diet.

## 11. Migration note (draft, for the CHANGELOG)

> Your first sync to v3.1 moves the PROJECT-CUSTOM region of `CLAUDE.md` — and any other
> local edits you made to it — into `.claude/rules/project.md`, then replaces `CLAUDE.md`
> with the template's. Local edits are placed under a "Migrated" heading, fenced; read
> them once and un-fence what still applies. `CLAUDE.local.md` is yours now: the template
> no longer ships or touches it. Sync will never again report a CONFLICT on either file.
> After this, edit only `.claude/rules/project.md` and `PROJECT_CONTEXT.md` values; every
> other template file is overwritten on sync and the sync tells you when it does.
> Files you held as keep-mine / PROJECT_CUSTOM migrate to `template` class and are
> overwritten on the first v3.1 sync with their diff saved in the backup dir — per §5a they
> were a variant gap or a per-project value, and the sync report names each one.
