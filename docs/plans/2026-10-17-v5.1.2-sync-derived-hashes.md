> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close GitHub issue #210. `template_finalize_sync` derives an applied file's manifest entry itself when the caller gives only its path. `template_apply_file` reports placeholders left in what it wrote. The sync skill uses both. Release as v5.1.2.

**Architecture:** Both changes are additive and live in `server/src/template_sync/v3.py`, which serves v3 and v4 manifests (`v3.manifest_supported`). The full apply-result form stays valid unchanged. One new helper, `derive_manifest_entry`, is shared by the applied path-only branch and the existing `new_files` loop. The skill's step 7 then writes paths and actions, no hashes.

**Tech Stack:** Python 3 (the template-sync MCP server), pytest via `bash scripts/test-server.sh`, bash consistency checks.

**Spec:** GitHub issue #210 (https://github.com/dagonet/claude-code-toolkit/issues/210). It carries over #175 items 11 and 13. Worktree `~/git/.worktrees/claude-code-toolkit/v512`, branch `fix/v5.1.2`, based on `fix/v5.1.1` at 25c80dd (v5.1.1 is still unmerged; rebase onto main after it merges).

## Global Constraints

- KISS. Additive only: no manifest schema change, no new tool, no new parameter.
- The existing applied item form `{"file_path", "manifest_entry", ...}` keeps its exact validation and messages.
- Fail closed: an applied item the server cannot derive refuses the WHOLE finalize ("applied_files validation failed — manifest NOT written"), exactly like an invalid entry today.
- The derived hash must equal what `apply_file_v3` records for the same file: `format_hash(core._sha256(template_content(pp, manifest, rules, proj_rel, tpl_raw)))`.
- Placeholder shape is `{{[A-Z_]{2,}}}` (the skill's sweep uses the same); report names without braces, sorted, unique.
- Every file LF. No heredocs in commands (Write tool). `git -C <absolute path>`. Push in its own call. Never push to main, never `--no-verify`.
- `bash scripts/test-server.sh` needs `server/.venv` in this worktree: run `bash server/install.sh` once first (from the worktree).
- The consistency script checks the CURRENT DIRECTORY's tree: run it through a wrapper script that does `cd /home/darknite/git/.worktrees/claude-code-toolkit/v512 || exit 1` first.

## Review Focus

1. A path-only item for a file applied with `source="provided"` (a keep-mine splice): the derived hash must be the TEMPLATE's rendered hash (what apply records), not the provided content's. Test in Task 1.
2. A path-only item whose template file no longer exists: the whole finalize is refused and the manifest bytes are unchanged. Test in Task 1.
3. A mixed list (full results, path-only dicts with `action`, bare strings): all recorded, and `files_created` still counts a path-only item that carries `action: "created_from_template"`. Test in Task 1.
4. A path-only item with `..` or an empty path: refused by the existing `invalid file_path` check. Test in Task 1.
5. A manifest missing a placeholder key the template uses: the apply result lists that name. With every key present, the list is `[]`. Test in Task 2.

### Task 1: finalize derives a path-only applied item

**Files:**
- Modify: `server/src/template_sync/v3.py` (`finalize_v3` ~:1459-1526; new helper near `template_content` ~:1030)
- Modify: `server/src/template_sync/mcp.py` (`template_finalize_sync` docstring ~:1797-1860: document the path-only form)
- Test: `server/tests/test_template_sync_v3_finalize.py` (fixtures `_mk_v3` :33, `_tpl_entry` :66; apply via `template_apply_file` as in `test_finalize_counts_files_created_separately` :374)

**Interfaces:**
- Produces: `derive_manifest_entry(pp: pathlib.Path, manifest: dict, rules: OwnershipRules, proj_rel: str) -> tuple[dict | None, str | None]`, in `v3.py`. It returns `(entry, None)` or `(None, error)`:
  - `entry` is `{"ownership": "once"}` or `{"hash": "sha256:<hex>", "ownership": "template"}`;
  - `error` is exactly `f"template file {tpl_rel} not found"` or `"no template/once rule"`.
- `finalize_v3` accepts, in `applied`:
  - (a) the full apply result, as today;
  - (b) a dict with `file_path` and no `manifest_entry` (optional `action` kept for counting);
  - (c) a bare path string, treated as `{"file_path": s}`.
  - Anything else is invalid: `f"applied item must be an object or a path string: {item!r}"`.
  - A derivation error becomes the invalid entry `f"{fp}: {error}"`.
- **Amended after the Task 1 review (round 1).** The helper decides ownership the way `apply_file_v3` does. The stored manifest entry wins: `(stored.get("ownership") if stored else None) or rules.class_of(tpl_rel)`. A `project` class is refused with apply's message. Under `claude_md_window_active(manifest, tpl_rel, tpl_raw)`, the helper returns apply's error `f"CLAUDE.md: {MIGRATION_REQUIRED_REMEDY}"`. Each case gets a test: path-only equals apply's `manifest_entry` for a tracked file whose stored ownership differs from the rules, in both directions; and path-only CLAUDE.md in the window refuses the whole finalize.

- [ ] **Step 1: Write the failing tests** in `test_template_sync_v3_finalize.py`:

  - `test_finalize_derives_template_hash_for_provided_apply`: apply with `source="provided"` and different content, finalize path-only, and assert the manifest hash equals the apply result's `manifest_entry["hash"]` and differs from the sha256 of the provided content.

  - `test_finalize_path_only_missing_template_refuses_whole_finalize`: the template file is removed before finalize. The result has `"error"` with "manifest NOT written", `invalid_entries` contains `"<fp>: template file <tpl_rel> not found"`, and the manifest file bytes are unchanged.
  - `test_finalize_mixed_applied_forms_and_created_count`: one full result, one `{"file_path", "action": "created_from_template"}`, one bare string. All three are in the manifest, and `files_created` is 1.
