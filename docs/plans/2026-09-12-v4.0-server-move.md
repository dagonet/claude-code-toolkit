# v4.0 — move template-sync-tools into the toolkit (goal and spec, 2026-09-12)

> Status: approved by the user 2026-09-12 with the three decisions below taken. Removal-side facts were measured by the mcp-dev-servers session at v0.3.8. The task-level implementation plan is a separate document, written when execution starts, as v3.1 did with its spec and plan.

## The goal, one line

**`/goal` text:** *v4.0.0 — the template-sync MCP server ships from this repo: same tool names, same manifest contract, one VERSION for templates, skill and server; every consumer re-registers once and nothing else about a sync changes; mcp-dev-servers removes it in its next version only after v4.0.0 is released and consumer-verified; no v4.0 PR merges without a review from a session that did not write it.*

## Why this shape

The move was decided against a recorded recommendation not to. The recommendation's two reasons are therefore the goal's two hardest constraints, not arguments to reopen:

1. **The seam shrinks, and what remains must stay measured.** Co-location buys "templates + skill + server change in one commit." It must not buy "the contract stops being written down." The manifest schema, ownership table, hashes, floors and capabilities keep their contract doc and their structural tests — moved, not dropped.
2. **The second reader found every defect in fourteen releases.** The repo boundary was the mechanism; the property has to survive without it. Hence the review constraint in the goal line, and the sequencing that keeps the server session as an outside reviewer measuring against tags.

## Out of scope — explicitly, so nobody folds it in

- **The `@import` cutover.** v4.1, on the unified repo. It needs the region-migration logic (the operation that produced the 0.3.2 regression) and is the reason the one-commit property is worth having — but it is a separate hazard and gets its own plan, of the v2→v3 shape: dry-run, backup, report, refuse rather than guess.
- Tool renames, manifest schema changes, any change to sync semantics.

## Sequence

1. Spec + plan committed to `docs/plans/` (this document, finalised), reviewed by the server session.
2. Branch `v4/server-move`: items 1–9, one PR per item or batched where same-shape, each gated and cross-reviewed.
3. Consumer round on the branch tip: re-register against the branch's venv, dry-run sync, report `server_source` and `server_version`.
4. v4.0.0: tag, propagate, release. Release note leads with the one action.
5. Consumer verification: ≥ 2 consumers re-registered against the tag, synced green, drift 0.
6. mcp-dev-servers 0.4.0 removes it. Its release note points at v4.0.0.
7. v4.1 planning opens: the `@import` cutover.

## Risks the goal owns

- **Two one-way doors, both in the toolkit's step, both closed by item 4.** If v4.0 raised the splice floor, the first finalize under the new server would raise every existing manifest to `">=4.0.0"` automatically — one-way per project, before the consumer decided anything — and any session still registered against 0.3.8 would then get a load refusal that reads as a regression. Not raising the floor in 4.0 removes both. The release note still states that the *only* consumer action is re-registration, and that a project remains loadable by either server.
- **`server_version` in the wrong namespace** (item 4a) is a machine-wide load outage. The check exists before the first v4.0 tag, not after.
- **Mid-session skew** (item 4b): `git pull` advances templates immediately and the server not at all. `server_commit` beside `template_commit` makes it visible; the skill names it.
- **Both copies exist for a window** (between steps 4 and 6). A consumer who has not re-registered runs 0.3.8 — fine, contract unchanged. One who has runs 4.0.0 — fine. Nobody runs "the wrong one"; the skill reports which via `server_source`.
- **A consumer reinstalls instead of re-registering.** The venv hazard is real and measured (locked launcher, no shim mid-flight). Every note says re-register and restart; none says reinstall.
- **`__version__` from the wrong place.** A literal drifts (v3.1.2); an import-time read of the repo-root file fails for non-editable installs. Package data, byte-identical to the root by a check, no silent fallback (item 3).
- **A registration written before its exe exists.** Item 8's ordering and the fixture's two assertions.
- **Gate time.** +32 s idle, +73 s under concurrent gates, at merge. Accepted in item 6, or reduce by marking slow tests.
- **Values crossing a namespace boundary that looks like a formatting difference.** Four times in the v3.1 round alone: the `v` prefix (version number vs tag name), `"unknown"` vs `null` (sentinel string vs contract null), `X.Y.Z` vs `v4.0.0` at `parse_version`, and now POSIX vs Windows paths in `templateRepo` vs `server_source`. Each survived a read-through because the two forms look alike. Rule for every v4.0 item that compares two values: name the namespace of each side in the spec, and if they differ, the comparison happens where a resolver exists — the server — and the skill reads a boolean. The skill's existing platform note about bash-typed paths handed to Python is this hazard arriving as an argument; item 9 is it arriving in a manifest field.
- **The second reader.** Constraint 13 is the mitigation. If it stops being honoured, the move's cost has arrived. Round 2 of the first PR is the measurement: the reviewer found a defect *in the fix for their own finding*, by showing two live values rather than predicting a mismatch.

## Decisions taken (user, 2026-09-12)

1. Item 6: **third gate command**, merge-time.
2. Location: **`server/` at the root, package `template_sync`** (item 1 as written).
3. `@import` home: **v4.1** — precedent (the v2→v3 migration shipped as a minor), and the hazard lives in the managed migration, not the steady state. Release note to be written as if it were a major: consumers must act, and the first sync under it is one-way.

## What the `@import` cutover means for the toolkit (for decision 3)

**Today.** `templates/*/CLAUDE.md` is one file with a `PROJECT-CUSTOM` region. It is `template`-class, but only outside the region: on every apply the server *splices* the consumer's region back in (`region_splice`, 0.3.2+), and check 39 pins the markers because they are how the server finds the region. Consumer instructions live inside it.

**After.** `templates/*/CLAUDE.md` is byte-identical for every consumer — genuinely `template`-class, overwritten wholesale, no splice — and carries one line, `@.claude/project-instructions.md`. That file is `once`-class: seeded at bootstrap, never touched by sync. Claude Code resolves the import at session start (measured) and it reaches spawned subagents (measured — the property rules files failed).

**What changes, file by file:**

| Where | Change |
|---|---|
| `templates/*/CLAUDE.md` ×6 | region and markers removed; the `@` line added; the context-mode sentinel line stays (check 37). Byte budget (check 35) falls. |
| `templates/ownership.json` | one new `once` row for the imported file. `.claude/rules/project.md` stays as it is — a different purpose (`paths:`-scoped conventions). |
| check 39 | retired, or inverted: assert **no** markers and assert the `@` line. |
| new check | the `@import` probe, re-run against the installed Claude Code on every gate — because the dependency is unversioned and its failure is silence. |
| `setup-project.{sh,ps1}` | seed the imported file; `--wrap-existing-claude-md` moves an existing consumer `CLAUDE.md` into it instead of into the region. |
| server (in-repo after v4.0) | the **migration**: read the region body out of the consumer's `CLAUDE.md` (the server already computes it) → write it to the imported file → apply `CLAUDE.md` wholesale. Dry-run first, backup before any write, report what moves, **refuse rather than guess** when the region cannot be resolved. Out-of-region edits are reported and discarded, as today. The region machinery stays for this path and for consumers who have not migrated. |
| the floor | **rises, legitimately, for the first time.** A pre-cutover server given a marker-less template reports `region_orphaned` and the consumer's region survives only in `backup_dir` (penumbra's case I, measured). So `requires_server` must become `">=4.1.0"` — and here the monotonic per-project raise is the *correct* tool, because the contract really changed. The release note says the first sync is one-way. |
| consumer's always-on channel | unchanged in effect, improved in reach: their instructions still load at session start, and now reach subagents. The file is theirs forever. Template-side additions never arrive — the same trade the region already makes. |

**What does not change:** hooks, agents, `PROJECT_CONTEXT.md`, the manifest schema (one new row), tool names, the sync skill's structure.

**The coupling v4.0 creates makes the migration a normal action:** after the move, `git pull` of the toolkit to 4.1 pulls the server to 4.1; restart; the next sync migrates. That is why the cutover *needs* the v2→v3 shape rather than a cheerful one — it will be triggered by the routine thing consumers already do.

**v4.1 or v5?** The cutover is a contract change with a one-way floor raise and a data-bearing migration — "breaking" in spirit. Precedent argues for **v4.1**: the v2→v3 manifest migration, the same class of change, shipped as v3.1, and the hazard lives in the migration (managed by dry-run + floor + refuse-not-guess), not in the steady state. The case for **v5.0** is one line: consumers must act, and a major number says so louder. Recommendation: **v4.1**, with the release note written as if it were v5.

**Adjacent, not included:** `CLAUDE.local.md` retirement (deferred since v3.1) could ride the same mechanism later — an import of a gitignored file — but that is its own measurement and its own plan.
