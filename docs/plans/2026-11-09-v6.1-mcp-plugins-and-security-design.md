# v6.1 design: the mcp-dev-servers as dagonet plugins, plus the v6.1 security fixes

**Status:** DRAFT 2026-11-09, revised 16:51 for the public marketplace. Q1 and Q2 are settled by that steer (§8). The implementation plan sits beside this file.

## 1. Intent

The user asked for three things on 2026-11-09:

- "next I want each of the mcp-dev-servers to be additional plugins for the cct market place - analyze that provide a plan for implementation"
- "and include the 6.1 security fixes"
- "keep in mind that this marketplace is public and I am not only focussed on my setup"

**The public marketplace sets the frame.**

- Anyone can add `dagonet` and install any one plugin without the others, without cct, and on Linux, Windows or macOS.
- Nothing in a plugin may assume the maintainer's machines: no paths, no default set, no Ollama host.
- Each plugin works alone. cct adds its protections when it is present, and nothing more.
- The maintainer's own two machines are migrated by an attended runbook (§4.5), kept apart from the public docs.

**Why (my reading; the user has not stated it).** Today each machine has to clone mcp-dev-servers, build a venv, and run `claude mcp add` per server, or have setup-project write a per-clone `.mcp.json`. That path has rotted without anyone noticing (§2). As plugins, the servers install with `claude plugin install`, are pinned to a toolkit release, and are checked by the drift probe like cct.

**Goals**

- Six new plugins in the `dagonet` marketplace, one per server: git-tools, github-tools, dotnet-tools, ollama-tools, rust-tools and python-tools.
- Each plugin is an independent opt-in: `claude plugin install <name>@dagonet`.
- No clone, no venv and no `claude mcp add` on any machine. The one prerequisite is `uv`, plus whatever CLI the server drives: git, gh, the dotnet SDK, cargo, Ollama.
- The four v6.1 security fixes (§6).
- No guard weaker than today. This includes the tool rename in §5.

**Non-goals**

- Publishing mcp-dev-servers to PyPI.
- Changing what the servers do.
- The template plugin-off guard speed-up and the v6.0 final-review minors M1–M4. These are v6.1 candidates, but the user named only the security fixes; they stay out unless the user adds them.

**Anti-goals** (failure even if it works)

- A deny rule or gate that silently stops matching.
- A per-session start cost the user notices.
- A second install path to maintain beside the old one.

## 3. Platform facts

**From the Claude Code docs** (code.claude.com, fetched 2026-11-09)

- **Tool names.** A plugin's MCP tools are named `mcp__plugin_<plugin>_<server>__<tool>`. Quote: "A matcher written against the bare server key never fires for these tools." The same holds for permission rules.
- **Config.** Plugin MCP config lives in `.mcp.json` at the plugin root. `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` and `${user_config.KEY}` are expanded in `command`, `args` and `env`. Servers see the same environment as manually configured servers.
- **Start-up.** Enabled plugins' servers start **eagerly** at session start. A failed stdio server is not retried for 15 minutes.
- **No pip.** Marketplace sources are a relative path, github, url, git-subdir, npm, archive or command. There is no pip source, and Python dependencies are not installed automatically.
- **Dependencies.** `dependencies` between plugins exist, with npm semver ranges.
- **Project-scope enabling.** A plugin enabled in project settings but not installed shows an Errors-tab entry, with no prompt. A relative-path plugin may load from the marketplace clone without an install record. Plugins shared through the repository need the same per-server approval as a project `.mcp.json`.

**Measured on Linux** (uv 0.13.7, mcp-dev-servers v0.4.0)

| How the server starts | Time to start and exit on empty stdin |
|---|---|
| `uvx --from "mcp-dev-servers @ git+https://github.com/dagonet/mcp-dev-servers@v0.4.0" mcp-git-tools` | cold 3.7 s, warm 1.6 s. A tag pin re-checks the network on every start. |
| the same, pinned to the 40-character commit | 1.3 s the first time, then **0.69 s**; with `--offline` **0.68 s** |
| today's venv console script | 0.65 s |

- **Memory.** A running server is about 15–27 MB RSS. 13 sessions are open on this host, so six servers in every session would add about 80 processes, roughly 1–2 GB.
- **Tooling.** uv is on both machines: Linux 0.13.7, PC 0.10.4, in Git Bash and PowerShell. Python is 3.14.4 on Linux; the PC has 3.14.2 plus uv-managed 3.11–3.13.

## 4. Design: the six plugins

### 4.1 Layout (my call)

- **Where.** Each plugin lives in the toolkit repo as two small files:
  - `plugins/<name>/.claude-plugin/plugin.json`
  - `plugins/<name>/.mcp.json`
- **Marketplace.** `.claude-plugin/marketplace.json` gains six entries `{ "name": "<name>", "source": "./plugins/<name>", "description": ... }`.
- **Why the toolkit repo.** One release train and one tag pin, the one users already add. The server code stays in mcp-dev-servers.
- **Server key.** The server key equals the plugin name, which is today's key, so the tools are `mcp__plugin_<name>_<name>__<tool>`.
- **The `.mcp.json` command:** `uvx --from "mcp-dev-servers @ git+https://github.com/dagonet/mcp-dev-servers@<40-char sha>" mcp-<name>`.
  - The SHA is a **tagged** mcp-dev-servers commit; a commit pin starts as fast as today and works offline (§3).
  - There is no SessionStart installer, no data directory and no venv; uv's cache does that job.
  - Prerequisite on every machine: `uv` on the PATH of the Claude process.
- **Environment.**
  - github-tools sets the constant `GH_PROMPT_DISABLED=1` in its `env`. `GH_EXE` is inherited from the user's environment, if set.
  - Nothing machine-specific goes into `.mcp.json`.
  - ollama-tools declares three `userConfig` options: `ollama_url`, `model_first_pass` and `model_extract_json`. They carry the server's own defaults, so a user who never sets them gets today's behaviour, and they feed `OLLAMA_URL`, `OLLAMA_MODEL_FIRST_PASS` and `OLLAMA_MODEL_EXTRACT_JSON`.
  - Task 0 measures whether `userConfig` takes a default, and what an unset option expands to. If an unset option would expand to an empty string that overrides the server default, the fallback is to inherit the variables from the user's environment and document that.
- **Descriptions.** Each `plugin.json` and marketplace entry says, in one line, what the server does and which CLI it needs, for example "needs the .NET SDK on PATH", so a stranger can choose.
- **Versions.**
  - Every sub-plugin's `plugin.json` `version` equals `VERSION`. Check 72 extends to all seven manifests, because without a bump no machine receives the update.
  - A new check asserts that all six `.mcp.json` files pin the same 40-hex SHA, that it is the commit of a `v*` tag in mcp-dev-servers (read from a pinned constant in the check, not the network), and that each names its own `mcp-<name>` script.
- **Plugin root and cct.** The cct plugin root is the repo root, so `plugins/` lands in cct's cache copy. Claude Code reads only `<root>/.mcp.json`, `agents/`, `skills/` and `hooks/hooks.json` there, so that copy is inert. Task 0 confirms that cct gains no servers.

### 4.2 Where they are switched on (settled by the public-marketplace steer)

The servers start eagerly in every session where their plugin is enabled. A public marketplace cannot know which ones a stranger wants, so:

- **Nothing is installed or enabled by default.** Not by the marketplace, not by cct, and not by the installer.
- **Install.** A user runs `claude plugin install <name>@dagonet`, which by default enables the plugin at user scope, in every project.
- **Per project.** A user who wants a server in some projects only installs it, disables it at user scope, and enables it per clone with `claude plugin enable <name>@dagonet --scope local`. That writes the gitignored `.claude/settings.local.json`, so it is personal and per machine, like today's gitignored `.mcp.json`. The docs show both patterns and the memory cost: about 15–27 MB per server per session.
- **setup-project** (the toolkit's public bootstrap): for the dotnet and dotnet-maui variants it enables dotnet-tools at local scope, and for rust-tauri it enables rust-tools, **only when that plugin is already installed**. Otherwise it prints one line saying which plugin would add .NET or Rust tools. This mirrors today, where it writes `.mcp.json` only when given `--mcp-dev-servers-path`.
- **The template settings stay byte-identical.** No `enabledPlugins` entry for the six goes into the templates: a stranger without the plugin would get an Errors-tab entry, and repository-shared plugin servers need the per-server approval that stalls headless and cloud runs.

### 4.3 Installer, drift probe, docs

**`scripts/install-user-level-linux.sh` step 1.**

- `marketplace remove` uninstalls every dagonet plugin (backlog #20), so the installer currently reinstalls only cct and silently drops the rest.
- New behaviour:
  1. Before the remove, record which dagonet plugins are installed at user scope, and whether each is enabled.
  2. After `marketplace add #tag`, reinstall each one and restore its enabled state.
  3. It never installs a sub-plugin that was not there before.
- The Windows recipe (`docs/plugin-migration-windows.md` and the CHANGELOG downstream-migration section) gets the same steps.

**`scripts/verify-user-level-drift.sh`.**

- Each installed dagonet sub-plugin must sit at `VERSION`. A sub-plugin that is not installed is not drift.
- A user-scope `claude mcp` entry that shadows the name of an installed sub-plugin counts as drift, because two copies of a server would be running.

**setup-project.sh and .ps1.**

- They stop writing dotnet-tools and rust-tools into `.mcp.json` and do the §4.2 local enable instead.
- `--mcp-dev-servers-path` is accepted for one release with a warning that it is ignored.
- The bootstrap fixtures (check 27) follow.

**Public docs.**

- **README:** a short "MCP server plugins" section with the install line per plugin, the uv prerequisite (with the uv install link), each plugin's CLI requirement, and the two enable patterns from §4.2.
- **`mcp-servers/HOWTO.md`:** the mcp-dev-servers sections are rewritten to the plugin install, with the ollama-tools options. The old venv path becomes a short note: "Upgrading from a manual install: after installing the plugin, remove your `claude mcp add` registration (`claude mcp remove --scope user <name>`) and any per-project `.mcp.json` entry for it, or the server runs twice."
- **mcp-dev-servers README:** one paragraph pointing Claude Code users to the plugins, with the pip install kept for other MCP clients. That is a small separate PR in that repo.
- **The cloud recipe (README:91):** gains the plugin install lines and uv. Task 0 measures uv and PyPI reachability in a cloud run.

**Platforms.** Linux is measured here and Windows by the PC helper in Task 0. macOS is not tested, since no mac is available: the docs say "expected to work, untested", and uvx is cross-platform.

### 4.4 mcp-dev-servers side

- Nothing changes: the v0.4.0 SHA runs under uvx as measured. A later server fix reaches users through a toolkit release that bumps the pin.

### 4.5 The maintainer's own machines (attended runbook, not public docs)

These run after the release, on the user's go, from `$HOME`:

1. The installer, or the Windows recipe.
2. Install the plugins the user wants on each machine.
3. Verify each server in `/mcp`.
4. Then remove the old registrations:
   - `claude mcp remove --scope user github-tools` on both machines;
   - `claude mcp remove --scope user ollama-tools` on the PC, after setting the three ollama-tools options to the PC's current values;
   - per-clone `.mcp.json` entries: listed for the user, never deleted by a script. Organizer's dead rust-tools entry is the user's call.
5. Run the drift probe: 0 on both machines.

Which plugins go on which machine is asked at install time.

## 5. Security item S5: the plugin rename must not open the guards

Moving a server into a plugin renames every tool (§3). Every rule in §2 that names an old-form tool stops matching, and nothing reports an error. Concretely:

- auto-merge through github-tools leaves the merge gate;
- the five git-tools write tools leave the deny list, with a matching allow `mcp__plugin_git-tools_git-tools__*`;
- agents lose the GitHub and .NET tools from their `tools:` lists.

**Fix (my call): twin every rule.** Each old-form name gets its plugin-form twin in the same rule:

- the `hooks/hooks.json` merge matcher;
- the template allow and deny lists (six variants, still byte-identical);
- `user-level-reference/settings.json`;
- the root `.claude/settings.json`;
- every agent `tools:` list. Task 0 confirms that a `tools:` entry naming an absent tool is harmless.

The old names stay. They cost nothing and cover machines and consumers that have not migrated.

**A new consistency check.** Every old-form `mcp__(git|github|dotnet|ollama|rust|python)-tools__X` named in a guard-bearing file must have its `mcp__plugin_<name>_<name>__X` twin in the same rule or list, and the reverse. A missing twin goes red. The check is two-sided:

- a fixture with one twin removed must fail;
- the full tree must pass.

**Behaviour rows in `test-hooks.sh`:**

- the plugin-form `github_pr_auto_merge` is refused without a gate pass and allowed with one;
- the dead `no-push-main.sh` and `pre-commit-test.sh` MCP branches either get both names, or are deleted with a comment that nothing routes MCP tools there. That is the builder's call; deleting is KISS.

**The git-tools write tools stay in the server (§8).** In cct-template projects the twinned deny rules keep them blocked under both names.

## 6. The four v6.1 security fixes (backlog since the v6.0 review)

Each fix starts with a failing test (red), then the fix (green). Where a parser configuration is involved, the test runs in that configuration.

**S1. A lone surrogate empties the command on python3-only hosts.**

- The python3 JSON reader in `hooks/lib/json.sh` returns rc 0 with an **empty** `tool_input.command` for a payload holding a lone-surrogate escape (`\udcff`).
- The git gates' `[ -n ]` fast exits then allow the command, which is a fail-open on hosts with python3 and no node.
- **Fix:** the reader keeps the text (an error handler that does not drop the string). In addition, a reader rc 0 with an empty command while the raw payload carries a non-empty `"command"` is treated as cannot-determine and refuses. The test is a lone-surrogate payload in the python3-only matrix row.

**S2. `gc_protect_c_paths` has no fallback.**

- If `sed` is missing or fails, it returns empty. `GC_CMD` becomes empty, and a `git -C ...` command is allowed.
- **Fix:** on failure, return the input unchanged. That is the documented floor: "v4.1.1's behaviour is the floor, never allow-all". The test runs a PATH without sed.

**S3. The registration resolves `bash` from PATH.**

- The plugin registration is `exec bash "${CLAUDE_PLUGIN_ROOT}/hooks/dispatch.sh" bash|powershell`.
- Under a raw `usr\bin\bash.exe` launcher with a PowerShell PATH, `bash` is WSL's bash, which gives 127. That is a non-blocking hook error, so the guards do not run. 5.2.1 had the same exposure.
- **Fix:** `exec "${BASH:-bash}" ...`. **First** measure, in a temporary HOME, which shell Claude Code uses to run hook command strings on Linux and on Windows. If it is `sh`, `$BASH` is empty and the fallback applies, which is no worse than today.

**S4. The 56-minute hang window.**

- The dispatcher's single registration carries timeout 3360 s, needed for pre-commit-test's **Test**. The closed guards (no-push-main, gate-before-merge, deny-secret-reads) therefore run under it too.
- no-push-main's cost grows quadratically with the command's length. A pathological command could hold a tool call for up to about 56 minutes.
- **Fix (KISS):** the dispatcher refuses any command longer than N bytes, with "command too large for the safety checks: put it in a script file and run bash <path>". That fails closed and bounds the time.
- **Picking N:** measure the closed guards' time against command size, and the largest real command in recent transcripts on both machines. N must sit far above the real maximum and below the size where the guards pass about 10 s.

All four touch the hook libraries, so the release needs the full gate, the parser matrix and the PC Windows suite run. These are machine-wide jobs: announce them, never overlap them, and on the PC wait for mm-agent's all-clear.
