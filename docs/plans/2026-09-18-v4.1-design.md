# v4.1 — option B: template-owned `CLAUDE.md`, project-owned instructions and agent grants (design spec)

**Status:** spec draft, 2026-09-18. Kept separate from v4.0.3 (which lands on main first); implementation branch `v4/1` is cut from main after v4.0.3's release commit.
**Decision of record:** 2026-09-12 (v4.0 ledger, after challenge): v4.1 = option B — byte-identical template `CLAUDE.md` + `@.claude/project-instructions.md` (once-class), file-level ownership, a PreToolUse deny on consumer writes to `CLAUDE.md`, a precedence sentence in the template body, the `@` line at the END, sync refuses any consumer `CLAUDE.md` diff outside the import line, v2/v3-shape migration (dry-run, backup, move region content, refuse-not-guess), a recurring gate check because `@import` is unversioned, and the first legitimate skill-floor raise `>=4.1.0`. Options A (region + marker-parsing hook) and C (dual support) were rejected. **2026-09-18 (user):** agent tool grants are in scope via a server-spliced project-owned grants file.
**Version:** toolkit `4.1.0`, server `4.1.0`, `manifest_version` **4** (the manifest gains `instructions_file` and `agent_grants` declarations; a v3 server must not silently apply a v4 manifest), skill marker `v4.1.0`, `requires_skill >=v4.1.0` in `templates/ownership.json`, `MIN_SERVER_FOR_V4 = 4.1.0`.

## Goal

Every consumer's `CLAUDE.md` is byte-identical to its variant's template; project content lives in one project-owned file the template imports; per-agent project tool grants live in one project-owned file the server splices; a sync can therefore never conflict on `CLAUDE.md` or on a grant-only agent diff, and `template_verify` reports both as IDENTICAL.

## Spike results (measured before this draft)

- **(b) Delivery gate = session start, not HEAD.** In this session: an unscoped rules file present at session start but UNTRACKED (`zz-load-probe.md`) was delivered to a subagent; a rules file created mid-session was not delivered untracked, staged, or COMMITTED on a branch (three spawns, 2026-09-18). Consequence: every instruction file this release introduces or moves is "picked up at the next session start" — the migration step and the seeds say so, and no verify line may claim a mid-session effect.
- **(a) Precedence.** Documentation (search-snippet verified, `code.claude.com/docs/en/settings`, `/memory`): no hard precedence rule between memory sources; the documented mitigation is an explicit precedence sentence in the more specific file. `@path` resolves relative to the file containing the line; import chains are capped at four hops; code spans are skipped; the launch-time snapshot is cached until `/clear`, `/compact` or restart. Unscoped `.claude/rules/*.md` load at session start at CLAUDE.md priority; `paths:`-scoped ones load on matching reads (open issues report Write not triggering). Consequence: precedence is established by the template's own sentence (below), never assumed from position; the `@` line is last only so the project text is nearest the end of context.
- **Agent `tools:`** (docs, `/sub-agents`): omitted = inherit everything incl. MCP; `tools:` = allowlist; `disallowedTools` wins when both set; no documented mechanism EXTENDS a shipped agent's list from another file — hence the server splice, not a second file.
- **PreToolUse deny** (docs, `/hooks`): `permissionDecision: deny` applies to `Edit`/`Write` and fires before permission modes, including bypass; `tool_input.file_path` is absolute for Read/Edit/Write. `MultiEdit`/`NotebookEdit` field names to be measured in the fixture (memory: NotebookEdit uses `notebook_path`).

## The model

### 1. Files and ownership

| File | Class | Owner | Sync behaviour |
|---|---|---|---|
| `CLAUDE.md` | template | template | overwritten on every update; any consumer diff outside the import line is `CONFLICT` and the sync REFUSES to apply until resolved (never "keep mine") |
| `.claude/project-instructions.md` | once | project | seeded at bootstrap/migration, never overwritten; `template_notes_changed` audit as for other once-class files |
| `.claude/agent-grants.json` | once | project | seeded empty at bootstrap; read by the server at every agent apply |
| `.claude/agents/*.md` | template | template | stored hash = the SPLICED template content (template + grants); a diff confined to the spliced `tools:` additions or to the agent's own PROJECT-CUSTOM region (kept, as in v3 — see H1 in §5) is IDENTICAL; anything else LOCAL_EDITED |
| `.claude/rules/project.md` | once | project | unchanged (v4.0.2 seed) |

The PROJECT-CUSTOM region is REMOVED from the template `CLAUDE.md` (all six variants) — and ONLY there. **Measured on main `7f9634e` (2026-09-19): 53 template files carry the markers — 6 `CLAUDE.md`, 6 `AGENT_TEAM.md`, 41 `.claude/agents/*.md` (v2.1.2, cf15dcc).** Decision 1 scopes this release to `CLAUDE.md`, so the 47 other regions are unchanged under manifest v4 and every region instrument (`region.sh`, the `region_bytes` field, the `region_markers` verify line, the per-file flags, `is_empty`, the server's region-tolerant status) stays LIVE for them; for `CLAUDE.md` those instruments serve the v3→v4 migration path only. Retiring the 47 is a v4.2 decision with its own spec, never a side effect of this one.

### 2. The template `CLAUDE.md` tail (all six variants, byte-identical across consumers of a variant)

```
Project-specific instructions live in the imported file below; where the two conflict, that file wins.
<!-- Editing note: write to .claude/project-instructions.md, never to this file -- the sync owns it,
     an editing hook refuses Edit/Write here, and the next sync overwrites it. -->
@.claude/project-instructions.md
```

The precedence sentence is PLAIN PROSE addressed to the model (the documented mitigation for the absence of a hard rule); only the editing note is an HTML comment addressed to the editor (reviewer: an instruction inside a comment reads as an editing note, not as an instruction). The `@` line is the last line of the file. The block carries no placeholder and is not region content (there is no region). **Bytes (reviewer D2, measured on v4.0.2):** the region block that leaves is 192 B (BEGIN 91 + inner hint 73 + END 28, identical in all six variants) plus the lines 3–4 blockquote (151 B: "Project-specific hard rules live in the PROJECT-CUSTOM region below — read it first." and the rationale pointer — both point at a region that no longer exists); the tail block that enters is **320 B** as written above (re-measured with `wc -c` after the plain-prose rewrite — the first draft's 4-line block was 325 B, the rewrite grew to 389 B before the redundant "picked up at the next session start" sentence was dropped, since §3's seed header already states it — two copies, one truth; reviewer G3 re-measured the final block at 320, not 321); and the plan's ruling R-F KEEPS the comment line above the region (`templates/*/CLAUDE.md:123`, the only carrier of the `context-mode` sentinel check 37 asserts) and rewrites it to point at the instructions file (124 → 132 B, +8), while Task 3 also drops the blank line after lines 3–4 (−1); so out = 192 + 151 + 1 = 344 B, in = 320 + 8 = 328 B, net **−16 B**, headroom after the change **17–25 B** per variant (java 6119 · dotnet-maui/python 6123 · dotnet 6124 · rust-tauri 6125 · general 6127 against `BUDGET_CLAUDE_MD` 6144) — **derived figures, the third revision of this sentence (reviewer P3); the MEASURED record is Task 3's report (`task-3-report.md`, plan constraint 10), which supersedes this sentence wherever they differ.** The plan re-derives these with `wc -c` (or `LC_ALL=C awk`), never a locale-dependent `length()`, and any later edit to the block re-measures before it lands.

### 3. `.claude/project-instructions.md` seed (once-class)

Header (two paragraphs): (1) this file is imported at the end of `CLAUDE.md` and overrides it where they conflict; loaded at session start, always on; a new or edited version is picked up at the NEXT session start; (2) what belongs here — project rules, routing blocks (context-mode and similar), the MCP servers this project relies on (name, purpose, main-thread only — the v4.0.2 item 3 guidance, relocated here by v4.0.3 ruling R1), and nothing that duplicates a `paths:`-scoped rules file. Body: empty at bootstrap; at migration, the former PROJECT-CUSTOM region body verbatim.

### 4. `.claude/agent-grants.json` (once-class)

```json
{
  "schema": 1,
  "grants": {
    "Explore":   ["mcp__glider__symbol_lookup", "mcp__glider__decompile"],
    "architect": ["mcp__glider__symbol_lookup"]
  }
}
```

Rules: agent names are the shipped agents' `name:` values (a name that no shipped agent carries is refused by the sync with the list of shipped names); tool names are full `mcp__<alias>__<tool>` tokens; the file is LF, keys sorted by the server on every write it performs (it performs none in v4.1 — the consumer edits it; the server only reads). Check 50's census applies to grants on the TOOLKIT side (fixtures) and `template_verify` gains `agent_grants_resolvable` on the consumer side: every granted token must exist in the installed servers' exports (the v4.0.1 `list-mcp-tools.py` route), else FAIL — a typo must never silently grant nothing. Grants EXTEND `tools:` only; they cannot remove a tool, cannot touch `disallowedTools`, and cannot add `Agent`, the `template_*` sync tools, or the merge/PR tools the template withholds from coders. `UNGRANTABLE_TOOLS` is a HAND-WRITTEN literal (the decision), and the test asserts `union(withheld sets of every shipped agent) ⊆ UNGRANTABLE_TOOLS` — `⊆`, not `==`, so a deliberately grantable tool stays grantable, and never derived from the withheld sets (that would be the data equalling itself — reviewer).

### 5. Server splice (`template_apply_file` and `compute_status_v3` → v4)

- **Injection point (reviewer D3):** the splice enters whatever PRODUCES `tpl_replaced` for `.claude/agents/*` paths (the single place `compute_status_v3`, `template_apply_file` and `template_get_diff` all read the "template as it applies to this project"), not the two tool call sites — otherwise `_status_for_template_entry` compares the spliced stored hash against the BARE template and every grants-carrying agent reads `TEMPLATE_UPDATED` forever. With one injection point, `local_diff = _unified(tpl_replaced, proj_content)` shows only the real deviation for free. **Measured (2026-09-19, whole-file `grep -n '_apply_placeholders('` over the package, definition excluded): TEN call sites produce placeholder-rendered template content today** — `v3.py`: `resolve_base` (`:933`, the base provider), `compute_status_v3` (`:955`), `apply_file_v3` (`:1093`), **`finalize_v3` (`:1250`) and `migrate_v2_to_v3` (`:1503`) — the two STORED-HASH WRITERS**; `mcp.py`: `template_compute_status` (`:1073`, the v2 path), `template_get_diff` (`:1252`, `:1265`), `template_apply_file` (`:1418`), `template_finalize_sync` (`:1662`). (An earlier draft counted eight; its grep was keyed on the `tpl_replaced =` variable, a window that hid the two writers — reviewer H2.) **The rule is an invariant, not a count: the helper is the ONLY caller of `_apply_placeholders` outside its own body, and the test asserts zero call sites elsewhere, so a producer added later fails on arrival rather than against a stale constant.** The stored-hash writers matter most: `finalize_v3` runs at the end of every sync and computes the manifest baseline — computed un-spliced while apply writes the disk file spliced, every grants-carrying agent reads `TEMPLATE_UPDATED` permanently, and all four witnesses below pass anyway because they start from an apply whose hash the same un-spliced path wrote (the D3 failure arriving through the writer instead of the comparator). The base provider matters next — un-spliced, a consumer whose template moved on compares an un-spliced base part against a spliced project part and reads LOCAL_EDITED. The v3→v4 migration (§7 step 1c) is modelled on `migrate_v2_to_v3` and inherits the rule: every hash it writes comes from the helper. Witness for the writer: after apply + finalize, a status call with nothing changed reads `IDENTICAL` (already witness two) AND the manifest entry's hash equals `sha256` of the on-disk file's spliced template content — asserted against the file, not against the helper's return value. **H1 (reviewer, after the region count):** the 41 agents KEEP their PROJECT-CUSTOM region under v4 (§1), and the region-tolerant status already exists — `region_status` (`v3.py:880-904`) splits both sides with `_split_custom_region`, compares template PARTS (falling back to the held base's part), then decides `IDENTICAL`/`TEMPLATE_UPDATED` by `sha256(tpl_replaced)` against the stored hash. So the stored hash is the hash of the spliced TEMPLATE content (what apply writes: template part + grants + the template's empty region), the consumer's region prose lives outside the compared part, and the splice enters upstream of `_split_custom_region` by construction because it lives in the producer. Witnesses (four; the third is the one that can fail under the broken wiring, the fourth under a splice placed downstream of the split): apply → `IDENTICAL`; a second status call with nothing changed → still `IDENTICAL`; `TEMPLATE_UPDATED` appears ONLY after a grants edit; an agent with BOTH grants and consumer prose in its region → `IDENTICAL`, and with grants, region prose AND a template part edit → `LOCAL_EDITED` whose `local_diff` shows only the part edit.
- Apply: for a template-class file under `.claude/agents/`, after placeholder substitution the server parses the frontmatter `tools:` line (a comma-separated list on ONE line — no list form, no wildcard; a consistency check asserts every shipped agent has exactly one such line), appends the grants for that agent name (deduplicated, original order then grant order), and writes the result; the manifest hash is the sha256 of the WRITTEN content (full-content hashing, as the region reclassification rule established — never a template-part hash). **An agent with no `tools:` line inherits every tool including MCP, so a grant for it has nothing to extend:** the splice REFUSES such a grant by name ("<agent> ships no `tools:` line and already inherits every tool — remove the grant"), never synthesises an allowlist (that would convert inherit-everything into a narrowed list — a grant that subtracts). **Premise corrected (2026-09-19):** D1 as first reported said five language coders ship no `tools:` line; that was an instrument error (a 20-line `sed` window; their `tools:` sits on line 26). Measured whole-file at `39135e7`, `5e46c52` and `7f9634e`: 41 shipped agents, 41 one-line `tools:`, 0 list forms, 0 wildcards, 0 without. So no shipped agent can trip the refusal today; the rule stays as defence-in-depth and is witnessed with a FIXTURE agent that ships no `tools:` line (a fixture can carry the case no shipped agent may). `template_verify`'s `agent_grants_extendable` line covers this refusal as a FAIL (a separate predicate from `agent_grants_names_known`, which only asks whether the name is a shipped agent — folding the two would pass for exactly the failing case). No shipped agent's `tools:` line is added, removed or reshaped by this release.
- Status (region-aware, H1): an agent whose on-disk TEMPLATE PART equals the spliced template part (its own region prose tolerated, as in v3) is IDENTICAL; whose part equals the BARE template part while grants exist for it → `TEMPLATE_UPDATED` (the grants were added after the last apply; the stored hash no longer equals `sha256(tpl_replaced)`); anything else → LOCAL_EDITED with `local_diff` computed against template+grants, so the diff shows only the real deviation.
- `get_diff` for an agent shows three-way base = template+grants.
- Capability `agent_grants` with a behavioural witness (a grants file + an agent → spliced content, IDENTICAL status, `local_diff` empty).

### 6. Enforcement

- `hooks/deny-claude-md-writes.sh` (PreToolUse, matcher `Edit|Write|MultiEdit|NotebookEdit`): denies when `tool_input.file_path` (or the tool's path field) resolves to `<project root>/CLAUDE.md` AND **a manifest v4 exists at that root** (`.claude/template-manifest.json` with `manifest_version == 4`) — the predicate is the thing meant, not a proxy (reviewer D4: "checks for `templates/ownership.json`" was a proxy of the gate-directory-listing kind; a v4-manifest predicate needs no toolkit exemption because the toolkit root carries no consumer manifest, and no-manifest / v3 repos are allowed by construction). **Registration scope: project-level only** — registered in every variant's `settings.json`; the hook is NOT mirrored into `user-level-reference/hooks/` and never registered in `~/.claude/settings.json` (unlike `deny-secret-reads.sh`, whose user-level precedent is exactly why this must be stated: a user-level deny would refuse `CLAUDE.md` writes in every non-consumer repo on the machine). `HOOKS_NO_MIRROR` lists it with that reason. Message names `.claude/project-instructions.md` as the place to write. Rows: deny on a v4 consumer's path; allow on any other file; allow in a repo with no manifest and in a v3 repo; allow in the toolkit root; deny survives `bypassPermissions` (documented; pinned by a row that sets the permission mode field in the payload). **Scope (reviewer D5):** the matcher covers the editing tools only; a Bash write (`sed -i`, `>>`, a heredoc) bypasses it — a guardrail, not a boundary; stated in Non-goals and in the template text (§2), never described as "refuses writes".
- `template_verify` lines: `claude_md_identical` (consumer `CLAUDE.md` == variant template after placeholders; FAIL with the diff summary), `import_line_present` (last line is the `@` line) — **scoped to the v3-manifest window only** (§7): under manifest v4 it cannot fail independently of `claude_md_identical` (an identical file ends with the `@` line by the toolkit-side check), so under v4 its status is **SKIP with reason "manifest v4: owned by claude_md_identical"** (it sits in `skip_ids` under v4 and in neither exact set inside the window — reviewer G2: a line whose status is unstated is a line the partition cannot enumerate); in the window, where `claude_md_identical` does not apply, it FAILs on its own (reviewer F5, the acceptance rule applied to the spec's own lines), `instructions_file_present` (once-class file exists; FAIL — an import to a missing file is silently ignored by the harness, which is the "unversioned import" hazard; genuinely independent: a hand deletion), `agent_grants_resolvable` (above), `agent_grants_names_known` (every grant key names a shipped agent — unknown names only), **`agent_grants_extendable`** (a grant key names a shipped agent that ships NO `tools:` line — FAIL naming the agent; the apply's refusal and the verify line answer the same question, one predicate each — reviewer F4: folding both into `names_known` would pass for the failing case). `region_markers` (the one `region_*` verify line) is UNCHANGED under v4: it measures malformed markers (`verify.py:475-481`), not presence, and 47 of a consumer's template-class files keep their region (§1) — a well-formed marker pair reappearing in a v4 consumer's `CLAUDE.md` is owned by `claude_md_identical`, so nothing is lost by not skipping and a real malformed pair in an agent is still caught.
- Consistency (toolkit): every variant `CLAUDE.md` ends with the `@` line; the tail block is byte-identical across variants; no `PROJECT-CUSTOM` marker survives in any variant `CLAUDE.md` (scoped: the 47 `AGENT_TEAM.md`/agent regions are unchanged, §1 — an unscoped "anywhere in `templates/`" would read as an instruction to strip 47 files); every shipped agent has exactly one one-line `tools:` (no list form, no wildcard; measured 41/41 — an "OR none" arm, which F2 first asked for on the false D1 premise, would wave through a future agent that inherits every tool including the merge/PR tools the template withholds from coders, so the check makes that an explicit red rather than a silent escalation, and the splice's refusal rule is the defence-in-depth behind it); `union(withheld sets) ⊆ UNGRANTABLE_TOOLS`.

### 7. Sync skill (v4.1.0)

- Floor: `requires_skill >=v4.1.0`; the server refuses a v4.0.x skill body on a v4 manifest with the restart instruction; `MIN_SERVER_FOR_V4` refuses a v3-era server before migration (the manifest's `requires_server` is bumped by migration).
- **The v3-manifest window (reviewer ruling, accepted):** a v4.1 server serving a consumer whose manifest is still v3 is the mirror of v4.0's "door one" — `MIN_SERVER_FOR_V4` refuses an OLD server on a NEW manifest, but a pre-migration `requires_server >=0.3.2` is satisfied by 4.1.0, so nothing stops the new server applying a region-less template `CLAUDE.md` over a v3 consumer whose project content still lives in the region. Rule: while `manifest_version == 3`, `template_apply_file` REFUSES `CLAUDE.md` specifically with "migrate first (`template_migrate_manifest`, dry-run then `backup_dir`)"; `compute_status_v3` reports it as `MIGRATION_REQUIRED` for that path — **a NEW template-class status, which is a contract change against v4.0.3 item 10's CLOSED partition** (`verify.TEMPLATE_CLASS_STATUSES`; an unenumerated status fails `classes_and_hashes` BY NAME — reviewer F3): Task 1 adds `MIGRATION_REQUIRED` to the tuple deliberately, with a witness that a v3-window consumer's `classes_and_hashes` PASSES while `CLAUDE.md` reads `MIGRATION_REQUIRED`, and `status_clean` reports the path with the migrate-first remedy. Concretely for the plan: the six new verify ids (§6: `claude_md_identical`, `import_line_present`, `instructions_file_present`, `agent_grants_resolvable`, `agent_grants_names_known`, `agent_grants_extendable`) grow `LINES` from 24 to 30, and BOTH exact sets move in Task 1 — the skip set gains `import_line_present` under v4 and nothing else (`region_markers`, the only `region_*` id in `LINES`, keeps PASSing on the green v4 fixture — it measures the 47 regioned files; `region_bytes` is a field, `region_bytes_raw` a capability, `region_orphaned`/`region_markers_malformed` per-file flags — reviewer, measured on the v4.0.3 tuple; the earlier phrase that put `region_markers` in the skip set rested on the six-file premise), the info set is re-enumerated — so the count assertion and the two set assertions are red before the lines exist and green after, never adjusted afterwards to match; every other file applies as under v3. Step 1's "sync first" therefore means: sync everything except `CLAUDE.md`, then migrate, then `CLAUDE.md` applies under the v4 rules. Witness: a v3 fixture + the v4.1 template → apply of `CLAUDE.md` refused with that message, the region body intact byte-for-byte; after migration → applied, `claude_md_identical` PASS.

### 9. Migration per consumer (downstream list, final wording decided at release)

0. Restart the server; `server_commit == rev-parse HEAD`; `registered_tools` includes `template_migrate_manifest`.
1. Sync on the branch where the CURRENT region lives (MM-Agent: its session branch); dry-run first; read (a)/(b)/(c).
2. Resolve every (c) diff by moving the text into the region BEFORE migrating (the migration refuses otherwise).
3. Migrate with `backup_dir`; the sync applies the template `CLAUDE.md` and the agents.
4. Restart the session (session-start delivery) before trusting the new instructions.
5. Expected verify lines per mode; the two MM-Agent agents read IDENTICAL.

## Non-goals

- Retiring the 47 `AGENT_TEAM.md`/agent PROJECT-CUSTOM regions, `region.sh` and the region verify lines (v4.2, after every consumer is on v4 and with its own spec — §1).
- A version floor against mcp-dev-servers (still dropped).

- Nested `CLAUDE.md` files in subdirectories (unchanged, project-owned as today).
- Intercepting Bash writes to `CLAUDE.md` (`sed -i`, `>>`, heredocs): the deny hook covers the editing tools only. A Bash matcher would repeat the `GC_GIT_PRE` cost for a guardrail; the sync's `claude_md_identical` FAIL line and the next sync's overwrite are the boundary.

## Decisions taken (user, 2026-09-18)

1. The deny hook covers `CLAUDE.md` only this release; `AGENT_TEAM.md` and `.claude/settings.json` stay hand-editable (their edits keep surfacing as LOCAL_EDITED on sync; a project-owned extension for `settings.json` hooks is a v4.2 candidate).
2. Manifest **v4**: a v3-era server refuses a v4 manifest loudly rather than applying the new template `CLAUDE.md` over a consumer whose region content has moved out.
