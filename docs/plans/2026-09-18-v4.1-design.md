# v4.1 — option B: template-owned `CLAUDE.md`, project-owned instructions and agent grants (design spec)

**Status:** spec draft, 2026-09-18. Kept separate from v4.0.3 (which lands on main first); implementation branch `v4/1` is cut from main after v4.0.3's release commit.
**Decision of record:** 2026-09-12 (v4.0 ledger, after challenge): v4.1 = option B — byte-identical template `CLAUDE.md` + `@.claude/project-instructions.md` (once-class), file-level ownership, a PreToolUse deny on consumer writes to `CLAUDE.md`, a precedence sentence in the template body, the `@` line at the END, sync refuses any consumer `CLAUDE.md` diff outside the import line, v2/v3-shape migration (dry-run, backup, move region content, refuse-not-guess), a recurring gate check because `@import` is unversioned, and the first legitimate skill-floor raise `>=4.1.0`. Options A (region + marker-parsing hook) and C (dual support) were rejected. **2026-09-18 (user):** agent tool grants are in scope via a server-spliced project-owned grants file.
**Version:** toolkit `4.1.0`, server `4.1.0`, `manifest_version` **4** (the manifest gains `instructions_file` and `agent_grants` declarations; a v3 server must not silently apply a v4 manifest), skill marker `v4.1.0`, `requires_skill >=v4.1.0` in `templates/ownership.json`, `MIN_SERVER_FOR_V4 = 4.1.0`.

## Goal

Every consumer's `CLAUDE.md` is byte-identical to its variant's template; project content lives in one project-owned file the template imports; per-agent project tool grants live in one project-owned file the server splices; a sync can therefore never conflict on `CLAUDE.md` or on a grant-only agent diff, and `template_verify` reports both as IDENTICAL.

## Spike results (measured before this draft)

- **(b) Delivery gate = session start, not HEAD.** In this session: an unscoped rules file present at session start but UNTRACKED (`zz-load-probe.md`) was delivered to a subagent; a rules file created mid-session was not delivered untracked, staged, or COMMITTED on a branch (three spawns, 2026-09-18). Consequence: every instruction file this release introduces or moves is "picked up at the next session start" — the migration step and the seeds say so, and no verify line may claim a mid-session effect.
- **(a) Precedence.** Documentation (search-snippet verified, `code.claude.com/docs/en/settings`, `/memory`): no hard precedence rule between memory sources; the documented mitigation is an explicit precedence sentence in the more specific file. `@path` resolves relative to the file containing the line; import chains are capped at four hops; code spans are skipped; the launch-time snapshot is cached until `/clear`, `/compact` or restart. Unscoped `.claude/rules/*.md` load at session start at CLAUDE.md priority; `paths:`-scoped ones load on matching reads (open issues report Write not triggering). Consequence: precedence is established by the template's own sentence (below), never assumed from position; the `@` line is last only so the project text is nearest the end of context.
- **Agent `tools:`** (docs, `/sub-agents`): omitted = inherit everything incl. MCP; `tools:` = allowlist; `disallowedTools` wins when both set; no documented mechanism EXTENDS a shipped agent's list from another file — hence the server splice, not a second file.
- **PreToolUse deny** (docs, `/hooks`): `permissionDecision: deny` applies to `Edit`/`Write` and fires before permission modes, including bypass; `tool_input.file_path` is absolute for Read/Edit/Write. `MultiEdit`/`NotebookEdit` field names to be measured in the fixture (memory: NotebookEdit uses `notebook_path`).

## The model

### 1. Files and ownership

| File | Class | Owner | Sync behaviour |
|---|---|---|---|
| `CLAUDE.md` | template | template | overwritten on every update; any consumer diff outside the import line is `CONFLICT` and the sync REFUSES to apply until resolved (never "keep mine") |
| `.claude/project-instructions.md` | once | project | seeded at bootstrap/migration, never overwritten; `template_notes_changed` audit as for other once-class files |
| `.claude/agent-grants.json` | once | project | seeded empty at bootstrap; read by the server at every agent apply |
| `.claude/agents/*.md` | template | template | stored hash = the SPLICED content (template + grants); a diff confined to the spliced `tools:` additions is IDENTICAL; anything else LOCAL_EDITED |
| `.claude/rules/project.md` | once | project | unchanged (v4.0.2 seed) |

The PROJECT-CUSTOM region is REMOVED from the template `CLAUDE.md` (all six variants); `region.sh`, `region_bytes`, `region_*` verify lines and the region capabilities stay in the codebase for the v3 migration path only and are retired in v4.2.

### 2. The template `CLAUDE.md` tail (all six variants, byte-identical across consumers of a variant)

```
Project-specific instructions live in the imported file below; where the two conflict, that file wins.
<!-- Editing note: write to .claude/project-instructions.md, never to this file -- the sync owns it,
     an editing hook refuses Edit/Write here, and the next sync overwrites it. Changes to either
     file are picked up at the next session start. -->
@.claude/project-instructions.md
```

The precedence sentence is PLAIN PROSE addressed to the model (the documented mitigation for the absence of a hard rule); only the editing note is an HTML comment addressed to the editor (reviewer: an instruction inside a comment reads as an editing note, not as an instruction). The `@` line is the last line of the file. The block carries no placeholder and is not region content (there is no region). **Bytes (reviewer D2, measured on v4.0.2):** the region block that leaves is 192 B (BEGIN 91 + inner hint 73 + END 28, identical in all six variants) plus the lines 3–4 blockquote (151 B: "Project-specific hard rules live in the PROJECT-CUSTOM region below — read it first." and the rationale pointer — both point at a region that no longer exists); the tail block that enters is ~325 B; net **−18 B**, headroom after the change **19–27 B** per variant (java 6117 · dotnet-maui/python 6121 · dotnet 6122 · rust-tauri 6123 · general 6125 against `BUDGET_CLAUDE_MD` 6144). The plan carries these numbers, not an expectation.

### 3. `.claude/project-instructions.md` seed (once-class)

Header (two paragraphs): (1) this file is imported at the end of `CLAUDE.md` and overrides it where they conflict; loaded at session start, always on; a new or edited version is picked up at the NEXT session start; (2) what belongs here — project rules, routing blocks (context-mode and similar), the MCP servers this project relies on (name, purpose, main-thread only — the v4.0.2 item 3 guidance, relocated here by v4.0.3 ruling R1), and nothing that duplicates a `paths:`-scoped rules file. Body: empty at bootstrap; at migration, the former PROJECT-CUSTOM region body verbatim.

### 4. `.claude/agent-grants.json` (once-class)

```json
{
  "schema": 1,
  "grants": {
    "Explore":   ["mcp__glider__symbol_lookup", "mcp__glider__decompile"],
    "architect": ["mcp__glider__symbol_lookup"]
  }
}
```

Rules: agent names are the shipped agents' `name:` values (a name that no shipped agent carries is refused by the sync with the list of shipped names); tool names are full `mcp__<alias>__<tool>` tokens; the file is LF, keys sorted by the server on every write it performs (it performs none in v4.1 — the consumer edits it; the server only reads). Check 50's census applies to grants on the TOOLKIT side (fixtures) and `template_verify` gains `agent_grants_resolvable` on the consumer side: every granted token must exist in the installed servers' exports (the v4.0.1 `list-mcp-tools.py` route), else FAIL — a typo must never silently grant nothing. Grants EXTEND `tools:` only; they cannot remove a tool, cannot touch `disallowedTools`, and cannot add `Agent`, the `template_*` sync tools, or the merge/PR tools the template withholds from coders. `UNGRANTABLE_TOOLS` is a HAND-WRITTEN literal (the decision), and the test asserts `union(withheld sets of every shipped agent) ⊆ UNGRANTABLE_TOOLS` — `⊆`, not `==`, so a deliberately grantable tool stays grantable, and never derived from the withheld sets (that would be the data equalling itself — reviewer).

### 5. Server splice (`template_apply_file` and `compute_status_v3` → v4)

- **Injection point (reviewer D3):** the splice enters whatever PRODUCES `tpl_replaced` for `.claude/agents/*` paths (the single place `compute_status_v3`, `template_apply_file` and `template_get_diff` all read the "template as it applies to this project"), not the two tool call sites — otherwise `_status_for_template_entry` compares the spliced stored hash against the BARE template and every grants-carrying agent reads `TEMPLATE_UPDATED` forever. With one injection point, `local_diff = _unified(tpl_replaced, proj_content)` shows only the real deviation for free. Witnesses (three, the third is the one that can fail under the broken wiring): apply → `IDENTICAL`; a second status call with nothing changed → still `IDENTICAL`; `TEMPLATE_UPDATED` appears ONLY after a grants edit.
- Apply: for a template-class file under `.claude/agents/`, after placeholder substitution the server parses the frontmatter `tools:` line (a comma-separated list on ONE line — no list form, no wildcard; a consistency check asserts every shipped agent has either exactly one such line or NO `tools:` line at all), appends the grants for that agent name (deduplicated, original order then grant order), and writes the result; the manifest hash is the sha256 of the WRITTEN content (full-content hashing, as the region reclassification rule established — never a template-part hash). **Agents with no `tools:` line (reviewer D1 — measured: `dotnet-coder` ×2, `java-coder`, `python-coder`, `rust-coder`; five of six variants) inherit every tool including MCP, so a grant for them has nothing to extend:** the splice REFUSES such a grant by name ("<agent> ships no `tools:` line and already inherits every tool — remove the grant"), never synthesises an allowlist (that would convert inherit-everything into a narrowed list — a grant that subtracts). `template_verify`'s `agent_grants_names_known` covers this refusal as a FAIL line. Whether those five coders should GAIN a `tools:` line is a separate decision with its own diff, not a side effect of making the splice parseable (out of scope here).
- Status: an agent whose on-disk content equals template+grants is IDENTICAL; equals the bare template while grants exist for it → `TEMPLATE_UPDATED` (the grants were added after the last apply); anything else → LOCAL_EDITED with `local_diff` computed against template+grants, so the diff shows only the real deviation.
- `get_diff` for an agent shows three-way base = template+grants.
- Capability `agent_grants` with a behavioural witness (a grants file + an agent → spliced content, IDENTICAL status, `local_diff` empty).

### 6. Enforcement

- `hooks/deny-claude-md-writes.sh` (PreToolUse, matcher `Edit|Write|MultiEdit|NotebookEdit`): denies when `tool_input.file_path` (or the tool's path field) resolves to `<project root>/CLAUDE.md` AND **a manifest v4 exists at that root** (`.claude/template-manifest.json` with `manifest_version == 4`) — the predicate is the thing meant, not a proxy (reviewer D4: "checks for `templates/ownership.json`" was a proxy of the gate-directory-listing kind; a v4-manifest predicate needs no toolkit exemption because the toolkit root carries no consumer manifest, and no-manifest / v3 repos are allowed by construction). **Registration scope: project-level only** — registered in every variant's `settings.json`; the hook is NOT mirrored into `user-level-reference/hooks/` and never registered in `~/.claude/settings.json` (unlike `deny-secret-reads.sh`, whose user-level precedent is exactly why this must be stated: a user-level deny would refuse `CLAUDE.md` writes in every non-consumer repo on the machine). `HOOKS_NO_MIRROR` lists it with that reason. Message names `.claude/project-instructions.md` as the place to write. Rows: deny on a v4 consumer's path; allow on any other file; allow in a repo with no manifest and in a v3 repo; allow in the toolkit root; deny survives `bypassPermissions` (documented; pinned by a row that sets the permission mode field in the payload). **Scope (reviewer D5):** the matcher covers the editing tools only; a Bash write (`sed -i`, `>>`, a heredoc) bypasses it — a guardrail, not a boundary; stated in Non-goals and in the template text (§2), never described as "refuses writes".
- `template_verify` lines: `claude_md_identical` (consumer `CLAUDE.md` == variant template after placeholders; FAIL with the diff summary), `import_line_present` (last line is the `@` line; FAIL), `instructions_file_present` (once-class file exists; FAIL — an import to a missing file is silently ignored by the harness, which is the "unversioned import" hazard), `agent_grants_resolvable` (above), `agent_grants_names_known` (every grant key names a shipped agent). `region_*` lines SKIP with reason "no region under manifest v4".
- Consistency (toolkit): every variant `CLAUDE.md` ends with the `@` line; the tail block is byte-identical across variants; no `PROJECT-CUSTOM` marker survives anywhere in `templates/`; every shipped agent has a one-line `tools:`; `UNGRANTABLE_TOOLS` covers every tool withheld from every coder.

### 7. Sync skill (v4.1.0)

- Floor: `requires_skill >=v4.1.0`; the server refuses a v4.0.x skill body on a v4 manifest with the restart instruction; `MIN_SERVER_FOR_V4` refuses a v3-era server before migration (the manifest's `requires_server` is bumped by migration).
- **The v3-manifest window (reviewer ruling, accepted):** a v4.1 server serving a consumer whose manifest is still v3 is the mirror of v4.0's "door one" — `MIN_SERVER_FOR_V4` refuses an OLD server on a NEW manifest, but a pre-migration `requires_server >=0.3.2` is satisfied by 4.1.0, so nothing stops the new server applying a region-less template `CLAUDE.md` over a v3 consumer whose project content still lives in the region. Rule: while `manifest_version == 3`, `template_apply_file` REFUSES `CLAUDE.md` specifically with "migrate first (`template_migrate_manifest`, dry-run then `backup_dir`)"; `compute_status_v3` reports it as `MIGRATION_REQUIRED` for that path; every other file applies as under v3. Step 1's "sync first" therefore means: sync everything except `CLAUDE.md`, then migrate, then `CLAUDE.md` applies under the v4 rules. Witness: a v3 fixture + the v4.1 template → apply of `CLAUDE.md` refused with that message, the region body intact byte-for-byte; after migration → applied, `claude_md_identical` PASS.
- Step 1c: `template_migrate_manifest` v3 → v4: dry-run lists (a) the region body that will move to `project-instructions.md`, (b) every LOCAL_EDITED agent whose diff is confined to `tools:` additions and the grants entry it will write, (c) every other `CLAUDE.md` diff outside the region — which is a REFUSAL with the diff, never a guess; `backup_dir` required; writes: `project-instructions.md` (seed header + region body verbatim), `agent-grants.json` (from (b)), `CLAUDE.md` (template), manifest v4 (`instructions_file`, `agent_grants`, `requires_server >=4.1.0`). The migration report is written to `backup_dir` (not in-repo, per v4.0.1 item 14).
- Step 3/4/5: no CLAUDE.md keep-mine route exists; the only project surfaces are the two once-class files; steps say "picked up at the next session start".
- Step 6b: a grants entry replaces the "rename the agent" route for grant-shaped agent diffs; other agent diffs keep the v4.0.2 rules.
- Step 8/9b: the new verify lines; expected lines per mode.

### 8. Bootstrap (`setup-project.sh`/`.ps1`)

Writes the two once-class seeds, registers the deny hook, writes manifest v4 directly (no migration for new projects). The `test-setup-project.sh` fixtures assert: `CLAUDE.md` byte-identical to the variant template after placeholders, both seeds present, `agent-grants.json` = `{"schema":1,"grants":{}}`, the last line of `CLAUDE.md` is the `@` line.

### 9. Migration per consumer (downstream list, final wording decided at release)

0. Restart the server; `server_commit == rev-parse HEAD`; `registered_tools` includes `template_migrate_manifest`.
1. Sync on the branch where the CURRENT region lives (MM-Agent: its session branch); dry-run first; read (a)/(b)/(c).
2. Resolve every (c) diff by moving the text into the region BEFORE migrating (the migration refuses otherwise).
3. Migrate with `backup_dir`; the sync applies the template `CLAUDE.md` and the agents.
4. Restart the session (session-start delivery) before trusting the new instructions.
5. Expected verify lines per mode; the two MM-Agent agents read IDENTICAL.

## Non-goals

- Retiring `region.sh` and the region verify lines (v4.2, after every consumer is on v4).
- A version floor against mcp-dev-servers (still dropped).
- Grants that REMOVE tools or touch `disallowedTools`.
- Nested `CLAUDE.md` files in subdirectories (unchanged, project-owned as today).
- Intercepting Bash writes to `CLAUDE.md` (`sed -i`, `>>`, heredocs): the deny hook covers the editing tools only. A Bash matcher would repeat the `GC_GIT_PRE` cost for a guardrail; the sync's `claude_md_identical` FAIL line and the next sync's overwrite are the boundary.

## Decisions taken (user, 2026-09-18)

1. The deny hook covers `CLAUDE.md` only this release; `AGENT_TEAM.md` and `.claude/settings.json` stay hand-editable (their edits keep surfacing as LOCAL_EDITED on sync; a project-owned extension for `settings.json` hooks is a v4.2 candidate).
2. Manifest **v4**: a v3-era server refuses a v4 manifest loudly rather than applying the new template `CLAUDE.md` over a consumer whose region content has moved out.

## What the region's removal touches (one decision, not five discoveries — reviewer)

The region is not only WHERE project content lived; it is WHAT several v4.0.x instruments measure. Each gets a stated verdict for the absent case, on manifest v4:

| Instrument | Today | Under v4 (no region in the template `CLAUDE.md`) |
|---|---|---|
| `region_markers` verify line | FAIL on malformed markers | SKIP with reason "manifest v4: no region" — NOT "n/a": a consumer `CLAUDE.md` carrying markers is a `claude_md_identical` FAIL, which is the line that owns it |
| `region_bytes` field / `region_bytes_raw` capability / `region.sh --bytes` | raw span | field absent on v4 manifests; the capability name stays (permanent) with its witness running against a v3 fixture; `region.sh` unchanged for the migration path |
| `region_orphaned`, `region_markers_malformed` (compute_status per-file flags) | present only in the hazardous case | never set on v4 (no markers expected); a marker found in a v4 consumer `CLAUDE.md` is reported through `claude_md_identical` |
| `is_empty()` single-placeholder classifier (`region.sh`) | decides EMPTY/CONTENT for check 31 arm A and step 6a | used by the v3→v4 migration only (an EMPTY region migrates to an empty `project-instructions.md` body; CONTENT moves verbatim); check 31 arm A is retargeted to "no marker in any variant `CLAUDE.md`" |
| `gate_self_reference` | region-independent | unchanged |
| `project_md_scoped_consistent` / `project_md_seed_current` | region-independent | unchanged |
| the v4.0.2 item 3 seed line | blocked by budget + classifier | lands in the `project-instructions.md` seed header (§3), outside the `CLAUDE.md` budget |
| `BUDGET_CLAUDE_MD` (check 35) | 6144, headroom 1–9 B | out: the 192 B region block + the 151 B lines 3–4 blockquote (both reference a region that no longer exists); in: the ~325 B tail block (§2); net −18 B; headroom 19–27 B per variant (numbers in §2, measured by the reviewer); the budget stays 6144 |

## Ordering (draft, to become the plan after the questions)

1. Server: manifest v4 + migration + splice + verify lines + capabilities.
2. Templates: `CLAUDE.md` ×6 tail block and region removal; seeds; agents' one-line `tools:`; `settings.json` hook registration; consistency checks; setup scripts.
3. Hooks: `deny-claude-md-writes.sh` + rows.
4. Skill v4.1.0 + docs.
5. Release + one canary consumer (penumbra volunteered as a consumer for v4.0.3/v4.1; MM-Agent is the grants fixture).

## Risks

- The `@import` is unversioned and silently ignored when the target is missing: `instructions_file_present` is a FAIL line and the seed is once-class, so a consumer cannot lose the file to a sync; deletion by hand shows up at the next verify.
- Session-start delivery means a migrated consumer runs one session on the old instructions after migrating; step 4 says restart.
- Full-content hashing of spliced agents means a grants edit alone flips the agent to `TEMPLATE_UPDATED` until re-applied — by design (the sync re-applies; the consumer never hand-edits the agent).
