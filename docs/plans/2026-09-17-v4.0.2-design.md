**Version:** toolkit `4.0.2`, server `4.0.2`, skill marker `v4.0.2`. `manifest_version` stays **3** (the one new manifest key, `deletedAcknowledged`, is already on disk in the installed base and preserved by every v3 server). `MIN_SERVER_FOR_V3` stays `0.3.2`; no floor raise (item 24 of v4.0.1 stays dropped — the user did not overrule).

## Goal

Close every defect and every doc contradiction the v4.0.1 rollout surfaced, at its source, with a test that was red first. One real `template_verify` defect (item 15) goes first because it FAILs a correct sync. No behaviour change for a consumer that does not sync, except that a restarted server now reports an identity and a capability list that cannot disagree with its tool registry (item 5).

## Non-goals

- Option B (template CLAUDE.md byte-identical + project-owned extension; per-agent `tools:` grants — MM-Agent's two LOCAL_EDITED agents are the design case) — v4.1, separate spec.
- A version floor against mcp-dev-servers (v4.0.1 item 24) — stays dropped.
- The rules-file load-order/precedence spike and the HEAD-vs-session-start delivery gate (panoscribe's measurement) — v4.1 spike input; item 12 here only states the measured fact.

## Global constraints (bind every task)

1. Every PR and every fix is reviewed by an outside session (`mcp-dev-servers-update-cc-template`) at the exact sha in a detached worktree (constraint 13). Task PRs stack onto the integration branch `v4/0.2`, true merges (`--merge`), no rebases (R11); the release PR merges `v4/0.2 → main`, then the tag goes on the merge commit.
2. All toolkit commits happen in worktrees; the gate runs in the detached gate worktree with its own venv (`bash server/install.sh` once there). The LIVE checkout's `server/.venv` is installed only after every session's server has released the exe (R27); until then the live `test_version.py` shows one red whose message names the remedy.
3. Gate: `bash scripts/verify-template-consistency.sh && bash scripts/test-hooks.sh && bash scripts/test-server.sh`, run as `bash hooks/run-gate.sh > <log> 2>&1` — never piped (R14). Implementers run the suites their task touches; the controller runs the full gate at merge time.
4. Every file LF; no counts in `CLAUDE.md`; byte-identical variant files edited in `templates/general/` then copied.
5. Every fix ships with the test that fails without it; a check, fixture or verify line is two-sided.
6. Expectations are derived, never hard-coded: keys from the consumer's own variant, commit from the template repo HEAD, tool names from the live registry.
7. **A check's passing output must be distinguishable from its null case** (v4.0.1 constraint 9): SKIP in-band with a reason; a list non-empty on every healthy consumer is never a FAIL line.
8. **Capabilities, not versions.** `test_template_sync_capabilities.py` pins the set EXACTLY; every new server surface a skill branches on gets a name and a behavioural witness; EXPECTED moves in the same PR. New names here: `deleted_acknowledged` (15) and `registered_tools` (5) — the two surfaces the skill branches on. New `template_verify` INFO lines (items 4, 7, 12) are NOT capabilities: no skill branches on them, and `verify.LINES` is their discoverable inventory (the `template_verify` witness already asserts `len(lines) == len(verify.LINES)`). Names are permanent — never split or rename the list.
9. **Second-instance rule** (memory `feedback_second_instance_and_failure_direction`): after fixing a pattern, grep the tree for its other copies and pin them together; a stale deny/allow fails OPEN and must go red.
10. An implementer who finds a stated defect already green stops and reports it instead of writing a test that was never red.
11. A release note never names a directory to delete — only files the release itself created (R28). A rollout notice never pins a sha; it states the rule (`server_commit == rev-parse HEAD`).
