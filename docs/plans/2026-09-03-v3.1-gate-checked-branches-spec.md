# Spec — `**Gate-checked branches**:` declaration (v3.1 candidate)

**Status:** spec only, not planned. Consumer-authored requirements from the one workflow
this serves (a worktree-based flow landing milestones on a session branch, then one PR).
Origin: finding 56 — the session-branch migration is not lossless; it relocates the gate
from per-merge to per-PR because a merge onto a non-protected branch is UNGATED, not
artifact-approved. This declaration is the lossless version.

## The line

```
- **Gate-checked branches**: m*-session-*
```

Sits directly under `**Protected branches**:` in `PROJECT_CONTEXT.md`. Same parsing
convention (space- or comma-separated), same discipline that no hook reads any other line.

## Requirements, in priority order

1. **A PATTERN, not a literal.** Session branches are dated (`m106-session-2026-09-02`) and
   a new one appears every few days. A literal goes stale on the first rollover, and a stale
   gate-checked list **fails open** — the worst way for it to fail. Glob is enough; regex is
   more than the other lines use and invites mistakes.

2. **Applies ONLY the artifact-freshness check, not the protected-branch refusals.** The
   session branch works as a landing route because it is *pushed* and a PR opened from it.
   If declaring it gate-checked also made `git push origin <session>` return 2, the
   declaration recreates the exact blocker the migration exists to escape. So: a merge onto
   a matching branch requires a fresh sha-matched `.gate/last-pass.json` exactly as `main`
   does today; pushes to it stay ungated.

3. **Absent line means no gate-checked branches** — fully backward compatible. But **an
   unfilled placeholder (`{{...}}`) must be REPORTED, not silently treated as absent**, the
   way the protected-branches line handles it. A consumer who templated the line and never
   filled it should hear about it on every sync rather than believe milestone merges are
   gated.

4. **Refusal text names the branch as gate-checked, not protected.** Today's messages say
   "protected branch"; on a session branch that sends the operator to the wrong config
   line. Shape:
   `BLOCKED: <branch> is gate-checked (PROJECT_CONTEXT.md **Gate-checked branches**); artifact sha X does not match HEAD Y`

## Explicitly NOT wanted

Inferring gate-checked status from the branch being upstream of a PR, or from any remote
state. Every defect this cycle came from a hook reading state the command could change or
a fixture could not reproduce. **A line in a file the hook already parses is the only
source that stays honest under both.**

## Fixture requirement — the strip-the-line control

The want-2 row for a gate-checked branch must go to 0 when the `**Gate-checked branches**:`
line is stripped, exactly like the Gate-field test. Otherwise a consumer cannot tell "gated
by my declaration" from "gated for some other reason" — and the declaration's whole
purpose is to be the reason. Vacuity closed both ways, as in the v3.0.2 pre-sync
verification.

## Acceptance, from the consumer

If v3.1 ships this, their migration note changes from "not lossless" to "lossless with one
line", and they run the same seven landing-route rows plus the strip-the-line control
before syncing.

## Coupling to check before planning

- `hooks/lib/git-cmd.sh` `gc_protected_branches` — the parser to mirror. Any change there
  obliges the parser matrix (`scripts/test-hooks-parser-matrix.sh`). Prefer a sibling
  function in `gate-before-merge.sh` if the matrix cost is not affordable in the release.
- `hooks/gate-before-merge.sh` — the artifact comparison is currently reached only via the
  protected-branch path; the gate-checked path must reach it WITHOUT passing through the
  A6 merge refusals.
- `templates/*/PROJECT_CONTEXT.md` ×6 and `setup-project.{sh,ps1}` placeholder handling.
- `scripts/verify-template-consistency.sh` placeholder-parity checks.
