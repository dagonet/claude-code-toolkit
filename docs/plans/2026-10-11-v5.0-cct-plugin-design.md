## 1. Structure and installation — APPROVED 2026-10-11

- **The toolkit repo becomes the plugin `cct`.**
  - It gets `.claude-plugin/plugin.json`, whose `version` always equals `VERSION` (a new consistency check). Without that bump, machines receive no update (F5).
  - The same repo is its own marketplace: `.claude-plugin/marketplace.json` with `source: "./"`.
- **One install per machine, at user scope:**
  - `/plugin marketplace add dagonet/claude-code-toolkit`, then `/plugin install cct@dagonet` (the marketplace is named `dagonet` in `marketplace.json`; a name with `claude` in it is avoided, F7).
  - It can be pinned to a release tag (`owner/repo#vX.Y.Z`).
  - Updates come with `claude plugin update`. Each installed version is about 7 MB.
- **Into the plugin:**
  - all agents in `agents/`, including the variant coders;
  - all skills in `skills/`;
  - the `pm-report` output style;
  - the hooks, which already live at the repo root in `hooks/`.
- **Stays outside the plugin:**
  - **Per project:** `CLAUDE.md`, rules, and `.claude/settings.json`. That file holds the permissions, enables the plugin, and carries the guard from §3.3. The native git pre-push hook also stays per project.
  - **Per machine:** the user's `~/.claude/CLAUDE.md`, the permission list and the autoMode entries (F7).
    - On Linux, `install-user-level-linux.sh` shrinks to just these.
    - On the PC, they stay a documented manual copy until part 3 (the mod) can deliver instructions.
  - **The toolkit checkout and its sync server**, unchanged.
- **Projects stop receiving** agent files and hook files through the sync. §3.4 covers the small set of files that stays.

## 2. Agents, skills, report style — APPROVED 2026-10-11

- **Names:** every agent is called `cct:<name>` (`cct:coder`, `cct:dotnet-coder`, `cct:tester`, `cct:Explore`, ...). `AGENT_TEAM.md`, the variant `CLAUDE.md` files, the user-level `CLAUDE.md` and the skills are rewritten to match. A new consistency check asserts that every agent name the docs mention exists in `agents/`.
- **Agent-frontmatter hooks move to plugin-wide hooks (F4):**
  - Today only the coder agents carry their own `gate-before-merge` hook.
  - The project settings already register that same check for every caller, so it is registered once, in the plugin.
- **Three hooks read an agent's own definition file:** `enforce-agent-contract`, `model-floor` and Jev.
  - They learn to read the plugin's `agents/` folder and to strip the `cct:` prefix.
  - Agents from other plugins and the built-ins are not toolkit agents, so these hooks let them pass.
- **Skills:** the user types `/cct:sync-template`, `/cct:commit` and so on. `sync-template` stays user-invoke-only (F2).
- **Report style:** moves into the plugin. Open, to check during the build: is a plugin's output style selected by its bare name or with the prefix?
- **Projects with their own agent extras:**
  - mm-agent's Explore and architect carry the glider tools. They become mm-agent's own project agent files, which the sync does not own.
  - The server's agent-grants mechanism is removed.
- **Old copies are removed on each machine:**
  - the six user-level agents, nine skills and the style;
  - the hook registrations in `~/.claude/settings.json`.
  - Otherwise there would be two coders and two sync skills. §3.2 makes it safe if hooks briefly exist twice.
  - On Linux the shrunk installer does this removal; on the PC, a documented list.

## 3. Hooks — APPROVED 2026-10-13

### 3.1 Two classes, one `hooks/hooks.json`

All hooks are registered in the plugin's `hooks/hooks.json`. Because the install is per user, they fire in **every** project on the machine. The hooks fall into two classes.

| Class | Hooks | Where they act |
|---|---|---|
| machine-wide (today registered at user level) | no-push-main, deny-secret-reads, deny-hang-shapes, model-floor, bash-output-guard, verify-hooks | every project |
| project-only (today registered only by the project settings) | pre-commit-test, gate-before-merge (Bash and the merge MCP tools), enforce-delegation, agent-budget-warn, deny-claude-md-writes, read-size-gate, post-edit-build, enforce-agent-contract, retro-ledger, retro-brief, now-brief | only in a **toolkit project** |

**The toolkit-project signal:** a project is a toolkit project when `$CLAUDE_PROJECT_DIR/.claude/template-manifest.json` exists.
- Every bootstrapped or synced project has that file, and it belongs to the sync.
- A project-only hook in any other project exits 0 at once, so a plain repo on the machine is not gated.
- This is one `[ -f ]` test at the top of the shared wrapper (§3.5), not in each hook.

### 3.2 Step-aside: one rule, reused

Today every user-level registration steps aside when the project's `.claude/settings.json` already registers the same `}/hooks/<name>.sh"`. The plugin keeps exactly that rule and adds one more file to check:

- **The project registers the hook:** the plugin's copy exits 0. That covers two cases:
  - **Self-hosting:** the toolkit repo keeps its own root `.claude/settings.json`, which registers its gates from the **working tree**. A change to a hook is then tested by the commit that makes it, never by the installed copy.
  - **Migration:** a project that has not been synced to v5.0 yet still registers its own hooks, so nothing fires twice.
- **`~/.claude/settings.json` registers the hook:** the plugin's copy exits 0. This covers a machine where the plugin is installed before the old user-level copies are removed, so the order of those two steps no longer matters.

The match is the same literal substring test as today, run against at most two small files that are read anyway. Nothing new is modelled.

### 3.3 The "plugin off" guard (fail closed)

Without the plugin, a toolkit project would have no protection at all (F3). Every synced project's `.claude/settings.json` therefore carries one inline guard. It is not a file:

- **The plugin's SessionStart hook** writes the marker `${TMPDIR:-/tmp}/cct-$UID/<session_id>`. It runs on every source: startup, resume, clear and compact.
- **The project's PreToolUse guard** has an **empty matcher**, so it applies to every tool: Bash, PowerShell, Edit, Write, Agent and every MCP tool.
  - It reads `session_id` from stdin with `grep -o` (no JSON parser needed).
  - It exits 2 when the marker is missing or the id cannot be read. The message: `BLOCKED: the cct plugin is not active in this session. Install it with /plugin marketplace add dagonet/claude-code-toolkit and /plugin install cct, then restart the session.`
- **Why PreToolUse alone is enough:** with every tool refused, nothing runs, so the plugin's missing PostToolUse and SubagentStop hooks have nothing to act on.
- **The same guard covers a plugin whose SessionStart hook cannot run**, for example a wrong path or a broken script: no marker, so the guard refuses. It does not cover a hook shell without `bash`, because the guard runs in that same shell (§3.5).
- **Cost:** one extra hook process per tool call in toolkit projects. An earlier draft gave this as "about 1 s on the PC". That figure was the PC's general per-hook cost, not a measurement of the extra wait, and all matching hooks run in parallel (hooks docs: "All matching hooks run in parallel"). §3.6 measures the real cost. An earlier draft also said part 3 (the mod) removes this cost. That is unverified: when the plugin is off, its mod is off too, so the guard can't depend on it. Whether a mod can answer this hook in-process while the plugin is on is a question for part 3's spec.
- **Lockout escape:** slash commands are not tools, so `/plugin install` still works from the locked session. After the install, a restart writes the marker.
- **Not an escape:** `.claude/git-guard-off` is not honoured here, as with the pre-push hook.
- **Build checks:**
  - The prototype used matcher `Bash` only. The empty matcher must be tested two-sided: refused without the plugin, allowed with it.
  - Subagent tool calls must carry the parent's `session_id`, and are verified not to be refused.

### 3.4 What stays in the project

- **`hooks/git-pre-push.sh` and `hooks/lib/git-cmd.sh`.** Git runs the native pre-push hook outside Claude Code, so it needs a stable path in the clone. The installed plugin path changes with every version (F5).
- **The gate runner:**
  - It moves into the plugin as `bin/cct-gate`, a thin wrapper that runs the plugin's `run-gate.sh` (F6). Agents and the user type `cct-gate`, and the project permission becomes `Bash(cct-gate*)`.
  - The gate artifact is then written and read by the same plugin version, so no version contract crosses the gap between the plugin and the project.
  - In the toolkit repo itself, `bash hooks/run-gate.sh` from the working tree stays, as in §3.2.
  - F6 holds on Linux and Windows, so no per-project `run-gate.sh` and no artifact version contract are needed. `cct-gate` is run from the Bash tool; on Windows the PowerShell tool is not a supported way to call it (untested there).
- **Pre-push and no-push-main protect the same branches,** but from two copies that can be at different toolkit versions: the project's copy and the plugin's. Both read the protected set from the same `PROJECT_CONTEXT.md` line through `gc_protected_branches`. Only a change to that function's meaning could make them differ. When it changes, the CHANGELOG must say so under its downstream migration. The skill's `requires_skill` floor, already in place, makes the next sync bring the matching project copy. This is a known limit, not a new mechanism.

### 3.5 Registration form

- **Linux:** `bash "${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.sh" <name>`.
  - `run-hook.sh` is the one wrapper. It does the toolkit-project test (§3.1) and the step-aside (§3.2), then execs `hooks/<name>.sh` (`exec bash`, so the hook keeps its own `$0`).
  - The polarity stays per hook, as today:
    - the guards that fail closed exit 2 when their script is missing;
    - the diagnostics and the output guard exit 0.
- **Windows:** the same form. The PC spike (F1) showed plain `bash` resolving in the hook shell from Git Bash and pwsh sessions, so no per-machine path rendering is needed. Should a machine's hook shell lack `bash`, every shell-form hook fails to start, the guard included, and Claude Code treats that as non-blocking. That is the same exposure today's project registrations have, not a new one. The smoke script (§5) adds a checkout path with a space.
- **`verify-hooks.sh`** also learns to read the plugin's `hooks/hooks.json`, so the session-start doctor still sees every registration.

### 3.6 Hook cost: measured; one registration per hook, in parallel (user rulings 2026-10-12 10:16 and 22:17)

Hook processes started per tool call, counted from the registrations (today's user-level copies start a process before they step aside):

| Tool call | Today, toolkit project | Plugin, one process per hook, plus the guard | Plugin, one process per call, plus the guard |
|---|---|---|---|
| Bash | 10 (7 project + 3 user-level) | 8 | 2 |
| Edit / Write | 3 | 4 | 2 |
| Read | 4 (3 + 1) | 4 | 2 |
| any other tool | 1 | 2 | 2 |
| Bash in a non-toolkit repo | 3 | 7 (the project-only hooks start, then exit at once) | 1 |

- **Measure first.** `measure-hooks` (a throwaway harness, to become part of `scripts/plugin-smoke.sh`) runs headless `claude -p` for N sequential `true` Bash calls in a scratch project and times each call from its `tool_use` to its `tool_result` in the stream. It compares no project hooks, today's project hooks, and today's hooks plus the guard. It also runs a two-sided check that the guard refuses every call when no marker is written. On the PC it runs only after the Windows hook suite and never alongside it.
  - **Linux result (agent-host-1, 2026-10-12 10:20, 15 calls each, haiku), median wait per call:** no project hooks 0.49 s, today's hooks 0.49 s, today's hooks plus the guard 0.53 s. The differences are within the spread (min 0.34 s, max 0.68 s), so on Linux neither today's hooks nor the guard cost a measurable amount. The two-sided check passed: with no marker, 4 of 4 calls were refused.
  - **PC result (Windows, 2026-10-12 18:10–18:13, main 832bb11, 15 calls each, haiku, Claude Code 2.1.296, machine otherwise light):** median wait per call: no project hooks 0.57 s (p90 1.05), today's hooks 1.00 s (p90 1.70), today's hooks plus the guard 0.90 s (p90 1.27). The two-sided check passed: 4 of 4 refused. On the PC, today's project hooks cost about 0.4 s per Bash call. The guard costs nothing measurable: its median fell below today's, which is noise at n=15, not a saving. So the guard is not the cost problem; today's hook count is.
  - **Not yet measured:** the dispatcher itself. Today's ten processes start in parallel, while the dispatcher runs its hooks in turn, one subshell each. On Windows, where a fork is expensive, it could therefore be no faster. Before the dispatcher is built, a prototype runs through the same harness on the PC in two forms, with subshells and with functions. Its median must come in below today's 1.00 s, or the design changes.
  - **Prototype result (PC, 2026-10-12 21:16–21:21, quiet: 18→26 ms per spawn, v4.6.0, n=15, today and dispatch each run twice, interleaved):** median wait per call: none 0.50 s, today 1.21 / 1.07 s, dispatch (serial subshells) 2.22 / 1.80 s, floor (the dispatcher with the guard, no hooks) 0.54 s. **The serial dispatcher is slower than today by about 0.7–1.0 s per Bash call.** The minimums agree (1.61 against 0.86), so this is not noise. The floor shows that one bash process with the guard and table matching costs about 35 ms; the cost lies in running the hooks one after another. (The prototype skipped agent-budget-warn because of a table-parsing bug, found afterwards. That hook costs 7 ms, so the verdict stands.)
  - **Why (Linux, per hook, `true` payload, 5 reps):** each Bash-matching hook costs 80–175 ms on its own. Serially that sums to 616 ms; in parallel, as today, the slowest takes 174 ms. Nearly all of each hook's time is one `node` start, made to parse the JSON payload (execve trace of deny-hang-shapes: bash, dirname, cat, node). A serial dispatcher pays that start once per hook. PC (21:24, light load, 62 ms per spawn, mins, ±16 ms because the Git Bash clock ticks at 64 Hz): bash baseline 24 ms; a plain node-parsing hook 139 ms; enforce-delegation 296 ms; pre-commit-test 435 ms; bash-output-guard 61 ms. Serial sum 1,471 ms against a parallel max of 435 ms. The 1.04 s difference matches the claude-level gap. So on the PC today's wait per Bash call is set by pre-commit-test alone; making that one hook cheaper is the biggest single saving without any design change.
  - **Consequence (user ruling 2026-10-12 22:17):** drop the one-process dispatcher. v5.0 keeps one `hooks.json` registration per hook, run in parallel as today, plus the guard. Measured on the PC, that design costs the same as today (guard 0.90 s against today 1.00 s, within noise). The real lever is a cheaper hook: parsing the payload once per call instead of starting node in every hook. That touches the fail-closed JSON core, so it is a separate spike after v5.0, or it falls away with the mod stage (in-process, no spawns).
- **SUPERSEDED (22:17 ruling; kept for the record): one process per call.** `hooks.json` registers one dispatcher per event, with an empty matcher, instead of one entry per hook. Overlapping matchers (`Bash|PowerShell`, `Read|Bash`, `Bash`) would otherwise start several dispatchers for one call. `run-hook.sh` reads `tool_name` once, picks the hooks whose matcher fits (the matcher table lives in the dispatcher and is checked against §3.1's table by consistency), and runs them in turn in the same bash process. The toolkit-project test (§3.1) runs once per call, and the step-aside test (§3.2) once per hook. The cost of this choice: in a non-toolkit repo, a tool that no hook matches (Grep, for example) now starts one process, where today it starts none.
  - Each hook keeps its own polarity (§3.5). A deny from any hook is the call's result. A hook that exits 0 passes control to the next one.
  - Today's hooks are separate scripts that call `exit`. The dispatcher runs each in a subshell, `( . hooks/<name>.sh )`. That is a fork, not a new program start, and on Windows it still costs a process. The measurement decides whether subshells are cheap enough there, or whether the hooks must be turned into functions.
  - Order matters only for output. The hooks don't depend on each other today, and hooks run in parallel today, so no ordering is relied on.

### 3.7 Sessions without the plugin: cloud and headless (user ruling 2026-10-12: solve before §4)

Docs, fetched 2026-10-12:
- **Cloud sessions** (claude.ai/code, routines, `--cloud`) never load a repo's `enabledPlugins` and never add its `extraKnownMarketplaces`. Those need the workspace trust dialog, which a cloud session never shows. They also don't load the user's locally installed plugins.
- **Headless `claude -p`** ignores `extraKnownMarketplaces` and loads only plugins already installed on the machine.
- **Remote Control** runs on the local machine with its local setup, so it is not affected.
- Cloud sessions set `CLAUDE_CODE_REMOTE=true`.
- A cloud environment's setup script runs before Claude Code starts, and `claude plugin install` is documented for scripts. The docs don't say whether a plugin installed by a cloud setup script is loaded by that session.

Consequence: as drafted, §3.3's guard refuses every tool in a cloud session in a synced project, so the standing "use the cloud" routines would stop working there.

Candidate fixes, in order of preference (to be tested before §4):
1. **The cloud environment's setup script installs `cct`** (`claude plugin marketplace add dagonet/claude-code-toolkit && claude plugin install cct@dagonet`). Fail-closed stays intact. It needs a cloud spike: does a setup-script install load in the session, and does the guard then see the marker?
   - **Cloud probe, 2026-10-12 10:41 (one-off routine, sonnet, CC 2.1.296, no setup script; a nested `claude -p` inside the cloud VM stood in for the setup script):** `claude plugin marketplace add` + `install` inside the VM worked (user scope). A `claude` started afterwards loaded the plugin, its SessionStart hook wrote the marker, and the project guard allowed the call. With the plugin disabled and the marker cleared, the guard refused; re-enabled, it allowed again. So the setup-script route works for a `claude` started after the install. Not yet proven: that the **main** cloud session, which the environment runner starts, loads it too. That needs one run in a cloud environment that actually has the setup script.
   - **PROVEN, 2026-10-13 16:23 (the user's own cloud environment `cct-plugin-probe` with a real setup script, CC 2.1.296):** the setup script ran as root (HOME=/root, `claude` at /opt/node22/bin/claude). A throwaway local marketplace plus `claude plugin install` succeeded (user scope, enabled). The **main** session's SessionStart hook then ran: the marker carried sid 6f772e22-…, the same as the session's `CLAUDE_CODE_SESSION_ID`, and the hook's additionalContext reached the model with the same sid; `CLAUDE_CODE_REMOTE=true`. **So fix 1 works and §3.7 is solved by it; fix 2 (the fail-open skip) is not needed.** The setup script is in the ledger entry for 2026-10-13. Still open for the build: installing from the GitHub marketplace instead of a local one, and pinning a tag. Network access is needed for both.
   - **Not available:** the routine API's `enabled_plugins` / `extra_marketplaces` fields were accepted and then silently dropped (both stayed `[]`).
   - **Found on the way: the session id is inherited.** The nested `claude -p` reported the outer session's id (the env carries `CLAUDE_CODE_SESSION_ID`), so it found the outer session's marker and passed even with the plugin disabled. A marker keyed on the session id therefore can't tell a nested `claude` without the plugin from its parent with it. This matters for any nested `claude` (the smoke script, gate fixtures). The marker should be keyed on something per-process, or the guard must accept this as a known limit. To decide during the build.
2. **The guard skips when `CLAUDE_CODE_REMOTE=true`.** Simple, but a cloud session then runs with no toolkit checks at all, and an environment variable can be set by anyone. This is fail-open; it is only acceptable if the user rules that cloud sessions are trusted.

## 4. Moving machines and projects over — APPROVED 2026-10-13

~~Blocked on §3.7~~ Unblocked 2026-10-13: §3.7 was solved by the setup-script install (fix 1, proven in a real cloud environment). Each cloud environment used with a synced project needs the `cct` install in its setup script.

Order per machine. At every step exactly one copy of each hook acts, and no project is ever left refusing every tool.

1. **Release v5.0.** `requires_skill` in `templates/ownership.json` rises to `>=v5.0.0`, so a v4.x sync skill refuses to sync a project to v5.0. Otherwise a v4.x skill could add the guard to a machine without the plugin.
2. **Install the plugin on the machine.** Projects that are not synced yet still register their own hooks, so the plugin steps aside there (§3.2). The old user-level copies also make the plugin step aside, so nothing fires twice.
3. **Remove the old user-level copies:**
   - Linux: the shrunk installer;
   - PC: the documented list.
   - From now on the plugin's machine-wide hooks act.
4. **Sync each project with `/cct:sync-template`.** That skill exists only when the plugin is loaded, so a project can only reach v5.0 from a session that has the plugin. The sync:
   - deletes the project's agent and hook files, except §3.4's set;
   - removes the hook registrations from `.claude/settings.json`;
   - adds the guard (§3.3) and `Bash(cct-gate*)`.
   - From the next session on, the plugin's project-only hooks act there.
5. **Other machines with the same project:** after a `git pull`, the guard refuses until that machine has the plugin. That is the intended fail-closed path, and its message says what to do.

Rollout order:
1. agent-host-1 (Linux), first on a scratch project, then on this repo;
2. one consumer: penumbra, the smallest;
3. the PC, once the Windows checks in §5 pass;
4. the remaining consumers.

**Rollback:** revert the project's sync commit. The project's own registrations come back and the plugin steps aside again. Uninstalling the plugin is not a rollback; it leaves the guard refusing, by design.

## 5. Testing and release gate — APPROVED 2026-10-13

- **Consistency checks (new):**
  - `plugin.json` version equals `VERSION`;
  - `marketplace.json` parses and names `cct`;
  - every script `hooks.json` names exists and is classed in §3.1's table;
  - every `cct:<agent>` the docs mention exists;
  - no agent file carries frontmatter `hooks:` (they would be silently ignored, F4).
- **Hook suite (new fixtures, all two-sided):**
  - toolkit-project signal present or absent;
  - step-aside through the project settings and through the user settings;
  - the guard: marker present, marker missing, `session_id` missing, malformed stdin;
  - `run-hook.sh`'s per-hook polarity when a script is missing;
  - `cct-gate` writes the same artifact `run-gate.sh` writes today.
- **Plugin smoke script (`scripts/plugin-smoke.sh`, run before each release, not in the gate):**
  - It runs nested `claude -p --plugin-dir <checkout>` in a scratch repo. It touches nothing under `~/.claude`.
  - Checks: a blocked push is refused and its side-effect file is absent; an innocent command runs; the guard refuses with the plugin disabled; `cct-gate` resolves; a `cct:Explore` spawn works.
  - The PC runs it from Git Bash and from PowerShell.
- **Release gate:** the usual three gate commands and the parser matrix, plus the smoke script on Linux and on the PC, plus the Windows hook suite. Drift 0 now means: the plugin is installed at the release version, and the user-level leftovers are gone.
