# Template Sync

[Back to README](../README.md)

After initial setup, keep projects in sync with template changes using two skills. Both skills delegate all deterministic operations (hashing, diffing, placeholder replacement, three-way merge) to the **template-sync-tools** MCP server — the AI handles only user interaction and judgment calls.

## Prerequisites

- `.claude/template-manifest.json` must exist (generated by the setup script)
- **template-sync-tools** MCP server must be registered (see [`mcp-servers/HOWTO.md`](../mcp-servers/HOWTO.md))
- If template-sync-tools is not available, the skills will not function

## `/sync-template` (downstream: template -> project)

Pull template updates into your project. The skill calls MCP tools to classify each file:

| Template changed? | Project changed? | Status | Action |
|---|---|---|---|
| No | No | `UP_TO_DATE` | Skip |
| No | Yes | `PROJECT_CUSTOM` | Skip (your customization preserved) |
| Yes | No | `AUTO_UPDATE` | Auto-apply template update |
| Yes | Yes | `CONFLICT` | Three-way merge, you resolve |

**That table is exhaustive over its two axes and only over those.** Its axes are both *changes*, and **a deletion is an absence, not a change** — so two real states have no cell in it and are reported alongside it, not inside it: `TEMPLATE_DELETED` (the template no longer ships a file the project still has — see *Deletion* below) and `new_template_files` (a path the manifest has never tracked). Neither is a cell you can reach by answering "template changed? / project changed?".

For conflicts, the MCP server reconstructs the common ancestor via `git show` and produces a three-way merge. If the merge is clean, it's offered for approval. If it has conflict markers, you resolve manually.

## `/contribute-upstream` (upstream: project -> template)

Push project improvements back to the template. The skill:

1. Identifies locally modified template-sourced files (skips `PROJECT_CONTEXT.md`)
2. Shows diffs for each — you classify as generalizable or project-specific
3. Reverses placeholder replacement deterministically (longest values first)
4. Checks cross-variant file identity and propagates to matching variants
5. Stages changes in the template repo (does not commit — you review first)

## `/commit` Integration

When committing, if `.claude/template-manifest.json` exists, the commit workflow calls `template_compute_status` to detect drift:

- **Locally modified files**: Prints a reminder to run `/contribute-upstream`
- **Template updates available**: Prints a reminder to run `/sync-template`

This is informational only — it never blocks a commit.

## Manifest v2: `.claude/template-manifest.json`

Generated by `setup-project.ps1` (Windows) or `setup-project.sh` (Linux/macOS). The v2 format tracks:

| Field | Purpose |
|-------|---------|
| `version` | Schema version (currently `2`) |
| `variant` | Which template was applied |
| `templateRepo` | Path to the claude-code-toolkit repo |
| `lastSynced` | Git commit hash of last sync point |
| `lastSyncedVersion` | Toolkit tag for `lastSynced` (optional label, **client-written** by `/sync-template` since v2.2.5) |
| `lastSyncedVersionOf` | The `lastSynced` sha `lastSyncedVersion` was computed from (optional label, **client-written**, paired with the row above) — unequal to `lastSynced` means the label is stale AND KNOWN STALE |
| `templateSyncToolsVersion` | `template-sync-tools` version that performed the sync (optional label, **server-written** — reserved, no server emits it yet) |
| `placeholders` | Concrete values used during setup (for reverse-mapping) |

**The eight `files.*` fields.** Only the first four used to be documented, and the gap caused a real false red: a consumer's validator hash-checked every string field under `files.*` and reported `resolution: "keep-mine"` as MALFORMED. **Five of the eight are SHA-256 hex; three are not, and must never be validated as hashes.**

| Field | Hash? | Purpose |
|-------|-------|---------|
| `files.*.templateHash` | hash | SHA-256 of template file after placeholder replacement |
| `files.*.templateRawHash` | hash | SHA-256 of template file before placeholder replacement |
| `files.*.localHash` | hash | SHA-256 of project file at last sync (common ancestor for merge) |
| `files.*.localPartHash` | hash | SHA-256 of the project file **excluding** its `PROJECT-CUSTOM` region, so region content is not mistaken for deviation |
| `files.*.templatePartHashAtSync` | hash | the same part-hash taken over the template file at sync time; `localPartHash == templatePartHashAtSync` is what makes a file `region_only: true, deviates_from_template: false` |
| `files.*.locallyModified` | **no** — boolean | see the note below; it means *deviates from the template*, not *changed since sync* |
| `files.*.resolution` | **no** — enum string | written by `template_apply_file(source="skip")` as `"keep-mine"`; `source="template"` and `source="provided"` omit the key entirely. It is the discriminator a guard keyed on the decision that was made must read |
| `files.*.reason` | **no** — free text | optional human note recorded beside `resolution`; not emitted by every server version, and never parsed |

**Entries that predate the two part-hash fields carry a hint** ("re-register to get region-aware classification"). Until they are re-registered the server cannot tell region content from real deviation and must report the file as deviating; an empty hint set is the healthy state, not a skipped step.

**Top-level key order is part of the shape (v2.2.6).** The table above is also the order:

```
version, variant, templateRepo, lastSynced, lastSyncedVersion, lastSyncedVersionOf,
templateSyncToolsVersion, placeholders, files
```

This is the single authoritative list — `/sync-template` step 7b rebuilds the mapping in it and asserts `list(manifest)[:6]`, rather than assigning into the loaded dict. Assignment appends, and because every writer mutates-and-re-dumps, an appended key stays appended forever: one consumer's two version labels landed 270 lines below the `lastSynced` they annotate, past the whole `files` map, where a reader checking the header sees a bare sha and concludes nothing was stamped. Every other check reads BY KEY and is blind to position. Two known-benign exceptions: a pre-v2 manifest carries `version` last (the v1→v2 migration appends it and no sync corrects it), and unknown top-level keys are preserved at the end rather than dropped.

The `templateRawHash` field detects template changes without recomputing placeholder replacement. The `localHash` field serves as the common ancestor for three-way merge during conflict resolution.

**`locallyModified` means *the file deviates from the template*, NOT *the file changed since the last sync*.** Those are the same only by coincidence, and this doc taught the superseded pre-0.2.0 meaning long after the server stopped using it. The live counterexample that settles it:

```
locally_modified: true, deviates_from_template: true, changed_since_sync: FALSE
```

Impossible under the old reading; ordinary under the correct one — a file can deviate from the template without anyone having touched it since the last sync, because the *template* moved. The old meaning has its own field, `changed_since_sync`, and the two answer different questions: `locallyModified` asks *does this file differ from what the template ships?*, `changed_since_sync` asks *has anyone edited it since the sync point?*

**It is derived/informational, not authoritative** — `template_compute_status` recomputes it from the file on disk on every run, so a stale stored flag never affects classification (v2 manifests; the stored flag only feeds the v1-migration fallback).

**The two version fields are additive labels, and absent means *unknown*, never *stale*.** They exist because `lastSynced` alone is an opaque hex string: answering "which toolkit version is this repo on?" otherwise requires the toolkit checkout to be present with its tags fetched. Nothing classifies, gates or migrates on either field, and a sync never fails because one would not resolve. `lastSyncedVersion` is written by the skill from `git -C <templateRepo> describe --tags [--exact-match] <lastSynced>` and is therefore reproducible but *not* server-authoritative; `templateSyncToolsVersion` is deliberately left for the server, since the client has no honest way to observe the running server's version.

v1 manifests (missing `version`, `templateRawHash`, `localHash`) are auto-migrated to v2 by the `template_load_manifest` MCP tool.

## Deletion: `TEMPLATE_DELETED`

The 2×2 above cannot express deletion, and this doc did not mention it at all — zero hits for `delet`, `TEMPLATE_DELETED` or `git rm` across the whole file — while consumers were performing deletions on every release that retired something. **The contract is here; the step-by-step mechanics stay in the skill, which owns the ordering and the safety rules (a file whose `PROJECT-CUSTOM` region is non-empty is never offered for deletion).**

- `TEMPLATE_DELETED` means the template no longer ships a path the manifest still tracks. It is a state the classification table cannot reach, because the template's *absence* is not a *change* to a file.
- **A manifest entry drops when the template no longer ships the file AND the project no longer has it.** Both halves. Removing it upstream while the project keeps its copy leaves the entry in place, which is correct: the project still has a file whose provenance you want recorded.
- **`deleted_files` is not required when `git rm` precedes finalize.** Deleting on disk first is a supported order — finalize then observes the absence rather than being told about it.
- **Assert on the count of dropped entries that finalize reports, not on its exit code.** "The deletion took" and "finalize ran and changed nothing" are indistinguishable from the exit code alone; the count is the only thing that separates them. (The field name is the server's to state — this repo ships no definition of it, so do not hard-code one from memory.)

## `keep-mine`: the mechanism for files you never want overwritten

`keep-mine` appears in none of the shipped documentation outside a mid-sync resolution prompt, and **all four consumers surveyed use it for the files they care about most.** It is a concept, not just a menu item, and it has a cost worth stating before you choose it.

Resolving a file `keep-mine` (`template_apply_file(source="skip")`) keeps the project's version and records `"resolution": "keep-mine"` on that file's manifest entry. `CLAUDE.local.md` is the routine case.

**The trade-off, stated plainly: a `keep-mine` file never receives template improvements again, and you re-decide it on every sync.** The template will keep moving; your copy will not follow. The recorded resolution is what lets a guard tell a user-approved divergence from an accidental one — a check keyed on the file's path instead would fire on the correct outcome.

**Do not reach for the `PROJECT-CUSTOM` region as a substitute, and do not demote a region to a `keep-mine`.** They solve different problems: a region keeps *part* of a file project-owned while the rest keeps tracking the template; `keep-mine` freezes the *whole* file. Choosing `keep-mine` for something a region would have covered gives up every future template fix in that file to protect a few lines.

## The Gate Artifact: `.gate/last-pass.json`

**This format is a contract, not an implementation detail.** Replacing `hooks/run-gate.sh` wholesale is a supported shape — the terminal-exit contract is public precisely so that a project can supply its own runner — which makes the artifact the interface between the half that runs the gate and the half that reads it. It had not been written down anywhere, and one consumer discovered their own runner's shape by reading their own script.

`hooks/run-gate.sh` writes, at the repo toplevel of the current checkout **or worktree**:

```json
{"sha":"<HEAD sha>","tree":"<working-tree hash>","branch":"<branch>","ts":"<UTC ISO-8601>","status":"pass"}
```

What `hooks/gate-before-merge.sh` actually **reads** is narrower than what is written, and that asymmetry is the useful half of the contract:

| Key | Read by the gate? | Notes |
|---|---|---|
| `sha` | **yes** | must equal the checkout's `HEAD` |
| `tree` | **yes** | *or* must equal `HEAD^{tree}`; either match is sufficient. Added in v2.1.5 — this is the half that survives a squash, and the half that matches when the gate ran just before `git commit` |
| `branch` | no | informational |
| `ts` | no | **freshness is judged from the file's mtime, not from this field** — the artifact must be younger than 60 minutes |
| `status` | no | informational |

A minimal replacement runner therefore needs `sha` **or** `tree`, plus a fresh mtime. Two parsing rules matter if you write your own: the reader tolerates whitespace after the colon (`{"sha": "…"}` is valid JSON and a consumer emitted exactly that, was silently read as empty, and got blocked on every merge with `artifact sha: none`), and a red gate **deletes** the artifact rather than writing `"status":"fail"` — absence is the failure signal.

## Hooks Are Root-Tracked

Variants do **NOT** ship a `hooks/` directory. All hook scripts live once at the toolkit ROOT `hooks/` — a single source with zero cross-variant drift. Everything that consumes them resolves against the root:

- `setup-project.{sh,ps1}` copy `hooks/*.sh` from the toolkit root into new projects and register them in the manifest with a `hooks/` prefix.
- The sync server routes manifest paths starting with `hooks/` to the toolkit root (`_ROOT_TRACKED_PREFIXES` in `template_sync_mcp.py`) for status, diff, and apply.
- `/sync-template` step 6b materializes a missing hook via `template_apply_file(file_path="hooks/<name>.sh", source="template")` — never by copying from `templates/<variant>/hooks/`, which does not exist.
- `scripts/verify-template-consistency.sh` §13 asserts every hook referenced by any variant's `settings.json` or agent frontmatter exists non-empty at the root.

If a downstream sync reports a hook as missing from a variant: that is expected — the variant never carries it; the root does.

## Rollout: a Template Is a Source, Not a Shipment

Merging a hook into `templates/` changes nothing in any existing project. Enforcement needs **two** things in the consuming repo, and `/sync-template` installs both:

1. the script at `<project>/hooks/<name>.sh`, and
2. its binding in `<project>/.claude/settings.json`.

This is not theoretical. The v1.1 agent-liveness hooks were merged to `templates/` and, days later, were present in **one of 15** projects — the other 14 had no such hook entry and mostly no `hooks/` directory, so for them the feature did not exist. Determining that took a multi-hour transcript investigation.

**Check any project in one command:**

```bash
bash scripts/check-activation.sh /path/to/project
```

It reports the `settings.json` bindings, which hook scripts are on disk, whether a kill switch (`.claude/liveness-off`, `.claude/delegation-off`) is disabling enforcement, the contents of `.claude/liveness.log`, and the ledger directories under `TMPDIR` that prove whether the hooks have ever actually executed.

Two things that look like failure but are not:

- **No hook output in the session transcript.** `PreToolUse` and `SubagentStop` hook stderr is delivered to the *subagent*, not to the lead's transcript. Grepping the transcript for a hook's own message will find nothing even when the hook is firing correctly. Use the ledger directories or `.claude/liveness.log` instead.
- **An empty `.claude/liveness.log`.** It records threshold events only. A hook that has run thousands of times without crossing a threshold writes nothing there; its counter files still prove execution.

These hooks are deliberately **not** registered at user level (`~/.claude/settings.json`): their commands are `bash hooks/…`, resolved relative to the project root, and would break in any repo that has not been synced.

## PROJECT-CUSTOM Region

Every template `CLAUDE.md` ends with:

```markdown
<!-- PROJECT-CUSTOM:BEGIN — sync-template preserves everything between these markers -->
<!-- Project-specific rules, routing blocks, and extensions go here. -->
<!-- PROJECT-CUSTOM:END -->
```

> **⚠ THAT IS THE CURRENT AND ONLY SHIPPED MARKER TEXT — do not copy the wording from any older document.** The `BEGIN` marker carries an em-dash and the trailing prose *"sync-template preserves everything between these markers"*. Earlier records in `docs/` quote a superseded wording (*"never edits below this line"*) that **no shipped file carries**, and they are dated historical records, correct as of their date and deliberately not rewritten.
>
> **Do not hand-roll a matcher against either string.** v3.0.0 shipped `user-level-reference/skills/sync-template/region.sh` precisely because **two consumers implemented the marker check from prose and both got it wrong** — one matched `PROJECT-CUSTOM:BEGIN\s*-->`, which the em-dash and trailing prose defeat, and got *"zero regions"* on a repo with eleven. The reassuring answer is the one a wrong matcher returns. Use `region.sh`.

Project-owned content goes INSIDE the markers. When both the template and the project file carry the markers, the sync server treats the region as project-owned: region-only edits keep the file `UP_TO_DATE`, `template_apply_file(source="template")` splices the project's region into the applied template, and three-way merges exclude/reattach it. Content appended OUTSIDE the region conflicts on every template bump — move it inside.
